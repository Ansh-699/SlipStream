# Frozen check — R7 `keeper-role`

**Run:** `remediate` · **Slice:** `keeper-role` · **Issue:** `docs/runs/remediate/issues/07-keeper-role.md`
**Spec:** `docs/spec/remediate.md` — Decision 8

## Purpose

Three instructions gate on `GlobalState.authority`, and the fill-log keeper signs exactly those with
a loaded keypair on a keeper VM — so the BPF upgrade authority and the USDC mint authority are
structurally required hot in production. This slice adds a distinct `keeper` role so that key can
come down. It is the **only** part of `S10-01` that any code change in this repository can fix.

## Fix contract

- Item **1 or 2** failing is an environment problem, not a builder defect — see R1's contract.
- A failure of **4** means the keeper role does not work or a stranger slipped through. Fix
  `record_pending_fill.rs` / `initialize_fill_log.rs` / `delegate_fill_log.rs` or the accessor in
  `global_state.rs` — never the test.
- **A failure of 5 bricks the live deployment.** The live `GlobalState` is not extended, so the three
  instructions must fall back to `authority` whenever the account is short or the field is zero. If
  this item fails, the fill-log keeper stops working the moment the program is upgraded and before
  `set_keeper` is ever called. Fix the fallback, not the test.
- A failure of **6** means `set_keeper` is missing, mis-gated, or does not extend the account.
- A failure of **7** means `GlobalState::LEN` moved off 104. The keeper field goes **past** `LEN` at
  offset 136, exactly as `pending_authority` sits past it at 104. Fix `global_state.rs`; do not touch
  `tests/unit/src/test_state.rs`.
- A failure of **8 or 9** means an existing authority regression broke — the very guards this slice
  is widening. Widening the accepted set must not weaken it.
- A failure of **12** is a lint regression introduced by this slice.

Duration hint: item 1 is a full SBF rebuild, roughly 1–3 minutes cold.

## What each item asserts, and why it can fail

1. The SBF artifact exists.
2. **No regression.** All 123 pre-existing tests still pass.
3. All three keeper tests exist and pass. The `match` is mandatory: a filter matching zero tests
   exits 0.
4. **The attack is blocked and the capability is real.** `record_pending_fill` signed by the
   installed keeper succeeds and bumps `pending_fills`; signed by a stranger it is refused and
   changes nothing. Verified to fail against the unmodified program with `Failure(Custom(257))` —
   `InvalidAuthority`, ordinal 1 — because only `global.authority` is accepted today.
5. **The live deployment is not bricked.** On a `GlobalState` at exactly `LEN` with no keeper field,
   `record_pending_fill` signed by `authority` still succeeds. **This item passes before *and* after
   the fix — it is a guard, not a fix test**, and it is recorded as such so nobody mistakes its green
   for evidence the slice landed.
6. `set_keeper` refuses a stranger, and the authority's call extends the account and writes the
   pubkey at offset 136. Verified to fail against the unmodified program with
   `Failure(InvalidInstructionData)` — the instruction does not exist today.
7. `GlobalState::LEN == 104` and the whole layout module, 32 tests, unmodified.
8. `record_pending_fill`'s existing authentication regression passes unmodified. This is the guard
   the slice is directly widening.
9. The two-step authority rotation still works. `propose_authority` uses the same lazy-resize pattern
   the keeper field extends; breaking it would strand the only path to rotating the admin key.
10. The new instruction file exists on disk. Filesystem `test -f`, not `git grep`: a builder's new
    file in an unstaged worktree is invisible to `git grep`.
11. The dispatch constant is present. Pre-landed at freeze; this catches removal or rename.
12. **HARD STOP guard.** `deploy.json` is untouched. This run performs no key ceremony, no
    authority rotation, no deploy. A diff here is an automatic FAIL regardless of the rest.
13. No new lint.

  and treasury re-point are key-ceremony actions, and intake ruling 6 performs none of them. The job
  report must say so plainly rather than implying `S10-01` is closed. It is not — only its code half
  is.
- The faucet route reading the same key from an environment variable on a public HTTPS endpoint
  (`frontend/src/app/api/faucet/route.ts:85-100`) is a deployment-configuration problem, also not a
  code fix, also not closed here.
- Moving the other five keeper services and both bots to an unprivileged fee-payer key needs no
  program change at all. That is an ops action and is out of this slice.
