# S7 — Keepers

Audited at freeze `b98f0508b01af619f84a6cbb82b6326ebbcd7f9f`. Read-only devnet RPC was used
for the live account reads quoted below; no transaction was signed or sent.

K1 is the given: the keepers have been down since 2026-08-05. This slice's job is *why it
was possible*. Three mechanisms account for it and each is filed separately: nothing in
the repo can observe a stalled keeper (S7-01), a transient boot-time failure is
permanently fatal under the supervisor the repo ships (S7-02), and the fleet's steady-state
request rate against a public RPC endpoint is high enough that the quota exhaustion in the
root-cause chain is a designed-in property, not bad luck (S7-03).

## Calibration

> Flag only gaps that affect correctness, the stated requirements, or documented project invariants -- cite file:line evidence for every finding. Do not report stylistic preferences.

## Findings

### S7-01 · Nothing in the repository can observe a stalled keeper

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S7-C5
- **Evidence:** `keepers/ecosystem.config.js:7-13`, `keepers/src/twap-keeper.ts:46-53`, `keepers/src/liquidation-keeper.ts:312-319`, `keepers/src/fill-log-keeper.ts:372-379`, `frontend/src/app/api/status/route.ts:64-79`, `programs/slipstream/src/state/market.rs:13-16`

**What is wrong.** Every keeper's failure signal is a line on stdout and nothing else.
`ecosystem.config.js:7-13` is the only operational instrumentation in the whole fleet and
it configures *log rotation* — there is no health endpoint, no heartbeat write, no
threshold, no notifier. The consequence is not merely "no pager": each keeper's error
branch resets its own counter after backing off (`twap-keeper.ts:49-53`,
`liquidation-keeper.ts:315-319`, `fill-log-keeper.ts:375-379`), so a keeper that has failed
every single iteration for sixteen days is, from outside the process, indistinguishable
from one that is working. The program itself writes down the invariant this violates:
`market.rs:13-16` states that `last_mark_price` going stale means "the price feed is
effectively dead" and gives it a 30-minute budget. Nothing in the repo watches that field.
The one liveness-adjacent signal that exists, `/api/status`'s `indexer.lastFillAt`
(`frontend/src/app/api/status/route.ts:64-79`), is a raw timestamp with no threshold, and
it covers only the fills indexer — not TWAP, funding, liquidation or expiry.

**Proof.** Exhaustive grep for any alerting primitive across the entire keeper fleet plus
its supervisor and env template — no matches (grep exit status 1):


The oracle is 105 seconds fresh; the mark the protocol prices liquidations and
close-at-market against is 16.2 days stale and 22.7% below it. `MARK_PRICE_MAX_STALENESS_MINS`
is 30 (`programs/slipstream/src/state/market.rs:16`), so the deployment has been ~780x past

**Blast radius.** Every holder of an open position. With the mark frozen 22.7% below spot,
`compute_health_factor` prices every long as deeply underwater and every short as richly

absence of monitoring is what converts a routine event into a 17-day one.

the existing `fills.db`) at the end of every successful iteration, and add one process that
compares `market.last_mark_price`'s recorded minute (`Market::set_mark_price_minute`) and
each heartbeat against a threshold and exits non-zero; wire that to whatever notifier the
box has. Do not reset `consecutiveErrors` after a backoff without emitting the count.

### S7-02 · A transient boot-time failure permanently retires a keeper, and the retry guard written to prevent that sits below the first network call

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S7-C3
- **Evidence:** `keepers/ecosystem.config.js:28-34`, `keepers/src/fill-log-keeper.ts:343-363`, `keepers/src/fill-log-keeper.ts:98-105`, `keepers/src/fill-log-keeper.ts:385-388`, `keepers/src/funding-keeper.ts:9-11`, `keepers/src/liquidation-keeper.ts:14-16`

**What is wrong.** `ecosystem.config.js:29-33` records the intent in a comment — a boot-time
crash loop once burned the RPC quota, so `max_restarts: 50` was added. pm2's semantics are
that a restart counts against `max_restarts` only when uptime is under `min_uptime` (30s),
and once the count is exceeded the app is parked in `errored` and never retried. With
`restart_delay: 5000` that is roughly **four minutes**: any failure at boot lasting longer
than ~250 seconds retires the keeper permanently, silently, until a human runs `pm2 restart`.
The fix for a quota burn therefore introduced a permanent-outage mode of exactly K1's shape,
and nothing (see S7-01) reports the transition.

The fill-log keeper makes this concrete. Its author wrote a retry-with-backoff loop
specifically so startup would stop crashing into pm2 (`fill-log-keeper.ts:352-363`: "the
old exit(1)-into-pm2-restart loop burned RPC quota on every relaunch (33k restarts
observed)"). But `discoverEpoch` — an unbounded `for(;;)` whose every iteration is an ER
`getAccountInfo` (`:98-105`) — runs at `:343`, **twelve lines above** that guard, outside
any try. So does the module-level `new PublicKey(process.env.SWITCHBOARD_FEED || …)` in
funding (`:9-11`) and liquidation (`:14-16`), which throws during module evaluation, before
`main()` exists. Each of those paths lands on `main().catch(… process.exit(1))`
(`fill-log-keeper.ts:385-388`) — the exact path the guard below was written to replace.

**Proof.** Every keeper's sole crash handler, and the guard's position relative to the first
network call:

pm2 restart budget from `keepers/ecosystem.config.js:32-34`:
`min_uptime "30s"` + `max_restarts 50` + `restart_delay 5000` = 50 x 5s ≈ 250s of tolerated
boot failure before the app is parked in `errored` with no further attempt.

**Blast radius.** Any operator on the pm2 path (which `PRODUCT.md:45` states is the live
one). A four-minute RPC or ER blip — routine on public devnet, and the very condition K1's
root-cause chain names — permanently stops the affected keepers. On a real-money deployment
that means funding stops accruing and liquidations stop firing until someone notices by
hand, which per S7-01 is not a thing this repo can do.

**Suggested remediation.** Move `discoverEpoch` inside the existing `for(;;)` retry block at
`fill-log-keeper.ts:355`, and resolve the Switchboard address inside `main()` rather than at
module scope in funding and liquidation. Separately, either drop `max_restarts` in favour of
a growing `restart_delay` (an exponential backoff bounds the quota burn without a terminal
state), or pair the cap with the alert from S7-01 so `errored` is not silent.

### S7-03 · The fleet's configured cadences issue two unbounded getProgramAccounts every 5s and re-download the 612 KiB order book once per bot wallet per 2s

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S7-C4
- **Evidence:** `keepers/src/liquidation-keeper.ts:20`, `keepers/src/liquidation-keeper.ts:103-108`, `keepers/src/liquidation-keeper.ts:221`, `keepers/src/shared/accounts.ts:87-104`, `keepers/src/market-maker-bot.ts:181`, `keepers/ecosystem.config.js:64`, `keepers/src/shared/subscriber.ts:18-37`

**What is wrong.** K1's root-cause chain starts at "public devnet RPC quota exhausted". That
is a property of the configured cadences, not an accident. The liquidation keeper's loop
runs every `POLL_INTERVAL_MS = 5_000` (`:20`) and issues **two** `getProgramAccounts` calls
per iteration — `fetchAllPositions` (`shared/accounts.ts:87-104`, called at
`liquidation-keeper.ts:221`) and `executeTriggers` (`:103-108`) — neither bounded by result
count or paginated. `getProgramAccounts` is the most expensive method a public endpoint
serves; at 5s that is 34,560 such calls per day from one IP.

Separately, `market-maker-bot.ts:181` fetches and decodes the **entire** order book once per
wallet per cycle, purely to filter it for that wallet's own resting orders, at the
`BOT_MM_INTERVAL_MS: "2000"` configured in `ecosystem.config.js:64`. The account is 626,736
bytes. Two MM wallets at 2s is one full order-book download per second, forever.

The repo contains the machinery to avoid this and does not use it on any supervised path:
`AccountSubscriber` (`shared/subscriber.ts:18-37`) wraps `onAccountChange`, and its only
importer is `settlement-keeper.ts`, which no supervisor launches (S7-06). Every process that
actually runs polls.

**Blast radius.** The whole deployment. Every keeper shares one endpoint, so the cost of the
liquidation keeper's polling is paid by the TWAP crank's ability to land a transaction — the
quota is a shared resource and there is no per-keeper budget, no jitter, and no adaptive
backoff on 429 (`shared/connection.ts:11-16` deliberately disables web3.js's internal retry
and delegates backoff to callers, but every caller's backoff is a flat sleep). On a mainnet
deployment this is a straight bill; on any rate-limited endpoint it is the K1 outage again.

**Suggested remediation.** Add a `dataSize` filter to `fetchAllPositions` (the trigger scan
at `:103-108` already has one) and cache the position set across cycles, refreshing it on a
much slower cadence than the price check; the two concerns do not need the same interval.
For the MM, replace the per-wallet `fetchOrderBook` with one fetch per cycle shared across
wallets — or use `AccountSubscriber`, which already exists, on the ER order book.

### S7-04 · Seven long-running processes each load the program upgrade authority to do work that needs no authority at all

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [mainnet-only]
- **Class:** S7-C1
- **Evidence:** `keepers/src/shared/connection.ts:25-29`, `keepers/src/shared/bot-wallets.ts:452-455`, `keepers/src/shared/bot-wallets.ts:338-342`, `keepers/.env.example:8-11`, `keepers/src/expiry-keeper.ts:11-15`, `deploy.json:5`

**What is wrong.** K2 (the operator key holding three capabilities) is established and
`PRODUCT.md:64` lists splitting it as open. What S7 adds is that the *keepers* are where
that key is actually resident, and that none of them needs it. `loadKeypair()`
(`shared/connection.ts:25-29`) reads `KEEPER_KEYPAIR`, `.env.example:8-11` points that at the
operator's `id.json`, and `getOperator()` (`bot-wallets.ts:452-455`) is literally
`return loadKeypair()` — the file itself calls the result "the deploy authority + USDC mint
authority", and `bot-wallets.ts:341` uses it as the `mintTo` authority. `deploy.json:5`
records that same key as `authority`. So all five supervised keepers plus both bots hold the
program upgrade authority and the mint authority in process memory, continuously, on a
network-facing box.

The work they do needs none of it. `expiry-keeper.ts:11-15` documents the shape: `cancel_order`
has a permissionless bypass, "ANY signer may cancel it, and the freed margin still returns to
the real owner's credit". The same is true of `crank_twap`, `compute_funding`,
`liquidate_position`, `execute_trigger` and `settle_from_log` — every one is permissionless
and needs a fee payer, not an authority. No written invariant grants keepers authority;
`shared/manifest.ts:177` frames their address resolution as a *configuration* concern, not a
privilege one. That unwritten invariant ("a keeper is an unprivileged fee payer") is not
recorded anywhere, which is itself part of the finding.

**Proof.** The keeper key and the operator key are the same object, statically — every
loader in the package, pasted:

**Blast radius.** On a real-money deployment, a single compromise of the keeper box — the
same box that runs seven Node processes speaking to two public RPC endpoints — yields the

a P0 outcome one host compromise away; it is filed P1 because the compromise is a
precondition, not a demonstrated path. On devnet the tokens are worthless, hence

for fees, and change `.env.example:8-11` to point `KEEPER_KEYPAIR` at it. Keep `getOperator()`
as a separate loader (a distinct `OPERATOR_KEYPAIR` env var) used only by the provisioning
scripts, which are run by hand and can take the real key at invocation time. Write the
"keepers are unprivileged" invariant down where the loader lives.

### S7-05 · The taker bot will cross up to ~6% through the live oracle mid, thousands of times a day, into whoever is at top of book

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [mainnet-only]
- **Class:** S7-C10
- **Evidence:** `keepers/src/taker-bot.ts:65-66`, `keepers/src/taker-bot.ts:168-179`, `keepers/src/taker-bot.ts:185-196`, `keepers/src/taker-bot.ts:49-56`, `keepers/ecosystem.config.js:71-78`, `keepers/src/market-maker-bot.ts:186-194`

**What is wrong.** The taker bot's two price bounds compose multiplicatively rather than
sharing a reference, so the guard the code believes it has is roughly six times looser than
the number in it. `MAX_SLIPPAGE_BPS` (default 100) is applied to the *book's* top-of-book
price (`:168-169`, `:176-178`), and `MAX_ORACLE_DEVIATION_BPS` (default 500) is checked
against `refLevel.price` — the top-of-book again (`:185-196`) — **not** against the
`limitPrice` that is actually signed. The bot therefore accepts a resting price up to 5%
away from Pyth and then prices its IOC a further 1% through it. The code's own comment at
`:49-56` states the reason no on-chain check catches this: "there is no on-chain oracle band
on limit prices". So the only bound on what this bot pays is these two constants, and
neither is applied to the number it sends.

The precondition for someone else collecting that spread is that they, not the market maker,
are at top of book. That is not hypothetical: the MM only replaces its ladder when
`myOrders.length < targetOrders * 0.6` or the mid has moved `REFRESH_BPS`
(`market-maker-bot.ts:186-194`), it goes silent when its credit is exhausted, and per S7-11
it logs nothing when its whole ladder is rejected — so "the MM is not quoting while the
taker is" is a reachable and undetectable state.

**Proof.** Static derivation from the constants in the file. The signed price is bounded
only by these two lines, and no other guard touches `limitPrice`:

```
$ grep -n 'limitPrice' keepers/src/taker-bot.ts
160:  let limitPrice: bigint;
169:    limitPrice = roundToTick(ask.price + slip, tick);
178:    limitPrice = roundToTick(target, tick);
210:      price: limitPrice,
216:      `${wallet.name} ${sideName} ${SIZE_LOTS}lot IOC @ ...

worst-case BUY price / pyth mid
  = (1 + MAX_ORACLE_DEVIATION_BPS/10000) x (1 + MAX_SLIPPAGE_BPS/10000)
  = 1.05 x 1.01 = 1.0605                      -> 6.05% above the oracle
```

Cadence and size, from the deployed config (`ecosystem.config.js:71-78`): 2 taker wallets,
`BOT_TAKER_INTERVAL_MS 15000` + `BOT_TAKER_JITTER_MS 8000` (~19s mean),
`BOT_TAKER_CROSS_PROB 0.8`, `BOT_TAKER_SIZE_LOTS 2`. At the market's `lotSize` of
100000000 (0.1 SOL, `deploy.json:14`) and the live mid of $90.99, that is ~7,300 fills/day of
~$18.20 notional each; at the 6.05% ceiling the bot's maximum daily give-up is on the order
of $8,000 against a `BOT_CREDIT_USDC` default of $5,000 (`shared/bot-wallets.ts:77`) — i.e.
the bound does not bind: the bot can lose its entire credit inside a day to a passive
counterparty who does nothing but rest orders.

**Blast radius.** The operator, who funds the bot. Any outside trader who rests inside the
5% band whenever the market maker is not at top of book collects the difference; no
protocol rule is broken and the program behaves correctly throughout. Inert on devnet
(credit is minted free from the operator's own mint authority), hence `[mainnet-only]`.

**Suggested remediation.** Apply the oracle-deviation check to `limitPrice` rather than to
`refLevel.price`, so the two bounds share one reference instead of compounding, and lower
`MAX_ORACLE_DEVIATION_BPS` to something inside the MM's own quoted band (the MM quotes
within 24 bps of mid at the configured `BOT_MM_SPREAD_BPS`/`BOT_MM_LEVELS`). Add a per-day
realised-loss stop that idles the bot.

### S7-06 · settlement-keeper.ts is superseded dead code, and `npm run all` still starts it instead of the keeper that actually settles

- **Status:** CONFIRMED

- **Class:** S7-C12

### S7-07 · Oracle addresses escape the manifest: `switchboardFeed` is declared and never resolved, and both bots read Pyth from a module constant

- **Status:** CONFIRMED
- **Severity:** P2

Note that `CREATE TABLE IF NOT EXISTS` also means a schema change here does not migrate an
existing `fills.db`; the live file keeps whichever key it was created with.

**Blast radius.** The frontend's `/api/trades` and `/api/status`, which read this file
directly (`fill-db.ts:7-8`), plus any operator using it as the settlement record. On the day
a second market is added, that market's trade history silently disappears from the UI and
`lastFillAt` starts reflecting only market 0 — with no error anywhere, because the write
path is explicitly best-effort by design.

**Suggested remediation.** Make the key `PRIMARY KEY (market_index, sequence)` and add a
one-off migration (`CREATE TABLE IF NOT EXISTS` will not alter the deployed file). While
there, have `recordSettledFills` compare `insertAll`'s change count to `fills.length` and log
a warning on a mismatch, so a silent drop is at least visible.
