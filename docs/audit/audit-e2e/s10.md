### S10-01 · One key is upgrade authority, mint authority, on-chain admin, keeper signer and web-route signer, and the keeper role cannot be split off without a program change

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [reachable-now]
- **Class:** `S10-C1`
- **Evidence:** `deploy.json:5`, `frontend/src/app/api/faucet/route.ts:85-100`, `keepers/.env.example:11`, `docker-compose.yml:27-29`, `programs/slipstream/src/instructions/record_pending_fill.rs:61`, `keepers/src/fill-log-keeper.ts:73`, `Anchor.toml:15`, `PRODUCT.md:64`

**What is wrong.** `PRODUCT.md:64` records the concentration as an open question and names three
roles ("program upgrade authority, USDC mint authority, and faucet signer in one"). The live chain
says it is **five**, and the two the doc omits are the ones that make the split hard. `A5sV4Pkk…`
is additionally `GlobalState.authority` — the signer gate on twelve instructions — and
`GlobalState.treasury`. Critically, `record_pending_fill.rs:61`, `initialize_fill_log.rs:60` and
`delegate_fill_log.rs:98` all require `global.authority == authority.key()`, and the settlement
keeper signs exactly those with a single loaded keypair (`keepers/src/fill-log-keeper.ts:73`).
So the admin key is *structurally required* to be a hot key sitting on the keeper VM, mounted into
six containers (`docker-compose.yml:27-29`), and the same key is also read out of an environment
variable by a public HTTPS route (`frontend/src/app/api/faucet/route.ts:85-100`). The written
invariant this violates is `PRODUCT.md:35-38`: "a misbehaving rollup can at worst scramble order
*ordering* or misuse an already-capped credit allowance. It can never reach the vault." That bound
holds against the *rollup*; it does not hold against this key, which reaches the vault directly by
replacing the program.

Capability enumeration (what a holder of the key can do today):

**Blast radius.** Any single compromise of the Vercel environment, the keeper VM, or the operator
laptop yields all seven at once. On mainnet that is total loss of the vault plus unbounded
collateral inflation, with no timelock and no second signer anywhere in the path. On the current
devnet deployment it is exploitable today — the tokens are worthless, but the *exposure* is live,
not hypothetical, which is why this is tagged `[reachable-now]` rather than `[mainnet-only]`.

**Suggested remediation.** Three of the five separate with **no code change**: move the mint
authority to a faucet-only key (`spl-token authorize <mint> mint <new>`), move the BPF upgrade
authority to a Squads multisig (`solana program set-upgrade-authority`), and rotate
`GlobalState.authority` to a cold admin key using the two-step path the program already has
(`propose_authority` / `accept_authority`). The fourth does **not**: because
`record_pending_fill`/`initialize_fill_log`/`delegate_fill_log` are authority-gated, separating the
keeper signer needs a distinct `keeper` role on `GlobalState` — file that as the code prerequisite
rather than assuming the split is free.

### S10-02 · `scripts/deploy.ts`, the stated generator of `deploy.json` and the bootstrap every error message names, has never existed in this repository

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S10-C8`
- **Evidence:** `frontend/scripts/copy-manifest.mjs:1-2`, `frontend/src/lib/manifest.ts:73`, `deploy.json:17-18`, `keepers/src/shared/manifest.ts:101`, `tests/integration/package.json:10-12`

**What is wrong.** `deploy.json` is the stated source of truth for every address the frontend, the
keepers, the SDK and the integration suite use. `frontend/scripts/copy-manifest.mjs:1-2` describes
it as "the Deploy_Manifest emitted by scripts/deploy.ts", and eleven files instruct the reader to
run that script — including the user-visible error string at `frontend/src/lib/manifest.ts:73` and
the setup preconditions of every integration test. The file is not in the working tree, is not
tracked, and was never added in any of the 111 commits in the repository's history. There is
therefore no reproducible procedure that recreates `GlobalState`, `Market`, `OrderBook`, the vault
or the mint, and nothing that re-derives or validates the twelve addresses in `deploy.json` — it is
a hand-maintained JSON file. `deploy.json:17-18` records a `deployedAt` timestamp and a
`lastUpgradeSignature`, but no program build hash, so the deployed bytes are not tied to this source
either.

**Blast radius.** The operator. Disaster recovery, a mainnet deploy, and any second environment are
all blocked on a script that does not exist; whoever performs the next deploy must reconstruct the
bootstrap sequence (initialize_global → initialize_market → initialize_fill_log → the two-phase

`programDataHash` recorded at deploy time so the deployed bytes remain checkable). Route the eleven
doc/message strings to whichever fix run lands the script; the doc half is routed below as S10-X02.

### S10-03 · The keeper image's default command starts the settlement keeper the project's own docs call impossible, and omits the one that works

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S10-C10`
- **Evidence:** `keepers/package.json:14`, `docker-compose.yml:18-115`, `keepers/ecosystem.config.js:43-47`, `docs/04-settlement-and-the-fill-log.md:20`, `docs/03-ephemeral-rollups-and-delegation.md:88`, `keepers/src/settlement-keeper.ts:107`

**What is wrong.** Three launch surfaces disagree about which settlement keeper runs, and the
Dockerfile's default (`CMD ["npm","run","all"]`, keepers/Dockerfile line 55) picks the wrong one.
`keepers/package.json:14` defines `all` as `settlement + funding + liquidation + twap + expiry` —
it starts `settlement-keeper.ts` and does **not** start `fill-log-keeper.ts`.
`keepers/src/settlement-keeper.ts:107` settles by scheduling `commit_orderbook` on the ER, and
`docs/04-settlement-and-the-fill-log.md:20` states the invariant flatly: "**The OrderBook can never
be committed/undelegated** (612 KB ≫ the 10,240-byte …)", repeated at
`docs/03-ephemeral-rollups-and-delegation.md:88` as "for the 612 KB OrderBook this is
**impossible**". The keeper that actually works is `fill-log-keeper.ts`, which both real deployment
surfaces do launch (`docker-compose.yml:18-23`, `keepers/ecosystem.config.js:43`) — and neither of
those launches `settlement` at all. Nothing surfaced this because the compose file overrides
`command:` on all six services, so the image's `CMD` never executes there, and the live box runs
pm2.

**Proof.**

```

$ grep -nE "^  [a-z-]+:$" docker-compose.yml        # compose services

```

Set difference: `npm run all` ∖ {compose ∪ pm2} = {`settlement`}; {compose ∪ pm2} ∖ `npm run all` =
{`fill-log`, `market-maker`, `taker`}. No launch surface starts the union.

**Blast radius.** An operator who follows `keepers/Dockerfile` line 6 (`docker build … && docker
run`) or `keepers/README.md:62` gets five keepers whose settlement path is documented-impossible:
ER fills never become L1 `Position` accounts, so positions, PnL, funding and liquidation all stop
advancing while the order book keeps matching. The failure is silent — `settlement-keeper.ts:109`
logs `commit_orderbook failed on ER` and continues. This is not the cause of K1 (the live box runs
pm2, which does start `fill-log`), but it is reachable today by anyone who stands the stack up the
documented Docker way.

**Suggested remediation.** Make `all` the union of the keepers the two real deployments run
(`fill-log-keeper` in, `settlement` out or renamed `settlement-legacy`), and give
`docker-compose.yml` and `ecosystem.config.js` one shared definition of the keeper set instead of
three hand-maintained lists.

### S10-04 · `.dockerignore` excludes the two keeper secret directories it knew about and misses the third, so funded devnet keys can be baked into the image

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** `S10-C2`
- **Evidence:** `keepers/.gitignore:6-7`, `keepers/src/verify-session.ts:77-83`, `keepers/src/verify-close.ts:29-33`, `keepers/src/shared/bot-wallets.ts:67`, `docker-compose.yml:5`

**What is wrong.** `.dockerignore` line 1 states the invariant ("Keep the keeper image lean and
never ship secrets") and lines 17–23 carry a careful comment explaining that a plain
`COPY keepers ./keepers` would otherwise "bake whatever happens to exist on the build host straight
into the image layer" — then excludes `keepers/.bot-keys` and `keepers/data` only. The third
directory of the same kind, `keepers/.verify-keys/`, is not excluded by any pattern in the file.
`keepers/src/verify-session.ts:83` and `keepers/src/verify-close.ts:33` write raw 64-byte
`secretKey` JSON arrays there, and `verify-close.ts:36-42` funds those wallets with SOL transferred
from the operator key. `keepers/.gitignore:6-7` treats them exactly like `.bot-keys` ("Never
commit"); the Docker exclusion list simply did not get the same line. Nothing surfaced it because
the directory only exists on a host where `verify-session`/`verify-close` have been run, which is
the operator's own machine — the most likely build host.

**Proof.** Reproduction at `docs/audit/audit-e2e/repro/s10/dockerignore_secret_dirs.py` implements
Docker's documented `.dockerignore` matching (last-matching-pattern-wins, ancestor match excludes a
subtree, `**` spans segments) and asserts each secret path against what the file's own comments
claim:

```

keepers/.verify-keys/verify-user.json       False      <none>

FAIL keepers/.verify-keys/verify-user.json: expected excluded=True, got False
     claim: .dockerignore:1 'never ship secrets' - but NO pattern in the file matches it

1 of 6 secret paths are NOT excluded from the build context.

```

(The Docker daemon is not running in this environment, so the assertion is against the pattern
semantics rather than a produced image layer; the `COPY keepers ./keepers` line is keepers/Dockerfile
line 29 and Docker's `COPY <dir>` includes dot-directories.)

**Blast radius.** An image built on a host where the live-verification scripts have run carries
funded devnet keypairs in a readable layer. Today those are throwaway wallets holding ~0.03 SOL and
a devnet trading credit, so the loss is bounded; the exposure is unbounded the moment the image is
pushed to any registry, and the same code path on a mainnet deployment would ship real keys. Note
also that `*.log` and `*.so` on lines 15–16 match root-level files only (Docker patterns do not
cross `/` on a bare `*`), unlike the `**/`-prefixed entries above them.

**Suggested remediation.** Add `keepers/.verify-keys` beside `keepers/.bot-keys`, and prefer a
deny-by-default context (`*` then `!`-list the four paths the image actually needs:
`keepers/src`, `keepers/package*.json`, `client/`, `deploy.json`) so the next secret directory is
excluded without anyone having to remember.

### S10-05 · The production keeper image installs with `npm install`, so it runs a dependency tree no gate has validated — the exact thing the CI file's own comment forbids

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** `S10-C8`
- **Evidence:** `.github/workflows/ci.yml:111-118`, `frontend/vercel.json:4`, `keepers/package-lock.json:1`, `client/package-lock.json:1`, `frontend/package-lock.json:14`

**What is wrong.** `.github/workflows/ci.yml:111-118` installs the keeper and client trees with
`npm ci` and states why in a comment: "`npm ci` (not `npm install`) so this actually honors the
committed client/package-lock.json instead of silently allowing it to drift." `keepers/Dockerfile`
lines 23–26 copy both lockfiles into the image and then install with `npm install` on both — the
one form the comment rules out. `npm install` is free to re-resolve and to rewrite the lock, and it
prunes root dependencies that `package.json` does not declare, so the image's tree is not the tree
CI type-checks. The divergence is not theoretical: `frontend/package-lock.json:14` declares
`@radix-ui/react-radio-group@^1.3.8` as a root dependency that `frontend/package.json` does not
list, so `npm ci` installs a 19-package subtree that `npm install` removes. A second instance of
the same class: `frontend/scripts/gen-assets.mjs:4` imports `sharp`, which appears in the lockfile
only as an **optional** transitive dependency of `next` and is declared nowhere in
`frontend/package.json`.

**Blast radius.** The processes that hold the operator signing key run a dependency set that no CI

`gen-assets.mjs` fails with `ERR_MODULE_NOT_FOUND` on any checkout where Next's optional `sharp`

cannot be re-run from a clean tree.

`*` from the `COPY … package-lock.json*` globs so an absent lockfile fails the build instead of
silently degrading), remove `@radix-ui/react-radio-group` from the frontend lock root or add it to
`package.json`, and declare `sharp` as a `devDependency`.

### S10-06 · The one direct dependency worth gating — `next` — is 26 highs behind with a non-major fix, and no gate in the repository would ever say so

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** `S10-C6`
- **Evidence:** `frontend/package.json:30`, `frontend/package.json:42`, `.github/workflows/ci.yml:47-56`, `frontend/vercel.json:2-4`

**What is wrong.** `.github/workflows/ci.yml:47-52` documents the deliberate omission of
`npm audit`, and the reason it gives is true of the trees as a whole: "deep, wallet-adapter heavy,
dozens of pre-existing advisories that would need a dedicated remediation pass before an audit gate
could ever be green there." K6 records that omission as accepted. The residual gap is that the
reason argues against a *green-or-fail gate over everything* and was then applied as *no bound at
all*: the deployed public frontend pins `next` at `16.2.4` (`frontend/package.json:30`,
`eslint-config-next` matched at line 42) against 22 advisories, and npm reports the fix as
`16.3.2`, `isSemVerMajor: false`. `cargo audit` (`ci.yml:53-56`) covers only the Rust tree, which is
clean.

**Proof.** Advisory counts, run here because CI does not (`npm audit --package-lock-only`, 2026-08-21):

Reachability triage, as the slice requires (report reachable only):

- **Reachable.** `next` App-Router advisories that need no middleware and no Server Actions —
  Server-Component DoS, RSC response cache poisoning, unauthenticated disclosure of internal Server
  Function endpoints. Five API routes are exposed under `frontend/src/app/api/`.
- **Not reachable.** The `next` Middleware/Proxy-bypass family (no `middleware.ts` exists anywhere in
  the repo), the Image-Optimization and `sharp`/libvips advisories (`grep -rn "next/image"
  frontend/src` returns nothing), and the SSRF-in-rewrites advisory (`frontend/next.config.ts:3-5`
  declares no rewrites).
- **Not reachable, dev/optional only.** The `critical` `shell-quote` in `frontend` is
  `optional: true` under `react-devtools-core`; in `keepers` it is `dev: true` under
  `concurrently`, whose arguments come from `keepers/package.json` and are not attacker-controlled.
  `mermaid`/`dompurify` render repo-authored markdown only.
- **Reachable but low-value.** `bigint-buffer` and `ws` reach the keepers and the browser through
  `@solana/spl-token` and `@solana/web3.js`; both require a hostile RPC endpoint, which is already a
  trusted input in this architecture.

**Blast radius.** Public visitors to the deployed frontend, for the cache-poisoning and
Server-Function-disclosure classes. No key material is at risk. The real cost is that the gap is
invisible: nothing in the repository would tell the operator the number had moved, so the
distance from a shipped version to a patched one grows monotonically.

**Suggested remediation.** Do not add a green-or-fail `npm audit`; add a bound the stated reason
still permits — pin `next` forward to `16.3.2` and run `npm audit --audit-level=high --production`
on `frontend/` and `keepers/` as a *non-blocking* reporting step, or an allowlist-based
`audit-ci` with the current advisory set recorded as the baseline.
