### S12-04 · `docs/06` says the session key is kept in memory; the shipped app persists the raw secret in `localStorage`

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S12-C1 — Claim verification
- **Evidence:** `docs/06-session-keys.md:108-115`, `docs/06-session-keys.md:91-104`, `frontend/src/hooks/use-session.ts:130`, `frontend/src/hooks/use-session.ts:158-173`, `frontend/src/hooks/use-session.ts:622`

**What is wrong.** `docs/06-session-keys.md:110-111` states: "The browser generates the
session keypair, prompts the wallet **once** to sign `authorize_session`, then keeps the
session key **in memory** to auto-sign ER orders." The shipped hook writes the 64-byte

executes on the origin. `docs/06-session-keys.md:91-104` then builds a "what a leaked
session key can and can't do" table on the in-memory premise. The table's rows are each
still correct — the program's scoping is real — but the doc never states *how* such a key
would leak, because it never admits the key is at rest on disk.

function sessionStorageKey(owner: PublicKey, marketIndex: number): string {

function loadStoredSession(
  owner: PublicKey,
  marketIndex: number
): { keypair: Keypair; expiry: number } | null {
  if (typeof window === "undefined") return null;

}
