# S6 — SDK layout parity: TS decoders vs the Rust `#[repr(C)]` layouts

**Run:** `audit-e2e` · **Slice:** S6 · **Issue:** #8 · **Freeze:** `b98f0508b01af619f84a6cbb82b6326ebbcd7f9f`

Scope filed against: `client/src/{index,constants,pda,accounts,instructions}.ts` and
`frontend/src/lib/slipstream/{index,constants,pda,accounts,instructions,orderbook}.ts`.
Everything else was read, and defects found elsewhere are routed, not filed.

**Method.** Two reproductions, both under `docs/audit/audit-e2e/repro/s6/`:

1. `layout/` — a throwaway Rust binary that depends on the real `slipstream` crate and
   prints `size_of` / `align_of` / `offset_of!` for every field of all twelve
   `#[repr(C)]` structs, plus the seed literals, the account discriminators and the
   derived account sizes. Output committed as `repro/s6/rust-layout.json`. Nothing is
   hand-derived; the offsets come from the compiler.
2. `check-parity.mjs` — a zero-dependency Node script that reads that JSON and both
   vendored TS copies, and asserts, per copy: every decoder read offset against the
   Rust offset, every `*_SIZE` constant against `size_of`, every `DISC_*` and `SEED_*`
   against `state/mod.rs`, every `IX_*` against `instructions/mod.rs`, every builder's
   fixed account count and signer positions against the Rust handler's positional
   destructuring, and the two copies against each other.

A third, `live-decode.mjs`, is a read-only devnet check (no signer, two
`getAccountInfo` calls) that decodes the live Market account at the exact offsets the
TS decoders use, so the tables are validated against real on-chain bytes and not only
against Rust source.

**Headline result.** There is **no byte-offset drift**. All 69 builder checks, all 24
size constants, all 18 discriminator sets and all 23 decoders pass in both copies. The
defects that exist are on the other side of the contract: a field the Rust program
keeps *inside* a `_padding` array that neither decoder reads, a dead oracle address
both copies still export, and three instructions the SDK has no vocabulary for.

## Calibration

> Flag only gaps that affect correctness, the stated requirements, or documented project invariants -- cite file:line evidence for every finding. Do not report stylistic preferences.

## Findings

### S6-01 · `Market.mark_price_minute` is stored inside `_padding1` and neither vendored decoder reads it

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S6-C2 · Padding and alignment
- **Evidence:** `client/src/accounts.ts:88-121`, `client/src/accounts.ts:137-164`, `frontend/src/lib/slipstream/accounts.ts:92-125`, `frontend/src/lib/slipstream/accounts.ts:141-168`, `programs/slipstream/src/state/market.rs:136-161`, `programs/slipstream/src/state/market.rs:173-183`

**What is wrong.** `Market._padding1: [u8; 2]` at offset 14 is not padding. It carries
the mark-price freshness stamp `(unix_ts / 60) mod 2^16`, written by
`set_mark_price_minute` and read by `is_mark_price_fresh`, and that predicate is what
`mark_price_for_close` uses to decide between `Some(last_mark_price)` and `None ->
OracleStale`. The program's own comment states the invariant: the stamp exists "so
closes never break in the window between the program upgrade and the next crank", i.e.
`last_mark_price` is only usable while the stamp is within
`MARK_PRICE_MAX_STALENESS_MINS`. Both vendored decoders decode `lastMarkPrice` at
offset 200 and skip offset 14 entirely, so every SDK consumer gets the price without
the one field that says whether the protocol will honour it. The authors clearly knew
about this aliasing pattern — the sibling alias `last_settled_sequence`, which lives in
the *trailing* `_padding2` at 2058, **is** decoded and carries an explanatory comment
at `client/src/accounts.ts:112-114`. One of the two padding-embedded fields was
carried across; the other was not, and nothing errors either way.

**Proof.** Live devnet read, no signer, `docs/audit/audit-e2e/repro/s6/live-decode.mjs`
plus the freshness computation below (market `ECUp8pXzVLzxjVs8mtKBJma3mdcHf8zSC4cqPeBy8MPy`,
program-owned, 2064 bytes):

```
fetched-at             2026-08-21T19:22:09.477Z
Market._padding1 @14  bytes = [ 148, 48 ]
mark_price_minute()   = 12436 (u16 LE inside _padding1, market.rs:142-150)
now_min               = 35658
now_min - stamp       = 23222 minutes  = 16.1 days
MARK_PRICE_MAX_STALENESS_MINS = 30
is_mark_price_fresh() = false
=> mark_price_for_close() returns None -> OracleStale
last_mark_price @200  = 74114120 = $74.11412
Market._padding2 @2058 bytes = [ 141, 172, 0, 0, 0, 0 ]
```

The generated parity table confirms the asymmetry mechanically — `_padding2` has a TS
reader, `_padding1` does not:

```
   _padding1                    rust @  14 +   2   ts (not decoded)
   ...
   _padding2                    rust @2058 +   6   ts @2058 +  4  lastSettledSequence
```

**Blast radius.** Every consumer of the SDK's `Market` type on the live deployment.
`close_position` and `execute_trigger` revert with `OracleStale` right now, and the
decoded `lastMarkPrice` of `$74.11` is 16 days old while the market's own configured
feed reads fresh — but no SDK caller can compute that, because the predicate's input is
not in the decoded struct. The frontend has already paid for this: rather than reading
the stamp, `frontend/src/components/trading/status-panel.tsx:67-76` and
`frontend/src/components/trading/market-bar.tsx:59-63` reimplement freshness as
"divergence between the on-chain mark and the live Pyth stream", a heuristic that is
wrong in both directions — it reports "fresh" for a dead crank in a flat market (the
divergence stays small) and "stale" for a healthy crank during a fast move. A user
sizing a position against a mark the protocol will not settle at, and then finding the
close reverts, is the money consequence. On mainnet this is the difference between a
UI that says "prices are stale, closes are disabled" and one that silently takes the
order. Routed observation: S6-X02.

**Suggested remediation.** In both copies, add `markPriceMinute: readU16LE(data, 14)`
to `decodeMarket` and the `Market` interface, export
`MARK_PRICE_MAX_STALENESS_MINS = 30` from `constants.ts`, and add
`isMarkPriceFresh(market, nowSecs)` implementing the same modular-minute comparison as
`programs/slipstream/src/state/market.rs:154-161` (`stamp === 0` means unstamped and is
treated as fresh). Do not implement it here — the audit is read-only.

### S6-02 · Both copies export `PYTH_SOL_USD_DEVNET` pointing at a legacy feed frozen for 721 days that the market is not pinned to

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S6-C9 · Coverage gaps
- **Evidence:** `client/src/constants.ts:23-25`, `frontend/src/lib/slipstream/constants.ts:37-39`

**What is wrong.** Both vendored copies export a single named oracle constant,
`PYTH_SOL_USD_DEVNET = J83w4HKfqxwcq3BEMMkPFSppX3gqekLyLJBexebFVkix`. That account is
the legacy Pyth V2 aggregate; it stopped publishing on 2024-08-29 and still reads
$139.82. The market this SDK serves is pinned to a different account entirely —
`7UVimffxr9ow1uXYxsr4LHAcV58mLzhmwaeKvJ1pjLiE`, a 134-byte Receiver `PriceUpdateV2`
owned by `rec5EKMG…`. The invariant the constant violates is its own name plus the
vendored-copy header at `frontend/src/lib/slipstream/constants.ts:1-8`, which declares
this file "the CANONICAL, tested layout/decoder source of truth" and instructs callers
not to hand-roll values elsewhere. The mechanism that hid it: every in-tree caller was
individually warned off the constant in a comment rather than the constant being fixed
or deleted — see `keepers/src/twap-keeper.ts:14`, `keepers/src/funding-keeper.ts:20`,
`keepers/src/liquidation-keeper.ts:152` and `keepers/src/shared/manifest.ts:223`, each
of which names `PYTH_SOL_USD_DEVNET` explicitly as the thing to avoid.

**Proof.** Read-only devnet, `docs/audit/audit-e2e/repro/s6/live-decode.mjs`:

```
--- SDK constant vs the feed the market is pinned to ---
  PYTH_SOL_USD_DEVNET (client/src/constants.ts:23, frontend .../constants.ts:37)
    J83w4HKfqxwcq3BEMMkPFSppX3gqekLyLJBexebFVkix
  market.pyth_feed @80  7UVimffxr9ow1uXYxsr4LHAcV58mLzhmwaeKvJ1pjLiE
  MATCH? false
  legacy feed account: owner=gSbePebfvPy7tRqimPoVecS2UsBvYv46ynrzWocc92s len=3312
    price=13981741499 expo=-8 -> $139.81741499
    publish_ts=1724967841  2024-08-29T21:44:01.000Z   (age 721 days)
  market's own feed:   owner=rec5EKMGg6MxZYaMdyBfgwp4d5rB9T1VQH5pJv5LtFJ len=134
```

**Blast radius.** No in-tree caller uses it today, which is why this is P2 and not P1 —
the four keeper files above each dodge it by hand. The exposure is the next consumer.
The SDK offers exactly one SOL/USD feed address and it is dead: a caller who writes
`createCrankTwapInstruction(0, PYTH_SOL_USD_DEVNET)` gets a transaction that reverts at
`programs/slipstream/src/oracle.rs:68-70` with `InvalidOracle` (the on-chain identity
pin is what keeps this from being a money bug), and a caller who reads it for display
shows $139.82 for SOL. On mainnet the same shape — a hardcoded oracle address in the
canonical SDK that has silently drifted from the one the market is pinned to — is how a
UI ends up quoting a price the protocol has never heard of.

**Suggested remediation.** Delete `PYTH_SOL_USD_DEVNET` from both copies and make the
feed come from `Market.pyth_feed` (already decoded at offset 80) or from the deploy
manifest, the way the keepers already do; if a literal must stay, rename it to record
that it is the retired V2 aggregate.

### S6-03 · Three on-chain instructions have neither a discriminator constant nor a builder in either copy, and the only in-repo caller hand-rolls both the discriminator and raw Market byte offsets

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S6-C9 · Coverage gaps
- **Evidence:** `client/src/constants.ts:92-94`, `frontend/src/lib/slipstream/constants.ts:97-99`, `client/src/instructions.ts:1306-1333`, `programs/slipstream/src/instructions/mod.rs:95-101`

**What is wrong.** `instructions/mod.rs` declares 40 instruction discriminators,
`0x00`–`0x27`. Both TS copies stop at `IX_EXECUTE_TRIGGER = 0x24`. Missing from
*both*: `IX_SET_MARKET_ORACLE` (`0x25`), `IX_PROPOSE_AUTHORITY` (`0x26`),
`IX_ACCEPT_AUTHORITY` (`0x27`) — no constant, no builder, no caller in either SDK. The
written invariant is the vendored header at
`frontend/src/lib/slipstream/instructions.ts:1-16` — "CANONICAL, tested instruction
builders — the SAME source the keepers and integration tests use … do NOT hand-roll
account lists or data layouts" — and `docs/spec/audit-e2e.md:1-8` is not the claim; the
shipped docs state it, at `frontend/src/content/docs/01-architecture-overview.md:109`
("40 instructions (0x00–0x27)"). The mechanism that hid it: these three landed in
Rounds 7 and 8, after the SDK's last sync, and nothing cross-checks the two lists.

**Proof.** `node docs/audit/audit-e2e/repro/s6/check-parity.mjs` (full output at
`docs/audit/audit-e2e/repro/s6/`):

```
=== IX_* discriminators vs instructions/mod.rs ===
  Rust declares 40 instruction discriminators
  client/src: 37/40 present; MISSING: IX_SET_MARKET_ORACLE=0x25, IX_PROPOSE_AUTHORITY=0x26, IX_ACCEPT_AUTHORITY=0x27
  frontend/src/lib/slipstream: 32/40 present; MISSING: IX_INITIALIZE_FILL_LOG=0x1d, IX_DELEGATE_FILL_LOG=0x1e, IX_MIRROR_FILLS=0x1f, IX_COMMIT_FILL_LOG=0x20, IX_SETTLE_FROM_LOG=0x21, IX_SET_MARKET_ORACLE=0x25, IX_PROPOSE_AUTHORITY=0x26, IX_ACCEPT_AUTHORITY=0x27

=== instruction builder coverage ===
  client/src: 37 builders covering 37/40 instructions
    NO BUILDER: IX_SET_MARKET_ORACLE, IX_PROPOSE_AUTHORITY, IX_ACCEPT_AUTHORITY
```

The consequence is already in the tree, not hypothetical. `keepers/src/set-market-oracle.ts`
re-declares the discriminator and, because the SDK has no builder, re-derives Market
byte offsets by hand:

```
18: const IX_SET_MARKET_ORACLE = 0x25;
19:
20: // Market field offsets (repr(C), see programs/slipstream/src/state/market.rs).
21: const OFF_PYTH_FEED = 80;
22: const OFF_SWITCHBOARD_FEED = 2024;
```

Both values happen to be correct today (verified against `rust-layout.json`), which is
exactly why this is latent rather than broken.

**Blast radius.** Two separate exposures. (a) `set_market_oracle` is the only writer of
`Market.pyth_feed` after `initialize_market`, and its sole client is a one-shot script
carrying a private copy of two offsets from a struct that has already been appended to
twice ("Round 3 additions" at `programs/slipstream/src/state/market.rs:46-54`); the next
append that shifts the tail updates the SDK decoders and silently does not update the
script, and the operator points the market at a garbage 32-byte window. (b)
`propose_authority` / `accept_authority` are the two-step rotation of
`GlobalState.authority` — the on-chain half of the documented mitigation for the
operator-key concentration in §6 K2. There is no client path to them anywhere in the
repo, so on mainnet the emergency "move authority off the compromised key" lever would
have to be hand-assembled from raw bytes under time pressure.

**Suggested remediation.** Add the three `IX_*` constants and
`createSetMarketOracleInstruction` / `createProposeAuthorityInstruction` /
`createAcceptAuthorityInstruction` to `client/src`, re-vendor into
`frontend/src/lib/slipstream`, and have `keepers/src/set-market-oracle.ts` import the
builder and `decodeMarket` instead of its own constants. Longer term, run something
like `repro/s6/check-parity.mjs` in CI so the two lists cannot drift again.

### S6-04 · Copy-to-copy divergence, enumerated — including the direction K7 does not record: the declared source of truth is missing `SENTINEL`

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S6-C8 · Divergence between the two copies
- **Evidence:** `client/src/index.ts:1-4`, `client/src/constants.ts:115-126`, `frontend/src/lib/slipstream/index.ts:7-11`, `frontend/src/lib/slipstream/constants.ts:64`, `frontend/src/lib/slipstream/constants.ts:116-118`, `frontend/src/lib/slipstream/orderbook.ts:9`, `client/src/pda.ts:114-131`

**What is wrong.** §6 K7 records the divergence as one-directional — the frontend copy
lacks the FillLog surface and adds `orderbook.ts`. That is confirmed and is not
re-reported here. What is **not** on the record is that the divergence runs the other
way too: `client/src/constants.ts`, the file both frontend headers name as the
canonical source, does **not** declare `SENTINEL`. The frontend copy added
`SENTINEL = 0xffff` at `frontend/src/lib/slipstream/constants.ts:116-118` because
`orderbook.ts` needs the linked-list terminator to walk a price level's FIFO. Anything
built on `client/src` — the keepers, the integration tests, any future consumer — must
hard-code `0xffff` to do the same walk, which is precisely the hand-rolled-constant
pattern the vendored headers forbid. `SENTINEL: u16 = u16::MAX` is declared at
`programs/slipstream/src/state/mod.rs:58` and is load-bearing in matching
(`programs/slipstream/src/state/order_slot.rs:68-69`). Two smaller deltas, with a
verdict each, are listed under Blast radius.

**Proof.** `node docs/audit/audit-e2e/repro/s6/check-parity.mjs`:

```
=== client/src : *_SIZE constants vs core::mem::size_of ===
  ...
  ABSENT   SENTINEL - not declared in this copy

=== frontend/src/lib/slipstream : *_SIZE constants vs core::mem::size_of ===
  ...
  ABSENT   FILL_LOG_HEADER_SIZE - not declared in this copy
  ABSENT   FILL_LOG_CAPACITY - not declared in this copy
  ok       SENTINEL                 65535

=== frontend/src/lib/slipstream : DISC_* / SEED_* vs state/mod.rs ===
  ok       9/9 account discriminators match
  ABSENT   SEED_FILL_LOG - not declared in this copy

=== copy A vs copy B (byte-level decoder parity) ===
  ONLY IN client/src: FillLogHeader
  11/12 shared decoders are offset-identical across the two copies
```

**Blast radius.** Every semantic difference between the copies, with which copy is
right: (1) **`SENTINEL`** — the *frontend* copy is right; `client/src` should gain it,
since it is the declared source of truth and the value is a program constant, not a UI
concern. (2) **FillLog surface** (`SEED_FILL_LOG`, five `IX_*`, `findFillLogPda`,
`decodeFillLogHeader`, `decodeFillLogFills`, `FILL_LOG_HEADER_SIZE`,
`FILL_LOG_CAPACITY`, five builders) — the *client* copy is right, but the frontend does
not use the FillLog at all, so the omission is inert today; note that
`frontend/src/lib/slipstream/constants.ts:64` still exports `DISC_FILL_LOG = 8` with no
decoder to use it, a dangling half-import. (3) **`orderbook.ts`** — frontend-only
aggregation helpers built on the shared decoders; correct where it lives. Where it
matters — the twelve struct layouts — the copies are byte-identical, so no wrong number
follows from the split today. The risk is the next edit landing in one copy only.

**Suggested remediation.** Move `SENTINEL` into `client/src/constants.ts` and re-vendor;
either add the FillLog surface to the frontend copy or drop the orphaned
`DISC_FILL_LOG`; and make the vendoring a generated copy (a script, checked in CI) so
"keep in sync" stops being a comment.

### S6-05 · Batched P3 — decoder and constant coverage gaps that do not produce a wrong number today

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S6-C9 · Coverage gaps
- **Evidence:** `client/src/accounts.ts:160-163`, `frontend/src/lib/slipstream/accounts.ts:164-167`, `programs/slipstream/src/state/market.rs:50-54`, `client/src/accounts.ts:340-353`

**What is wrong.** Three small omissions, none of which mis-decodes anything.
(a) `Market.agreement_streak` at offset 2057 is decoded by neither copy, while its
neighbour `restricted_mode` at 2056 is. The streak is the hysteresis counter that
governs the exit from restricted (closes-only) mode after three consecutive
agreement readings, so a UI can say "closes only" but never "1 of 3 readings agreed".
(b) Neither copy exposes `DEFAULT_MAX_ORDER_SLOTS` / `DEFAULT_MAX_PRICE_LEVELS` /
`DEFAULT_MAX_FILL_EVENTS` / `DEFAULT_ORDERS_PER_USER`; `createInitializeMarketInstruction`
passes `?? 0` and relies on the on-chain zero-means-default branch at
`programs/slipstream/src/instructions/initialize_market.rs:81-83`. That is correct, but
a caller cannot compute the resulting account size without knowing values the SDK does
not publish, even though `computeOrderBookAccountSize` is right there. (c) There is no
TS mirror of `fill_log_account_size`, the FillLog analogue of
`computeOrderBookAccountSize`.

**Proof.** From the generated coverage report and the live read:

```
  ok       Market             size=2064  align=8  26 decoded fields
  GAP      Market: Rust fields never decoded: agreement_streak
```

```
  @2056 restricted    0
  @2057 agreement_str 0   <- decoded by NEITHER TS copy
```

Zero-means-default is confirmed rather than assumed —
`programs/slipstream/src/instructions/initialize_market.rs:81-83` substitutes the
`DEFAULT_*` values when the parsed `u16` is 0, so the builder's `?? 0` is right.

**Blast radius.** No wrong number and no broken path today. (a) costs the UI a
diagnostic during an oracle-disagreement episode, which is exactly when a trader most
needs to know when trading resumes. (b) and (c) push size arithmetic onto callers, the
same pattern that produced S6-03's hand-rolled offsets. All three are hygiene: they
block verification and invite re-derivation, they do not corrupt data.

**Suggested remediation.** Add `agreementStreak: readU8(data, 2057)` to `decodeMarket`
in both copies (guarded on `data.length >= 2058`, matching the existing Round-3 tail
guards), export the four `DEFAULT_*` capacities from `constants.ts`, and add
`computeFillLogAccountSize(capacity)` next to `computeOrderBookAccountSize`.

## Cross-slice notes

### S6-X01 · `FillLogHeader::LEN` doc comment states 32 and 8352 bytes; the compiler says 24 and 8344

- **Routed to:** S4
- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S4-C5 · Capacity and backpressure
- **Evidence:** `programs/slipstream/src/state/fill_log.rs:8-14`

**What is wrong.** The comment that justifies `FILL_LOG_CAPACITY = 80` computes the
account size as "`FillLogHeader::LEN (32) + 80 * FillEvent::LEN (104) = 8352 bytes`".
`size_of::<FillLogHeader>()` is 24, not 32, so `fill_log_account_size(80)` is 8344. The
code is right and the conclusion (well under the 10,240-byte per-CPI growth cap) still
holds with an extra 8 bytes of headroom; only the reasoning written down is wrong. The
TS side is unaffected: `FILL_LOG_HEADER_SIZE = 24` at `client/src/constants.ts:125`
matches the compiler, not the comment. Filed here because the value that would be
copied out of a stale comment is a capacity bound.

**Proof.** From `docs/audit/audit-e2e/repro/s6/rust-layout.json`, produced by the
compiler via `offset_of!` / `size_of`:

```
  "FillLogHeader": { "size": 24, "align": 8, ... }
  "_derived": { "FILL_LOG_CAPACITY": 80, "fill_log_account_size(FILL_LOG_CAPACITY)": 8344 }
```

**Blast radius.** Nobody today: no code reads the comment. The risk is a future capacity
change reasoned from 8352 and a 32-byte header, which would put the recomputed ring one
entry closer to the CPI cap than the author intended.

**Suggested remediation.** Correct the two numbers in the comment to 24 and 8344.

### S6-X02 · The UI reimplements mark-price freshness as an oracle-divergence heuristic instead of reading the on-chain stamp

- **Routed to:** S13
- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S13-C2 · Stale and error states
- **Evidence:** `frontend/src/components/trading/status-panel.tsx:67-76`, `frontend/src/components/trading/market-bar.tsx:59-63`

**What is wrong.** Both components derive "is the mark stale" from
`|mark - livePythPrice| / livePythPrice` crossing a threshold, with the comment "A dead
crank drifts within a couple of ticks". The program does not use divergence: it uses the
minute stamp in `Market._padding1` against a 30-minute window
(`programs/slipstream/src/state/market.rs:154-161`). The heuristic disagrees with the
protocol in both directions — small divergence with a dead crank reads as fresh, large
divergence with a healthy crank reads as stale. This is the downstream consequence of
S6-01 (the SDK does not decode the stamp), so the fix order is S6-01 first.

**Proof.** Live devnet, same read as S6-01: the stamp is 23,222 minutes old against a
30-minute window, so the protocol classifies the mark as stale and refuses closes —
while the divergence the UI measures depends entirely on where SOL happens to be
trading relative to the frozen `$74.11`.

```
mark_price_minute()   = 12436      now_min = 35658      delta = 23222 min (16.1 days)
is_mark_price_fresh() = false   ->  mark_price_for_close() = None -> OracleStale
```

**Blast radius.** A trader who reads "Mark freshness: ok" and then has their
close-at-market revert, or who sizes against a mark the protocol will not settle at.

**Suggested remediation.** Once the SDK exposes `markPriceMinute` / `isMarkPriceFresh`
(S6-01), replace the divergence heuristic with the exact predicate and keep divergence
only as a secondary display.

## Cleared

Negative results. Each class was checked mechanically where it could be; the command
and its full output are in `docs/audit/audit-e2e/repro/s6/`.

- **S6-C1** Byte-offset drift — **clean**. Every read offset in all 23 decoders across both copies matches `offset_of!` from the compiler; 0 mismatches. `client/src/accounts.ts:69-583`, table below.
- **S6-C2** Padding and alignment — **one finding, S6-01**. All eight explicit `_pad*` fields are correctly skipped; `Market._padding2` is correctly read as `lastSettledSequence`; `Market._padding1` is the gap. `programs/slipstream/src/state/market.rs:30`, `client/src/accounts.ts:161`.
- **S6-C3** Endianness and signedness — **clean**. Every reader is an explicit `*LE` form; `i64` fields use `readBigInt64LE` and `u64` fields `readBigUInt64LE`, matching Rust signedness field-for-field. The split-`i128` helper reads lo unsigned and hi signed and recombines with `(hi << 64n) | lo`, which reproduces `((hi as i128) << 64) | (lo as u64 as i128)` including negative values under JS BigInt two's-complement semantics. `client/src/accounts.ts:37-56`, `frontend/src/lib/slipstream/accounts.ts:41-60`, `programs/slipstream/src/state/market.rs:60-68`.
- **S6-C4** Struct size constants — **clean**.
