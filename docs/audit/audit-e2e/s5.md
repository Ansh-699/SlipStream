# S5 — Oracle and the ER trust boundary

**Run:** `audit-e2e` · **Slice:** S5 · **Issue:** #7 · **Freeze SHA:** `b98f0508b01af619f84a6cbb82b6326ebbcd7f9f`

The sentence under audit is `PRODUCT.md:38`: *"a misbehaving rollup can at worst scramble
order ordering or misuse an already-capped credit allowance. It can never reach the vault
or an undelegated balance."* The first half holds. The second half does not: the delegated
`TradingCredit` carries the field L1 pays out against, and nothing on L1 re-validates it
(**S5-01**).

**Method.** Read the 11 owned files plus every caller and consumer of them; repo-wide greps
for delegation and magic-program CPIs; read-only devnet + ER RPC reads of the live market,
its Pyth feed, its Switchboard feed, the order book, and global state (no signer, no
transaction, no mutation); two scratch reproductions under
`docs/audit/audit-e2e/repro/s5/`. No source, test, config, or doc file was modified.

**Consumed contract.** `S4-C8` (trust in ER-authored data) had not landed when this slice
ran — `docs/audit/audit-e2e/s4.md` does not exist at the freeze. It was re-derived from
`programs/slipstream/src/instructions/settle_from_log.rs` and
`programs/slipstream/src/instructions/mirror_fills.rs`; the re-derivation is published
below and routed back to S4 as `S5-X03`. A disagreement between S4's version and this one
is worth a ruling.

## Producer contracts

#### S5-C1 — the delegation inventory (consumed by S11-C8)

**The set of accounts this program can delegate is exactly `{OrderBook, TradingCredit,
FillLog}`.** An account leaves this program's ownership only through a System `Assign` CPI
whose target owner is the MagicBlock delegation program. There are exactly three such
sites, in three instructions, and each is PDA-pinned to one account type:

| Delegated account | Instruction (owned file) | `Assign` site | Authority gate | Undelegation entry point |
|---|---|---|---|---|
| `OrderBook` (`[b"orderbook", market_index]`) | `delegate_orderbook_prepare` + `delegate_orderbook` | `delegate_orderbook.rs:189-193` | `GlobalState.authority` must sign (`delegate_orderbook.rs:98-110`) | `undelegate_orderbook` (ER-only), `emergency_undelegate` (neither layer — see S5-02) |
| `TradingCredit` (`[b"credit", owner, market_index]`) | `delegate_trading_credit` | `delegate_trading_credit.rs:227-231` | credit `owner` must sign (`delegate_trading_credit.rs:94-96`, `:119-121`) | `undelegate_trading_credit` (ER-only) |
| `FillLog` (`[b"filllog", market_index, epoch]`) | `delegate_fill_log` | `delegate_fill_log.rs:195-199` | `GlobalState.authority` must sign (`delegate_fill_log.rs:97-100`) | none in-program |

**No path delegates `Position`, `UserAccount`, `Market`, `GlobalState`, or the token
vault.** `Market` in particular is never delegated, which is why `crank_twap` and
`apply_dual_oracle` always execute against the L1 `Clock` (see `S5-C7`).

```
$ grep -rn "owner: &DELEGATION_PROGRAM_ID" programs/slipstream/src/
programs/slipstream/src/instructions/delegate_fill_log.rs:197:        owner: &DELEGATION_PROGRAM_ID,
programs/slipstream/src/instructions/delegate_orderbook.rs:191:        owner: &DELEGATION_PROGRAM_ID,
programs/slipstream/src/instructions/delegate_trading_credit.rs:229:        owner: &DELEGATION_PROGRAM_ID,
```

Caveat for S11: `FillLog` has **no** undelegation instruction at all. Rotation to a fresh
epoch (`delegate_fill_log.rs:36-39`, `keepers/src/fill-log-keeper.ts:313-317`) is the only
lifecycle exit, so every retired epoch `FillLog` is abandoned, delegated, rent-funded,
forever. That is a design consequence, not a defect finding, but it belongs in the
inventory.

#### S5-C7 — the mark-price staleness contract (consumed by S3-C13)

S3 owns `mark_price_for_close` and its three callers. This is the oracle-side half only.

1. **What is written.** `crank_twap` writes two things and nothing else that S3 reads:
   `market.last_mark_price = price` and `market.set_mark_price_minute(now_min)`
   (`programs/slipstream/src/instructions/crank_twap.rs:71-76`). `crank_twap` is the only
   writer of both.
2. **What `price` is.** The Pyth reading, normalised to 6 decimals
   (`programs/slipstream/src/oracle.rs:197-209`), after three gates: feed identity
   (`oracle.rs:63-77` via `crank_twap.rs:35-38`), confidence `<= 100 bps`
   (`oracle.rs:152-161`), and publisher freshness `0 <= now - publish_time <= 60`
   (`oracle.rs:49-52` via `crank_twap.rs:44-47`). It is **not** the TWAP.
3. **Which clock.** `Clock::get()` inside `crank_twap` (`crank_twap.rs:44`). Because
   `Market` is never delegated (see `S5-C1`), this instruction can only execute on L1, so
   the stamp is always L1-clock-derived. **An ER-controlled clock cannot reach this
   field.** That is the load-bearing sentence for S3: the ER cannot forge mark-price
   freshness.
4. **Slack in the stamp.** The stamp records the *crank* time, not the *publish* time, so
   it over-states freshness by up to `MAX_STALENESS_SECS` = 60s
   (`programs/slipstream/src/oracle.rs:22`). Against a 30-minute window
   (`programs/slipstream/src/state/market.rs:16`) that is 3.3% slack.
5. **Width and aliasing.** The stamp is `(unix_ts / 60) mod 2^16` stored in
   `Market._padding1`. It can express **45.51 days** (65536 minutes) before it aliases; an
   age of exactly `N * 65536` minutes reads as age 0 and passes. The doc comment at
   `programs/slipstream/src/state/market.rs:153` says "correct for any real age < ~22
   days", which is conservative but not the real bound.
6. **The `stamp == 0` hole.** `is_mark_price_fresh` returns `true` unconditionally when the
   stamp is zero (`programs/slipstream/src/state/market.rs:156-158`), so a market whose
   `last_mark_price > 0` but which has never been cranked since the stamp was introduced
   would settle at an arbitrarily old price. **This is not the state of the live market** —
   verified below.
7. **Live state (read-only, `2026-08-21T19:20:52Z`, slot 486303116).** The gate holds. The
   stamp is set, the mark is 16.12 days old, and `mark_price_for_close` returns `None`:


**Contract summary for S3.** `mark_price_for_close` on the live market returns `None`
today, so K1's frozen `$74.114` cannot be settled against. What S3 must determine is what
each of its three callers does with `None` — that is the reachable-now question, and it is
S3's, not S5's. S5 asserts only that the producer side is sound.

#### S5-C2 — the malicious-ER capability table

What a hostile ER validator can do, and what stops it. "Stops it" means a check that
executes **on L1**, since the ER controls everything inside its own runtime.

| Hostile ER capability | What bounds it on L1 |
|---|---|
| Reorder or censor orders | **Nothing.** Accepted and advertised (`PRODUCT.md:38`). Matching runs entirely in the ER. |
| Commit arbitrary bytes into the `OrderBook` | **Nothing on the book itself.** `settle_trades` re-reads the committed book but validates only the PDA, discriminator, and capacity. The book is non-financial, so this is bounded by what the derived accounting does with it — S4's class. |
| Forge `FillEvent`s in the `FillLog` | **Only sequence monotonicity.** `settle_from_log` validates the FillLog PDA, discriminator, and capacity, then applies `fill.price`, `fill.size`, `fill.maker`, `fill.taker`, `fill.maker_side` verbatim to `Position` and `UserAccount` (`programs/slipstream/src/instructions/settle_from_log.rs:130-145`, `:190-260`). The only filter is `fill.sequence <= last_settled` (`:139`). Routed to S4 as `S5-X03`. |
| Inflate `TradingCredit.credit` beyond what the user funded | **Nothing.** `withdraw_trading_credit` pays the committed value straight into `UserAccount.free_collateral` (`programs/slipstream/src/instructions/withdraw_trading_credit.rs:53-64`). No high-water mark exists. **This is S5-01 — it falsifies the second half of `PRODUCT.md:38`.** |
| Rewrite `TradingCredit.session_authority` / `session_expiry` | **Nothing.** Both live in the delegated account (`programs/slipstream/src/state/trading_credit.rs:38-45`) and neither `authorize_session` nor `delegate_trading_credit` bounds the expiry, so a committed ER-chosen session key is accepted by L1 `place_order`/`cancel_order` indefinitely. Subsumed by S5-01 (an ER that can set `credit` need not bother with the session key). |
| Refuse to undelegate | **Nothing.** Every undelegation entry point is a magic-program CPI that only resolves inside the ER (`S5-02`). The ER refusing to schedule is unappealable from L1. |
| Roll back committed state | **Partially.** `Market.last_settled_sequence` is a monotone L1 cursor, so replaying an older FillLog settles nothing. Credit and book state carry no such cursor. |
| Reach `UserAccount.free_collateral`, `Position`, `Market`, `GlobalState`, or the vault **directly** | **The delegation inventory.** None of them is ever delegated (`S5-C1`), so the ER can never author their bytes. The claim holds *directly*; it fails *transitively* through the credit. |

#### Consumed — `S4-C8` re-derived (S4 had not published)

L1 re-validates, for ER-authored `FillLog` bytes: the FillLog PDA
(`programs/slipstream/src/instructions/settle_from_log.rs:75-80`), the account

## Findings

### S5-01 · A hostile ER can mint `TradingCredit.credit` and L1 pays it out of the vault

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [mainnet-only]
- **Class:** S5-C2
- **Evidence:** `programs/slipstream/src/instructions/delegate_trading_credit.rs:214-231`, `programs/slipstream/src/instructions/withdraw_trading_credit.rs:50-64`, `programs/slipstream/src/instructions/fund_trading_credit.rs:70-74`, `programs/slipstream/src/state/trading_credit.rs:27-46`, `PRODUCT.md:38`

**What is wrong.** `delegate_trading_credit` hands the whole `TradingCredit` account to the
delegation program, and the ER then owns every byte of it — including `credit.credit`, the
number `withdraw_trading_credit` moves into `UserAccount.free_collateral` and from there
out of the vault. The struct records the *current* allowance and nothing else: there is no
`funded` high-water mark, no per-user deposit ledger, no L1-side conservation check
(`programs/slipstream/src/state/trading_credit.rs:27-46`). `withdraw_trading_credit`
validates the owner, that the account is undelegated again, that it is idle, and that
`credit.credit >= amount` — all four of which an ER that authored the bytes satisfies
trivially. The invariant this violates is written down verbatim at `PRODUCT.md:38` ("It can
never reach the vault or an undelegated balance") and restated at `README.md:49`,
`docs/01-architecture-overview.md:56`, and `docs/07-problems-and-solutions.md:148`. The
mechanism that hides it is that `credit.credit` is *never increased anywhere except
`fund_trading_credit` on L1* — so every honest path, every test, and every code review sees
a monotone-down field and stops looking.

**Proof.** Static, by exhaustion: every read and write of the field, pasted. The only
increment is `fund_trading_credit.rs:71` (L1, gated on `user.free_collateral`); the only
consumer is `withdraw_trading_credit.rs:53-58`, which compares against nothing but the
field itself.

```
$ grep -rn "credit\.credit\|credit_mut\.credit" programs/slipstream/src/
programs/slipstream/src/instructions/fund_trading_credit.rs:71:    credit_mut.credit = credit_mut
programs/slipstream/src/instructions/withdraw_trading_credit.rs:53:    if credit.credit < amount {
programs/slipstream/src/instructions/withdraw_trading_credit.rs:58:    credit_mut.credit = credit_mut.credit.saturating_sub(amount);
programs/slipstream/src/instructions/place_order.rs:339:        credit.credit = credit
programs/slipstream/src/state/trading_credit.rs:139:        credit.credit = credit.credit.saturating_sub(drained);
programs/slipstream/src/instructions/initialize_trading_credit.rs:71:    credit.credit = 0;
```

`place_order.rs:339` is `checked_sub`; `trading_credit.rs:139` is `saturating_sub`;
`initialize_trading_credit.rs:71` is a zero-init. So the L1 program never validates an
increase it did not itself perform, and the account it reads is one the ER wrote and
committed. The delegation that creates this authority is
`delegate_trading_credit.rs:227-231`.

**Blast radius.** Every depositor in the market, up to the entire USDC vault balance. The
precondition is control of the ER validator that holds the delegation — on mainnet, a
third-party sequencer with no fraud proof (`README.md:241` lists "Fraud proofs | None").
The victim set is not limited to the attacker's own credits: one inflated credit drains the
shared vault, so honest users' `withdraw_collateral` fails afterwards. Tagged
`[mainnet-only]` because both devnet-inertness conditions in the spec hold — the tokens are
faucet-minted and worthless, and the ER is a single trusted operator — not because the code
path is any narrower.

**Suggested remediation.** Add an L1-authoritative `funded_total` (monotone, written only
by `fund_trading_credit`) to `TradingCredit` and have `withdraw_trading_credit` cap the
payout at `funded_total - withdrawn_total`, so an ER-committed `credit` can only ever be
*less* than what L1 recorded. The `withdraw_trading_credit` half is S1's file and is routed
as `S5-X04`; the S5 half is that `delegate_trading_credit` must not grant write authority
over a payout field without one.

### S5-02 · Delegation is a one-way door: every undelegation path is an ER-only CPI (K5 root cause)

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S5-C9
- **Evidence:** `programs/slipstream/src/instructions/delegate_trading_credit.rs:214-231`, `programs/slipstream/src/instructions/undelegate_trading_credit.rs:99-119`, `programs/slipstream/src/instructions/undelegate_orderbook.rs:86-97`, `programs/slipstream/src/instructions/emergency_undelegate.rs:25-36`, `programs/slipstream/src/instructions/fund_trading_credit.rs:52-54`, `programs/slipstream/src/instructions/withdraw_trading_credit.rs:41-43`

**What is wrong.** The L1 delegation state machine has a transition **in** and no
transition **out**. `delegate_trading_credit` runs on L1 and unconditionally reassigns the
credit to the delegation program, with no precondition that the credit be idle and no
confirmation that the ER ever adopted it. Every exit — `undelegate_trading_credit`,
`undelegate_orderbook`, `emergency_undelegate` — is a `ScheduleCommitAndUndelegate` CPI to
`Magic11111111111111111111111111111111111111`, a program that exists only inside the ER.
The program never CPIs the delegation program's own L1 `undelegate`. So once
`delegate_trading_credit` lands, the account's fate is entirely in the ER's hands: L1 sees
`owner == DELeGG…`, which makes `fund_trading_credit` return `CreditStillActive`
(`fund_trading_credit.rs:52-54`) and `withdraw_trading_credit` do the same
(`withdraw_trading_credit.rs:41-43`), while the only instruction that could undo it cannot
be executed from L1. **That is K5: not a keeper bug, a missing state-machine edge.** The
nominal escape hatch, `emergency_undelegate`, is documented in its own source as unable to
execute on either layer (`emergency_undelegate.rs:25-36`) because it combines an ER-only
CPI with an L1-only `GlobalState` write (`emergency_undelegate.rs:139-142`) — so there is
no in-program path out, and the absence is a design gap rather than a missing guard.

**Proof.** Static, by exhaustion of both directions. Three L1 delegation sites, five
magic-program CPI sites, zero L1 undelegation CPIs:

```
$ grep -rn "owner: &DELEGATION_PROGRAM_ID" programs/slipstream/src/
programs/slipstream/src/instructions/delegate_fill_log.rs:197:        owner: &DELEGATION_PROGRAM_ID,
programs/slipstream/src/instructions/delegate_orderbook.rs:191:        owner: &DELEGATION_PROGRAM_ID,
programs/slipstream/src/instructions/delegate_trading_credit.rs:229:        owner: &DELEGATION_PROGRAM_ID,

$ grep -rln "MAGIC_PROGRAM_ID" programs/slipstream/src/ | sort
programs/slipstream/src/instructions/commit_fill_log.rs
programs/slipstream/src/instructions/commit_orderbook.rs
programs/slipstream/src/instructions/emergency_undelegate.rs
programs/slipstream/src/instructions/undelegate_orderbook.rs
programs/slipstream/src/instructions/undelegate_trading_credit.rs
```

Every file in the second list is an undelegate-or-commit path and every one of them targets
the magic program; no file targets the delegation program's `undelegate`. The asymmetry is
also visible in the account lists: `undelegate_orderbook` only *reads* `GlobalState`
(`undelegate_orderbook.rs:48-64`) so it can run inside the ER, whereas
`emergency_undelegate` *writes* it and therefore cannot.

**Blast radius.** Any user whose `delegate_trading_credit` lands while the ER does not
adopt the account loses access to that credit permanently — the funds are neither
withdrawable nor re-fundable, and the PDA is derived from `(owner, market_index)` so the
same wallet can never hold a working credit for that market again. Four bot credits are in
exactly this state on the live deployment right now (K5), and the in-tree workaround is to
abandon the wallets (`keepers/ecosystem.config.js:55-59`, `keepers/.env.example:35-44`) —
which is why this is `[reachable-now]` and not hypothetical. On mainnet the stranded value
is real user collateral, and the same edge applies to the 612 KB `OrderBook` (4.36 SOL of
rent) and to every retired `FillLog` epoch.

**Suggested remediation.** Add an L1-only `force_undelegate` that CPIs the delegation
program's own `undelegate` under the `GlobalState.authority` (the operation
`emergency_undelegate` was meant to be), and split `emergency_undelegate` into an L1
pause/unpause and that forced undelegation so neither half needs the other's layer.
Separately, gate `delegate_trading_credit` on `credit.is_idle()` so a funded, in-use credit
cannot be pushed through the one-way door.

### S5-03 · One permissionless `crank_twap` latches the circuit breaker and halts closes and liquidations

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S5-C8
- **Evidence:** `programs/slipstream/src/instructions/crank_twap.rs:19-29`, `programs/slipstream/src/instructions/crank_twap.rs:55-69`, `programs/slipstream/src/state/market.rs:114-134`, `programs/slipstream/src/instructions/place_order.rs:123`, `programs/slipstream/src/instructions/close_position.rs:101`, `programs/slipstream/src/instructions/liquidate_position.rs:84`

**What is wrong.** `crank_twap` has no signer check of any kind — it validates the market's
owner and the feed's identity and nothing else, so any account that can pay a fee may call
it. It compares the live Pyth price against `Market::get_twap()`, a plain mean of a
**225-slot ring buffer that carries no timestamps** (`market.rs:114-134`): `get_twap` cannot
tell a sample from eight seconds ago from one from sixteen days ago. When the crank has been
down longer than the ring, the first call back compares a live price against a *frozen*
average, sees a >10% "move" that never happened, and latches
`market.circuit_breaker_active = 1` — which blocks `place_order`, `close_position`, **and**
`liquidate_position`. Clearing it requires enough further cranks to drag the mean back
within 10%, which on the live market is 116 more calls. The written invariant is
`crank_twap.rs:12-13` ("if price moved >10% from 5-min TWAP, pauses market" — the ring is
in fact 30 minutes at the keeper's 8s interval, `market.rs:6` with
`keepers/src/twap-keeper.ts:8`) and `close_position.rs:96-100` ("Self-clears on the next
in-range crank, so this is a brief price-integrity pause"). Neither is true here. The
mechanism that hides it is that the keeper cranks every 8 seconds, so the ring is normally
saturated with prices minutes old and the comparison is meaningful — the defect only
surfaces after an outage, which is exactly when nobody is watching.

**Proof.** Live read-only decode of the market and its own Pyth feed at the freeze,
replaying `crank_twap.rs:57-69` in Python. Reproduction:
`docs/audit/audit-e2e/repro/s5/circuit_breaker_live.py`.

```
$ python3 docs/audit/audit-e2e/repro/s5/circuit_breaker_live.py
market  ECUp8pXzVLzxjVs8mtKBJma3mdcHf8zSC4cqPeBy8MPy  owner=7qujfsb4ZPbQHYVZdqiXq1r8tVAMyyukX94obPqXbVwz  len=2064
pyth    7UVimffxr9ow1uXYxsr4LHAcV58mLzhmwaeKvJ1pjLiE  owner=rec5EKMGg6MxZYaMdyBfgwp4d5rB9T1VQH5pJv5LtFJ  len=134
parse_pyth -> price=90992070 ($90.992070)  publish_time=1787339958
twap_count=225 twap_write_index=114 mark_price_minute=12436 last_mark_price=74114120

```

That `crank_twap` is permissionless is exhaustive by inspection — the file contains no
`is_signer` call at all, unlike its sibling commit instructions:

```
$ grep -c "is_signer" programs/slipstream/src/instructions/commit_orderbook.rs programs/slipstream/src/instructions/commit_fill_log.rs programs/slipstream/src/instructions/crank_twap.rs
programs/slipstream/src/instructions/commit_orderbook.rs:1
programs/slipstream/src/instructions/commit_fill_log.rs:1
programs/slipstream/src/instructions/crank_twap.rs:0
```

**Blast radius.** Two harms, both live today. (1) Restarting the keepers halts the market
for ~15 minutes: no new orders, no closes, and no liquidations, while positions carry
20× leverage. (2) Because the trigger is permissionless and one-shot, any third party
chooses *when* it fires — a trader about to be liquidated can send a single `crank_twap`
and disable `liquidate_position` market-wide for the recovery window, at the cost of one
transaction fee. Separately, the ring is count-based rather than time-based with no
per-slot guard, so a caller can overwrite all 225 samples inside a single slot and collapse
the "30-minute TWAP" to spot at will; that also feeds `mark_price_for_close`'s fallback for
a market with `last_mark_price == 0` (`programs/slipstream/src/state/market.rs:180-181`).

**Suggested remediation.** Store a timestamp beside each ring sample (or a `last_crank_ts`
on `Market`) and have `get_twap` ignore samples older than the window, so a stale ring
yields `None` instead of a false baseline; reject a `crank_twap` whose predecessor is in
the same slot. Then latch the breaker on a *price* move rather than a move relative to a
possibly-dead average.

### S5-04 · `commit_orderbook` is permissionless and spends a budget the repo says the book must never spend

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S5-C11
- **Evidence:** `programs/slipstream/src/instructions/commit_orderbook.rs:65-84`, `programs/slipstream/src/instructions/mod.rs:149`, `README.md:103-105`, `programs/slipstream/src/instructions/delegate_fill_log.rs:36-39`, `keepers/src/settlement-keeper.ts:101-107`, `programs/slipstream/src/instructions/commit_fill_log.rs:56-71`

**What is wrong.** `README.md:105` states the 612 KB book "stays delegated forever, never
committed", and `README.md:103-104` gives the reason: a size cap plus "a verified
10-commit-per-account limit". `delegate_fill_log.rs:36-39` restates it — a small account
"can later be undelegated and re-delegated cleanly (or rotated by epoch) to refresh the
sponsored-commit budget — the thing the oversized OrderBook can never do". Yet
`commit_orderbook` (`0x1A`) is dispatched at `mod.rs:149`, is actively used by the

### S5-05 · The single-oracle downgrade fails open on a parser-shaped signal and leaves no on-chain record

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S5-C5
- **Evidence:** `programs/slipstream/src/oracle.rs:223-237`, `programs/slipstream/src/oracle.rs:256-271`, `programs/slipstream/src/oracle.rs:163-174`, `programs/slipstream/src/oracle.rs:331-337`, `programs/slipstream/src/oracle.rs:1-13`

**What is wrong.** That Switchboard is dead on devnet and the protocol runs Pyth-only is
established (`README.md:242`) and not re-reported here. What is not documented anywhere is
*how the switch is made*: `is_switchboard_unavailable` decides purely from the decoded
content of the account — "parse failed, or the price rounded to zero" — and on that signal
`dual_oracle_read` skips the divergence check and returns `agreement: true`
(`oracle.rs:262-271`), while `apply_dual_oracle` returns early and deliberately leaves
`restricted_mode` untouched (`oracle.rs:331-337`). The detector therefore cannot
distinguish *"the feed is dead"* from *"our parser is wrong for this feed"*, and it resolves
that ambiguity by **disabling the safety property**. `parse_switchboard` itself admits it
reads a layout "simplified for MVP" (`oracle.rs:163-174`); the account the live market is
actually configured with is a legacy Switchboard **V2** aggregator, not the On-Demand
`PullFeedAccountData` those offsets were written for. Nothing on-chain records that the
downgrade happened — `Market.restricted_mode` and `Market.agreement_streak` both read 0, the
same values a healthy dual-oracle market shows — so no keeper, no client, and no auditor can
tell the two states apart from account data. The module's own header still asserts the
property that is off (`oracle.rs:3-9`: "Both must … Agree within `MAX_DIVERGENCE_BPS`"), and
the mainnet guard is a comment ("this branch must NOT exist on mainnet",
`oracle.rs:334`) with no feature flag or cluster check behind it.

**Proof.** Live read-only decode of both configured feed accounts, showing which branch is
taken and why:

```

owner SW1TCH7qEPTdLsDHRgPuMQjbQxKdH2aBStViMFnt64f len 3851
```

documents. The zeros at offsets 80–104 are an accident of a dormant V2 aggregator, not a

**Blast radius.** No exploit path today, because the fallback is the only path the live

switch, and so the mode is visible on-chain. The stale `README.md:242` row and the
contradicted module header are routed to S12 as part of `S5-X01`.

### S5-06 · Batched P3 — the oracle parsers are `pub` and enforce no feed binding of their own

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S5-C3
- **Evidence:** `programs/slipstream/src/oracle.rs:55-77`, `programs/slipstream/src/oracle.rs:109-147`, `programs/slipstream/src/oracle.rs:175-195`, `programs/slipstream/src/oracle.rs:249-297`, `programs/slipstream/src/oracle.rs:197-209`

**What is wrong.** `parse_pyth`, `parse_switchboard`, and `dual_oracle_read` are all `pub`,
all read caller-supplied account bytes with `borrow_data_unchecked()`, and none of them
checks the account's owner, discriminator, or identity — `parse_pyth` even dispatches its
entire offset table off `data.len()`. The binding lives in a *separate* function,
`verify_feeds`, whose doc comment states the requirement as a convention the caller must
remember ("MUST be called before any `parse_pyth` / `parse_switchboard`",
`oracle.rs:58-62`). Today every caller honours it, so this is correct and safe as deployed;
the gap is that nothing enforces it structurally, and the one instruction that forgot would
be silently wrong rather than failing to compile. This is the same shape as the calibration
example at `Cargo.toml:8-13`: a rule that lives outside the mechanism that must obey it.

**Proof.** Exhaustive grep of every call site of the three entry points, with the guard on
each path:

```
$ grep -rn "verify_feeds\|dual_oracle_read\|apply_dual_oracle\|parse_pyth\|parse_switchboard" programs/slipstream/src --include='*.rs' | grep -v "^programs/slipstream/src/oracle.rs" | grep -v "//"
programs/slipstream/src/instructions/compute_funding.rs:11:use crate::oracle::{apply_dual_oracle, DualOracleOutcome};
programs/slipstream/src/instructions/compute_funding.rs:57:        match apply_dual_oracle(market, pyth_feed_acc, switchboard_feed_acc, now)? {
programs/slipstream/src/instructions/liquidate_position.rs:18:use crate::oracle::{apply_dual_oracle, DualOracleOutcome};
programs/slipstream/src/instructions/liquidate_position.rs:93:        match apply_dual_oracle(market, pyth_feed_acc, switchboard_feed_acc, now)? {
programs/slipstream/src/instructions/crank_twap.rs:37:        crate::oracle::verify_feeds(market, pyth_feed_acc, None)?;
programs/slipstream/src/instructions/crank_twap.rs:41:    let reading = crate::oracle::parse_pyth(pyth_feed_acc)?;
```

Three call sites, three guards: `apply_dual_oracle` calls `verify_feeds` itself at
`oracle.rs:327`, and `crank_twap` calls it at `crank_twap.rs:37` before
`crank_twap.rs:41`. `dual_oracle_read` is `pub` but has no external caller. So the binding
holds on every reachable path today — hence P3, not P2.

**Blast radius.** None today. The future risk is a fourth price-consuming instruction added
without the `verify_feeds` line, which would be a P0: an attacker-supplied account is an
attacker-chosen price, and via `crank_twap` that price becomes `Market.last_mark_price`.

`10u64.pow(exp_diff)` with no domain check (`oracle.rs:197-209`), which overflows `u64` for
`|exponent + 6| >= 20`; with `overflow-checks = true` now correctly at the workspace root
(`Cargo.toml:13-14`) that aborts the transaction rather than wrapping, and the exponent is
only reachable through a pinned feed, so it is inert.

**Suggested remediation.** Make the binding structural: take `&Market` in `parse_pyth` /
`parse_switchboard` (or return an opaque `VerifiedFeed` from `verify_feeds` that the
parsers require) so an unbound parse cannot be written, and clamp `exp_diff` to the
representable range in `normalise_to_6_decimals`.
