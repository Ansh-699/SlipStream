## Findings

### S4-01 · The settlement cursor is a high-water mark, so a fill absent from the batch is settled zero times

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [reachable-now]
- **Class:** S4-C1
- **Evidence:** `programs/slipstream/src/instructions/settle_from_log.rs:128-141`, `programs/slipstream/src/instructions/settle_from_log.rs:260-271`, `programs/slipstream/src/instructions/settle_trades.rs:44-49`, `docs/audit/audit-e2e/repro/s4/coverage.py:73`

**What is wrong.** `settle_trades.rs:44-49` states the invariant in the code itself:
"Settlement progress is tracked in a program-OWNED cursor on the Market
(`last_settled_sequence`), so each fill is applied to Positions/Users/Market **exactly
once** across repeated keeper calls." `README.md:218-219` sells the same property to
users ("A keeper mirrors your fill from the ER to L1 within a few seconds. Your Positions
table then shows the real settled position"). The implementation only delivers the
*at-most-once* half. `max_seq` is the **maximum** sequence settled in the batch
(`settle_from_log.rs:260-262`), and the cursor is set to it unconditionally
(`settle_from_log.rs:270-271`). Nothing requires the batch to have covered the contiguous
run `last_settled+1 ..= max_seq`. Any fill whose sequence falls in that interval but is
not in the log being settled is jumped over, and because the skip test is
`fill.sequence <= last_settled` (`settle_from_log.rs:139`) it can never be revisited: the
cursor only moves forward and there is no instruction that moves it back.

Nothing surfaced this because the failure is silent and looks like success. The keeper
logs "settled N fills (seq A..B)" (`keepers/src/fill-log-keeper.ts:280-283`), the cursor
rises monotonically, and no error is returned — the skipped fills simply never existed as
far as L1 is concerned.

**Proof.** `docs/audit/audit-e2e/repro/s4/coverage.py` enumerates every FillLog epoch PDA
that exists on L1, reads each one's ER ring (the ER copy is the complete historical record
— `FillLogView::push` never overwrites and nothing drains `count`, `fill_log.rs:80-99`),
unions all sequences ever mirrored, and compares against the live cursor. It fails:

```
$ python3 docs/audit/audit-e2e/repro/s4/coverage.py
FillLog epoch accounts on L1 : 206
  of which ER ring is FULL   : 187
  rent locked in them        : 12.14681472 SOL
Market.last_settled_sequence : 44173
distinct sequences ever mirrored : 11043
ring slots consumed              : 14960 (waste = 3917 duplicate re-mirrors)
sequences 1..cursor NEVER mirrored into any FillLog : 33146
AssertionError: EXACTLY-ONCE VIOLATED: 33146 fill sequences below the settlement
cursor were never mirrored into any FillLog, so they were settled ZERO times while
the cursor advanced past them (settle_from_log.rs:260-271).
```

The gaps are visible epoch by epoch. Each ring is contiguous internally; consecutive
epochs are not:

```
epoch 394: count=80 lms=33161 seq_min=33082 seq_max=33161 contiguous=True
epoch 400: count=80 lms=42781 seq_min=42702 seq_max=42781 contiguous=True   <- 9540 sequences skipped
epoch 401: count=80 lms=43229 seq_min=43150 seq_max=43229 contiguous=True   <-  368 sequences skipped
epoch 403: count=80 lms=44189 seq_min=44110 seq_max=44189 contiguous=True   <-  880 sequences skipped
Market.last_settled_sequence = 44173   (inside epoch 403's range)
```

The cursor sits at 44173, inside epoch 403's window, so all three gaps are already behind
it. The ER OrderBook's ring is full and has wrapped (`max_fill_events=4096`,
`fill_event_head=fill_event_tail=3229`, `count=4096`, `next_fill_sequence=44190`), so the
oldest fill that still physically exists anywhere is sequence 40094 — every skipped
sequence below that is gone from the chain entirely.

**Blast radius.** 33,146 of 44,173 matched fills (75%) never produced an L1 `Position`
update. For each one: the maker's slot margin was drained inside the ER
(`place_order.rs:423`), the taker's `TradingCredit` was debited there, and no
`Position.collateral`, `Position.size`, open-interest, fee, rebate, or insurance-fund
entry was ever written on L1. That money is not recoverable by any instruction the program
ships — `settle_from_log` refuses those sequences forever and the source fills have been
overwritten. On mainnet this is direct, unbounded loss of user collateral on the normal
happy path; no attacker is required.

**Suggested remediation.** Make the cursor a contiguous-prefix cursor: track the batch's
minimum new sequence, require it to equal `last_settled + 1`, and advance only across an
unbroken run (stop at the first gap, leaving the cursor below it). Pair that with S4-02 so
a rotated log actually starts at `last_settled + 1`, and add a recovery instruction that
can re-settle a supplied FillLog for a sequence range below the cursor.

### S4-02 · Every rotated FillLog epoch restarts its mirror cursor at zero and re-mirrors already-settled fills

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S4-C3
- **Evidence:** `programs/slipstream/src/instructions/initialize_fill_log.rs:98-108`, `programs/slipstream/src/instructions/mirror_fills.rs:103-139`, `programs/slipstream/src/instructions/mirror_fills.rs:144-152`, `keepers/src/fill-log-keeper.ts:171-180`

**What is wrong.** `initialize_fill_log` hard-codes `header.last_mirrored_sequence = 0`
(`initialize_fill_log.rs:108`) and its instruction data carries only `market_index` and
`epoch` (`initialize_fill_log.rs:31`), so there is no way to seed it. `mirror_fills` then
decides what is "new" purely against that per-log cursor
(`mirror_fills.rs:103`, `mirror_fills.rs:124`) and never consults
`Market.last_settled_sequence`. A freshly rotated epoch therefore appends the **oldest 80
surviving entries of the OrderBook ring**, which are already settled, rather than the 80
fills immediately after the settlement cursor. Rotation is documented as the designed
recovery for a spent commit budget (`fill_log.rs:6-14`), so this fires on the intended
path, not an exceptional one. The keeper knows about the symptom and works around it
rather than fixing it (`keepers/src/fill-log-keeper.ts:171-180`: "a fresh epoch's FillLog
re-mirrors the ring from sequence 0 … Keep mirroring … but skip the commit until the
mirror catches up") — but the workaround cannot succeed once ≥ 80 already-settled fills
survive in the OrderBook ring, because `FillLogView::push` refuses at capacity
(`fill_log.rs:90-99`) and the log jams before it can catch up.

**Proof.** Live devnet, all 206 FillLog epoch accounts that exist on L1:

```
$ python3 docs/audit/audit-e2e/repro/s4/coverage.py
FillLog epoch accounts on L1 : 206
  of which ER ring is FULL   : 187
  rent locked in them        : 12.14681472 SOL
distinct sequences ever mirrored : 11043
ring slots consumed              : 14960 (waste = 3917 duplicate re-mirrors)
```

3,917 of 14,960 ring slots (26%) were burned on fills that had already been mirrored into
an earlier epoch. Adjacent epochs overlap, which is only possible if the fresh log
restarted below the previous one's end:

```
epoch 382: seq_min=32658 seq_max=32737
epoch 383: seq_min=32693 seq_max=32772   <- 45 sequences re-mirrored from epoch 382
epoch 387: seq_min=32836 seq_max=32915   <- 46 sequences re-mirrored from epoch 386
epoch 394: seq_min=33082 seq_max=33161   <- 42 sequences re-mirrored from epoch 393
```

**Blast radius.** Each epoch can carry at most 80 fills and typically delivers only
~35-55 useful ones, so the pipeline's real throughput is roughly half its nominal
capacity while the ER produces fills at book speed. The operator pays
`(128 + 8344) * 3480 * 2 = 58,965,120` lamports of rent per abandoned epoch; 206 of them
hold 12.147 SOL that no instruction in the program can reclaim (there is no
`close_fill_log`). Combined with S4-01 the wasted capacity is what widens the skip gaps,
so this is the mechanism behind the 75% loss rate, not an efficiency complaint.

**Suggested remediation.** Give `initialize_fill_log` a `start_sequence` argument (or read
the `Market` account and seed `last_mirrored_sequence = market.last_settled_sequence`), so
a fresh epoch begins exactly where settlement left off. Add a `close_fill_log` that
reclaims rent from a fully-settled epoch.

### S4-03 · Refusing to overwrite the FillLog applies no backpressure to the OrderBook, which overwrites unmirrored fills instead

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S4-C5
- **Evidence:** `programs/slipstream/src/state/fill_log.rs:80-99`, `programs/slipstream/src/instructions/mirror_fills.rs:127-150`, `programs/slipstream/src/state/order_book.rs:195-222`

**What is wrong.** `fill_log.rs:80-89` writes the invariant explicitly: "this ring must
never overwrite an entry … overwriting it would silently and irrecoverably destroy a fill
no one has committed to L1." The FillLog honours it — `push` returns `false` at capacity
and `mirror_fills` stops without advancing its cursor (`mirror_fills.rs:127-134`),
surfacing `FillQueueFull` (`mirror_fills.rs:144-150`). But the *producer* side does the
exact thing the invariant forbids: `OrderBookHeader::push_fill_event` overwrites the
oldest entry and advances `fill_event_head` once the 4096-slot ring is full
(`order_book.rs:206-221`), and its justification — "already-mirrored old fills are the
only thing ever overwritten" (`order_book.rs:201-203`) — assumes a keeper that is
keeping up. The FillLog holds 80 (`fill_log.rs:14`); the OrderBook holds 4096. Backpressure
stops at the FillLog and never reaches `place_order`, so refusing the copy converts to
destroying the original.

**Proof.** Live ER OrderBook, read 2026-08-21T19:16Z:

```
[ER OrderBook] 83zMFL6cHjgXkQ7KRNcgtHaZ1fhyNgxhM8aMpPpEnMqe
  disc=5 max_fill_events=4096 fill_event_head=3229 tail=3229 count=4096 next_fill_sequence=44190
[L1 OrderBook] same address, owner DELeGGvXpWV2fqJUhqcF5ZSYMS4JTLjteaAMARRSaeSh
  disc=5 max_fill_events=4096 fill_event_head=0 tail=9 count=9 next_fill_sequence=10
```

`head == tail` with `count == max_fill_events` is the wrapped-and-overwriting state
produced by `order_book.rs:216-220`. Oldest surviving sequence is
`44190 - 4096 = 40094`; 187 of the 206 FillLog rings are simultaneously at
`count == capacity == 80` (`coverage.py` output in S4-01). Producer full and overwriting,
consumer full and refusing, at the same instant.

**Blast radius.** Every fill produced after the FillLog jams evicts an older one from the
OrderBook ring within 4096 fills. Once evicted, the fill exists in no account on either
layer and cannot be settled by any instruction — this is the physical half of the 33,146
lost fills in S4-01. On mainnet the loss rate scales with volume: the busier the book, the
faster unmirrored fills are destroyed.

**Suggested remediation.** Make the producer respect the consumer: have
`push_fill_event` return an error (rather than overwrite) when
`fill_event_count == max_fill_events`, so `place_order` fails loudly and the book stops
matching until settlement drains. If halting matching is unacceptable, size the FillLog
and the mirror cadence so the OrderBook ring cannot wrap before mirroring, and assert
that relationship on-chain.

### S4-04 · `pending_fills` is incremented per user but decremented per fill-side, has no reset path, and is already blocking 438,643 USDC on devnet

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [reachable-now]
- **Class:** S4-C10
- **Evidence:** `programs/slipstream/src/instructions/record_pending_fill.rs:24-36`, `programs/slipstream/src/instructions/record_pending_fill.rs:73-82`, `programs/slipstream/src/instructions/settle_from_log.rs:195-224`, `programs/slipstream/src/instructions/withdraw_collateral.rs:77-80`

**What is wrong.** The invariant is written in the code: `record_pending_fill.rs:26-32`
states `pending_fills` is "a monotonic counter decremented one-per-settled-fill by
settle_trades/settle_from_log, with **no user- or admin-facing reset path**", and that it
gates withdrawals and liquidation. The two halves do not match. `record_pending_fill`
bumps each **distinct user account** in the batch by exactly one
(`record_pending_fill.rs:73-82`), and the keeper passes the deduplicated user set for a
window of up to 8 fills (`keepers/src/fill-log-keeper.ts:252-276`). Settlement decrements
once per **fill, per side**, guarded by `if … > 0` (`settle_from_log.rs:199-201`,
`settle_from_log.rs:221-223`). So a batch that settles fully leaves the counter floored at
zero (over-decrement swallowed), while a batch that settles a partial prefix — the
documented `break` path when any of the four accounts is missing
(`settle_from_log.rs:171-187`) — leaves every non-settled user's bump permanently
outstanding. Because the whole transaction is atomic, the bump and the partial settle
commit together; there is no path that undoes the bump.

**Proof.** All 45 live `UserAccount`s on devnet, read 2026-08-21T19:36Z (byte 0 ==

`withdraw_collateral.rs:77-80` rejects with `PendingFillsExist` while the counter is
non-zero, and `close_user_account.rs:82-84` does the same, so those 13 wallets can neither
withdraw nor close. Total blocked: 438,643,100,422 quote atoms = **438,643.10 USDC**

advisory: refuse withdrawal only while a *specific* unsettled sequence is recorded, not on
a free-running counter).

### S4-05 · Settlement accepts any account whose first byte matches a discriminator as a maker/taker account

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S4-C4
- **Evidence:** `programs/slipstream/src/instructions/settle_trades.rs:463-497`, `programs/slipstream/src/instructions/settle_trades.rs:499-534`, `programs/slipstream/src/instructions/settle_from_log.rs:44-96`, `programs/slipstream/src/state/user_account.rs:36-49`

**What is wrong.** Both settlement entry points are fully permissionless — there is no
`is_signer` check in either file — and both locate the four accounts they credit by
scanning `remaining_accounts` for the first entry whose byte 0 equals the expected
discriminator and whose embedded `owner` field equals `fill.maker`/`fill.taker`
(`settle_trades.rs:463-534`). Neither the finders nor `UserAccount::from_account_info_mut`
/ `Position::from_account_info_mut` (`user_account.rs:36-49`) checks
`account.owner() == program_id`, and neither re-derives the PDA. The comment at
`settle_trades.rs:83-86` states the intended rule — "This instruction is permissionless
and mints Position collateral from the fills it reads, so BOTH accounts must be pinned to
their canonical PDAs. A discriminator byte alone is not identity" — and then applies it to
the `market` and `order_book` accounts only, leaving the four accounts that actually
receive value pinned by nothing but a discriminator byte.

**Proof.** Every ownership check and every finder call site in the settlement path:

```
$ grep -n "is_signer" settle_trades.rs settle_from_log.rs mirror_fills.rs
(no matches)

$ grep -n "\.owner()" settle_trades.rs settle_from_log.rs mirror_fills.rs

settle_from_log.rs:89:    if market_acc.owner() != program_id {
settle_trades.rs:74:    if global_state_acc.owner() != program_id {
settle_trades.rs:87:    if market_acc.owner() != program_id {

$ grep -rn "find_user_account\|find_position_account" programs/slipstream/src/
settle_from_log.rs:157:  try_find_user_account(remaining_accounts, &fill.maker);
settle_from_log.rs:158:  try_find_user_account(remaining_accounts, &fill.taker);
settle_from_log.rs:160:  try_find_position_account(remaining_accounts, &fill.maker, market_index_for_pos);
settle_from_log.rs:162:  try_find_position_account(remaining_accounts, &fill.taker, market_index_for_pos);

```

Those eight call sites are the complete set; no other caller exists, so the guard is
absent on every path.

Filed at P2 rather than P1 because the SVM's write protection is doing the work the
missing check should do: a foreign-owned forged account whose bytes change during the
instruction aborts the transaction, which blocks the interesting variants (crediting a
fake rich `UserAccount`, or writing a forged `Position`). The residual I could not settle
here is the **zero-delta** variant — a forged `UserAccount` carrying the victim's pubkey
with `free_collateral == 0` and `pending_fills == 0` makes
`collected = fee_owed.min(0) = 0` and `taker_user.free_collateral -= 0`
(`settle_from_log.rs:195-203`), so no byte changes and the runtime's comparison-based
check may not fire; the fill then settles with zero fee collected, zero maker rebate, zero
insurance cut, and the cursor advances past it. Settling that requires sending one devnet
transaction, which this run's shape forbids (spec §Assumptions 2). If it holds, this is
P1 `[reachable-now]`: permanent, per-fill evasion of the taker fee and denial of the
maker's rebate on a permissionless instruction anyone can front-run the keeper on.

**Blast radius.** Bounded today by runtime write protection. If the zero-delta variant
holds, any taker can settle their own fills fee-free and permanently deny the counterparty
maker their rebate and the market its insurance-fund accrual, once per fill, with no
signer and no privilege. On mainnet the same missing check is the difference between "the
runtime happens to catch it" and a genuine credit-to-arbitrary-account bug the moment any
future instruction writes to those accounts through a path the runtime does not compare.

**Suggested remediation.** In all four finders, require `acc.owner() == program_id` and
re-derive the canonical PDA (`["user", owner]`, `["position", owner, market_index]`) and
compare it to `acc.key()`, exactly as `settle_trades.rs:87-104` already does for `market`
and `order_book`.

### S4-06 · `filled_margin` becomes `Position.collateral` with no L1-side debit and no link to any `TradingCredit`

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [mainnet-only]
- **Class:** S4-C6
- **Evidence:** `programs/slipstream/src/state/fill_event.rs:17-24`, `programs/slipstream/src/instructions/settle_from_log.rs:226-246`, `programs/slipstream/src/instructions/settle_trades.rs:327-335`, `programs/slipstream/src/instructions/close_position.rs:171-232`

**What is wrong.** `PRODUCT.md:38` is the product's central safety claim: "a misbehaving

and reject any fill whose `filled_margin` exceeds it.

### S4-07 · The committed FillLog's `count` is never bounded by its `capacity`, so one commit can be settled repeatedly inside a single call

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [mainnet-only]
- **Class:** S4-C8
- **Evidence:** `programs/slipstream/src/instructions/settle_from_log.rs:108-141`, `programs/slipstream/src/instructions/settle_trades.rs:111-148`, `programs/slipstream/src/state/fill_log.rs:90-99`

**What is wrong.** `settle_from_log` reads `head`, `count` and `capacity` out of the
committed header (`settle_from_log.rs:108-115`) and validates `capacity != 0` and that the
account is big enough (`settle_from_log.rs:116-121`) — but never that
`count <= capacity`. The loop then runs `while processed < count` with
`idx = (head + processed) % capacity` (`settle_from_log.rs:131-132`). With
`count > capacity` the index wraps and re-reads slots it has already consumed, and because
the skip test compares against `last_settled` — a snapshot taken *before* the loop
(`settle_from_log.rs:98-101`, `settle_from_log.rs:139`) rather than the running `max_seq`
— a re-read fill is not recognised as already settled and is applied a second time: fee
charged again, rebate paid again, `filled_margin` added to `Position.collateral` again,
open interest incremented again. `settle_trades.rs:111-148` has the identical shape
against `fill_event_count` / `max_fill_events`. The on-chain writer cannot produce this
state (`FillLogView::push` refuses at `count >= cap`, `fill_log.rs:90-94`), which is
exactly why the reader treats it as impossible — but the reader's input is ER-authored
bytes, not the writer's output.

**Proof.** The full set of comparisons the reader makes against these two header fields:

```
$ grep -n "count\|capacity" settle_from_log.rs | grep -E "^\s*1(0[89]|1[0-9]|2[0-9]|3[0-9])"
108:    let (head, count, capacity) = {
112:            header.count as usize,
113:            header.capacity as usize,
116:    if capacity == 0 {
119:    if FillLogHeader::LEN + capacity * FillEvent::LEN > fl_data.len() {
122:    if count == 0 {
131:    while processed < count && settled < num_fills {
132:        let idx = (head + processed) % capacity;
```

`count` is compared to `0` and to nothing else. `capacity` is compared to `0` and to the
account length. There is no `count <= capacity` anywhere in the file. Reachability
requires an ER able to commit chosen header bytes, which this run cannot demonstrate
without a validator it controls — that half is reasoned from the code, not exercised.

**Blast radius.** With `count = 65535`, `capacity = 80` and `num_fills = 65535`, each of
the 80 stored fills is settled up to 819 times in a single instruction: every repetition
adds `filled_margin` to a `Position` and charges the taker again. That mints
`Position.collateral` and therefore vault-withdrawable balance from nothing. Tagged
`[mainnet-only]` on the same reasoning as S4-06 — the capability belongs to the ER
operator, not to an arbitrary devnet caller.

**Suggested remediation.** Reject `count > capacity` alongside the existing
`capacity == 0` check, and make the in-loop skip test compare against the running
`max_seq` rather than the pre-loop `last_settled`, so a duplicate sequence inside one
batch is skipped even if the header lies. Apply the same two changes to
`settle_trades.rs:125-148`.

### S4-08 · Sequence order is assumed by the position math but enforced nowhere

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [mainnet-only]
- **Class:** S4-C2
- **Evidence:** `programs/slipstream/src/instructions/settle_from_log.rs:131-141`, `programs/slipstream/src/instructions/settle_trades.rs:354-356`, `programs/slipstream/src/instructions/settle_trades.rs:377-405`, `programs/slipstream/src/instructions/settle_trades.rs:44-49`

**What is wrong.** The accounting in `update_position` is path-dependent: the VWAP entry
price folds each fill into the previous entry price (`settle_trades.rs:354-356`), and the
reduce/flip branch computes realised PnL and the collateral release from the *current*
`entry_price` and `abs_size` (`settle_trades.rs:377-405`). Applying the same set of fills
in a different order produces a different `entry_price`, a different `realized_pnl`, and a
different `free_collateral`. The code states the order property as an assumption about the
producer — "the committed queue holds every fill in ascending `sequence` order from
`fill_event_head`" (`settle_trades.rs:47-49`) — and then reads `head` straight out of the
account header without checking anything about it (`settle_from_log.rs:108-113`). The
only sequence test in the loop is the monotonic gate `fill.sequence <= last_settled`
(`settle_from_log.rs:139`), which accepts any order among fills above the cursor. The
spec's own rule for this class ("if assumed, P1") applies literally.

**Proof.** The complete sequence handling in the settlement loop:

```
settle_from_log.rs:131  while processed < count && settled < num_fills {
settle_from_log.rs:132      let idx = (head + processed) % capacity;   // `head` = header byte, unchecked
settle_from_log.rs:139      if fill.sequence <= last_settled { continue; }   // monotonic gate only
settle_from_log.rs:260      if fill.sequence > max_seq { max_seq = fill.sequence; }
```

No comparison between consecutive fills' sequences exists; `max_seq` is only a running
maximum, never used as an ordering constraint. `head` is not range-checked against
`count` or `capacity` — the modulo makes it memory-safe but lets any rotation of the ring
be presented as the read order.

**Blast radius.** An ER that rotates `head` (or interleaves appends) makes L1 compute a
wrong `entry_price` for both legs of every affected fill, and a wrong `realized_pnl` and
`free_collateral` credit on any reducing fill. Those are the numbers liquidation and
health factor run on, so mis-ordered settlement can move a position across the liquidation
threshold in either direction. Tagged `[mainnet-only]`: on devnet the order is maintained
in practice because `mirror_fills` appends in ring-scan order
(`mirror_fills.rs:119-139`) and nothing has reordered it, but nothing on L1 would notice
if that stopped being true.

**Suggested remediation.** Enforce what the comment already assumes: track the previously
applied sequence inside the loop and reject (or stop at) any fill whose sequence is not
strictly greater, so an out-of-order or rotated ring fails closed rather than settling at
wrong prices.

### S4-10 · The settlement cursor is stored as a `u32` and fill quantity is cast to `i64`, both without a guard

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S4-C9
- **Evidence:** `programs/slipstream/src/instructions/settle_from_log.rs:270-271`, `programs/slipstream/src/instructions/settle_trades.rs:255-257`, `programs/slipstream/src/instructions/settle_trades.rs:316-320`, `programs/slipstream/src/state/market.rs:189-213`

**What is wrong.** Two silent narrowing conversions sit on the settlement path.
(a) `FillEvent.sequence` is a `u64` (`fill_event.rs:12`), but the cursor it feeds is
packed into four bytes of `Market._padding2` and written as `(seq as u32).to_le_bytes()`
(`market.rs:207-213`), called unconditionally from `settle_from_log.rs:270-271` and
`settle_trades.rs:255-257`. The doc comment (`market.rs:191-197`) argues the bound is
fine — "A u32 supports ~4.29B fills, far beyond the devnet MVP" — but states it as a
belief about volume, not as an enforced precondition: nothing rejects a fill whose
sequence is ≥ 2^32. Settling one truncates the cursor to `seq mod 2^32`, which for
`seq == 2^32` is **zero**, re-opening every fill in the ring for replay.
(b) `signed_qty = fill_qty as i64` (`settle_trades.rs:316-320`) wraps to a negative value
for `fill_qty > i64::MAX`, so a BID fill would open a short position and corrupt open
interest; `compute_notional` (`fixed_point.rs:53-62`) does not catch it when
`fill.price == 0`.

**Proof.** Both conversions, with the guard that is absent:

```
market.rs:207   pub fn set_last_settled_sequence(&mut self, seq: u64) {
market.rs:208       let bytes = (seq as u32).to_le_bytes();      // truncates; no check on `seq`
settle_from_log.rs:271   market.set_last_settled_sequence(max_seq);   // max_seq is u64 from ER bytes

settle_trades.rs:316   let signed_qty = if side == SIDE_BID {
settle_trades.rs:317       fill_qty as i64                        // wraps for fill_qty > i64::MAX
settle_trades.rs:319       -(fill_qty as i64)
```

Live cursor is 44,173 (`probe_devnet.py` output in S4-01), so the honest path is nowhere
near the bound; the reachable variant needs an ER able to author the `sequence` and
`quantity` fields, which this run cannot exercise. `[profile.release] overflow-checks`
is now on at the workspace root (`Cargo.toml:13-14`), so the `+=` arithmetic aborts rather
than wrapping — but `as` casts are unaffected by that setting, which is why these two
survive it.

**Blast radius.** No path today. If it fires, (a) resets the exactly-once cursor to a low
value and every fill still in the log is re-settled — the double-credit that S4-07 also
reaches, from a different direction; (b) inverts a position's side, which corrupts
`open_interest_long`/`short` and every health-factor and liquidation computation that
reads them.

**Suggested remediation.** Reject `fill.sequence > u32::MAX` in both settle loops (or
widen the cursor by moving it out of `_padding2` in the next layout change), and use
`i64::try_from(fill_qty)` in `update_position`, returning `MathOverflow` on failure.

### S4-11 · Settlement pays out `rebate + 10% insurance` against a fee bounded only by `rebate <= fee`

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S4-C6
- **Evidence:** `programs/slipstream/src/instructions/settle_from_log.rs:204-212`, `programs/slipstream/src/instructions/settle_trades.rs:182-190`, `programs/slipstream/src/instructions/settle_trades.rs:29-30`, `programs/slipstream/src/instructions/initialize_market.rs:91`

**What is wrong.** Settlement collects at most `taker_fee_collected` from the taker and
then pays out two things scaled to it: the maker rebate and a 10% insurance cut
(`INSURANCE_SHARE_BPS = 1000`, `settle_trades.rs:29-30`). The scaling makes both
proportional to what was actually collected (`settle_from_log.rs:204-212`), which is the
right shape, but the *sum* is only conserved if
`maker_rebate_bps + 0.10 * taker_fee_bps <= taker_fee_bps`. The only bound the program
enforces is `maker_rebate_bps > taker_fee_bps` → reject, at market creation
(`initialize_market.rs:91`). The 10% insurance share is not in that inequality and is not
re-checked at settlement, so a market configured with `maker_rebate_bps == taker_fee_bps`
passes initialisation and then pays out 110% of every fee collected.

**Proof.** With `taker_fee_bps == maker_rebate_bps == F` and `notional == N`:

```
taker_fee_owed      = N*F/10000
maker_rebate_owed   = N*F/10000            (== taker_fee_owed, allowed by initialize_market.rs:91)
insurance_cut_owed  = taker_fee_owed/10
collected           = min(taker_fee_owed, taker.free_collateral)
maker_rebate        = maker_rebate_owed * collected / taker_fee_owed = collected
insurance_cut       = insurance_cut_owed * collected / taker_fee_owed = collected/10
payout              = collected * 1.10   >  collected      <- 10% minted per fill
```

The live market is safe: read 2026-08-21T19:36Z, `Market.taker_fee_bps = 6` (offset 6) and
`Market.maker_rebate_bps = 1` (offset 8), giving a payout ratio of
`1/6 + 0.10 = 0.267`, well under 1. `insurance_fund_balance` reads 20,725,715 (6-dp). So
this is an absent bound, not a live drain — P2 by the spec's definition.

**Blast radius.** A market created with a rebate close to the taker fee credits
`Market.insurance_fund_balance` more than the vault ever received. The insurance fund is
drawn on to absorb liquidation shortfalls, so the excess is a claim on other users'
collateral rather than a bookkeeping-only error. Reachable only by the market authority at
`initialize_market`, and there is no instruction to change the fees afterwards.

**Suggested remediation.** Tighten the initialisation guard to
`maker_rebate_bps * 10000 + taker_fee_bps * INSURANCE_SHARE_BPS <= taker_fee_bps * 10000`,
and additionally assert `maker_rebate + insurance_cut <= taker_fee_collected` at the point
of payout in both settle files, so an ER-supplied snapshot pair cannot break it either.

**Blast radius.** Every funding payment computed during settlement is scaled by a mark
price 16 days stale and ~19% below the market's own configured Pyth feed, so the debit or

than reading `last_mark_price` unconditionally.

## Cleared

- **S4-C1** — Exactly-once, both directions. Double-settle is prevented on the honest path:
  the cursor is read before the loop and every fill is gated on `fill.sequence <= last_settled`
  (`programs/slipstream/src/instructions/settle_from_log.rs:139`), the two entry points
  share that one cursor, and Solana transaction atomicity means a failed batch advances
  nothing. The *zero-times* direction is broken — covered by S4-01, with the in-call
  duplicate variant in S4-07.
- **S4-C2** — Ordering. Covered by S4-08. Verified sound in the honest chain:
  `mirror_fills` scans the OrderBook ring from `head` in ring order and appends in that
  order (`programs/slipstream/src/instructions/mirror_fills.rs:119-139`), the OrderBook
  ring is FIFO, and the live rings are contiguous and ascending (`coverage.py` per-epoch
  dump, every epoch `contiguous=True`). Nothing on L1 enforces it, which is the finding.
- **S4-C3** — Epoch rotation. Covered by S4-02. Also checked and found sound: the epoch is
  a PDA seed so a stale-epoch log cannot be settled against another epoch's account
  (`programs/slipstream/src/instructions/settle_from_log.rs:74-81`); re-initialising an
  existing epoch is refused (`programs/slipstream/src/instructions/initialize_fill_log.rs:79-81`);
  and the cursor lives on the Market, not the log, so rotation cannot rewind settlement
  progress.
- **S4-C4** — Replay and authorization. Covered by S4-05. Found sound: a hand-crafted
  FillLog cannot be substituted — the account is pinned to
  `["fill_log", market_index, epoch]` (`programs/slipstream/src/instructions/settle_from_log.rs:74-81`)
  and a PDA at that address can only be created by this program; the Market is pinned by
  owner and PDA (`settle_from_log.rs:89-96`); `global_state` is pinned and the pause flag
  is honoured (`settle_from_log.rs:53-60`); replaying a previously committed log account is
  a no-op because its sequences are `<= last_settled`. `mirror_fills` is permissionless by
  design and cannot fabricate fills — it copies from a PDA-pinned OrderBook
  (`programs/slipstream/src/instructions/mirror_fills.rs:57-69`).
  `record_pending_fill` and `initialize_fill_log` both require the `GlobalState.authority`
  signer (`programs/slipstream/src/instructions/record_pending_fill.rs:48-63`,
  `programs/slipstream/src/instructions/initialize_fill_log.rs:43-62`).
- **S4-C5** — Capacity and backpressure. Covered by S4-03. The log itself behaves
  correctly at `programs/slipstream/src/state/fill_log.rs:90-99`: `push` refuses at
  capacity rather than wrapping, and `mirror_fills` does not advance its cursor past the
  refused fill; `max_fills == 0` is clamped to the ring size rather than read as unbounded
  (`programs/slipstream/src/instructions/mirror_fills.rs:109-113`). One documentation
  mismatch noted and deliberately not filed as it affects no behaviour:
  `programs/slipstream/src/state/fill_log.rs:9-10` says `FillLogHeader::LEN (32)` and
  `= 8352 bytes`, while the struct is 24 bytes and the live accounts are 8,344
  (`probe_devnet.py` output: `len=8344`); both are under the 10,240-byte CPI cap the
  comment is arguing about.
- **S4-C6** — Value conservation across the boundary. Covered by S4-06 (the unbacked
  `filled_margin` credit) and S4-11 (the missing payout bound). Verified sound:
  `PRODUCT.md:53`'s claim that the taker fee is "snapshotted onto each fill event" holds —
  settlement charges `fill.taker_fee_bps_snapshot`, never a re-read of the live
  `Market.taker_fee_bps` (`programs/slipstream/src/instructions/settle_from_log.rs:143-146`).
  The taker debit is floored at the taker's balance and the downstream payouts are scaled
  to what was actually collected rather than to what was owed
  (`settle_from_log.rs:195-212`), which is the correct no-minting shape. The taker leg
  being credited with the *maker's* `filled_margin`
  (`programs/slipstream/src/instructions/settle_trades.rs:217-226`) is sound today because
  both sides' margin is computed at the same `level_price` with the same
  `market.max_leverage` — `leverage` is not a per-order input
  (`programs/slipstream/src/instructions/place_order.rs:169`,
  `programs/slipstream/src/instructions/place_order.rs:426-427`) and no instruction can
  change `max_leverage` after `initialize_market`
  (`programs/slipstream/src/instructions/mod.rs:112-166` has no setter).
- **S4-C7** — `settle_trades` / `settle_from_log` duality. Covered by S4-09. Verified they
  cannot both settle the same fill: both read and write the single cursor
  `Market.last_settled_sequence` (`programs/slipstream/src/instructions/settle_trades.rs:256-257`,
  `programs/slipstream/src/instructions/settle_from_log.rs:270-271`), and both apply the
  same `update_position` implementation (`settle_from_log.rs:10-12` imports it), so the
  accounting is genuinely identical rather than a second copy that could drift. Both also
  gate on the global pause (`settle_trades.rs:74-81`, `settle_from_log.rs:53-60`).
- **S4-C8** — Trust in ER-authored data. The full field-by-field enumeration is the
  producer-contract table above (for S5's `S5-C2`); the unbounded `count` is filed as
  S4-07. Found sound at `programs/slipstream/src/instructions/settle_from_log.rs:104-121`:
  the FillLog discriminator, capacity, and account-length bound are all validated before
  any indexing, and both ring indices are modulo-reduced, so no ER-authored header value
  can drive an out-of-bounds read of the account
  (`programs/slipstream/src/state/fill_event.rs:12-24` is the field list it indexes).
- **S4-C9** — Arithmetic. Covered by S4-10. Verified sound elsewhere on the path: fee and
  notional math is `u128`-widened with explicit overflow errors
  (`programs/slipstream/src/math/fixed_point.rs:53-87`); position collateral and the
  insurance fund use `checked_add`
  (`programs/slipstream/src/instructions/settle_trades.rs:327-332`,
  `programs/slipstream/src/instructions/settle_from_log.rs:249-253`); the reduce/flip
  branch guards its divisors with `.max(1)`
  (`programs/slipstream/src/instructions/settle_trades.rs:392-402`); and
  `overflow-checks = true` now sits at the workspace root where Cargo honours it
  (`Cargo.toml:13-14`), so the remaining `+=` on `pos.size` aborts rather than wrapping.
- **S4-C10** — Partial-failure atomicity. Covered by S4-04 (the `pending_fills` half). The
  cursor half is correct: a batch that stops early advances the cursor only to the maximum
  sequence it actually settled (`programs/slipstream/src/instructions/settle_from_log.rs:260-271`),
  the `break` on a missing maker/taker account deliberately does **not** advance past the
  unsettled fill (`settle_from_log.rs:171-187`), a batch that settles nothing errors out
  before writing (`settle_from_log.rs:266-268`), and any error inside the loop reverts the
  whole instruction, so there is no torn state between the Position, UserAccount, and
  Market writes.
