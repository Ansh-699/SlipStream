### S8-01 · The RPC proxy allowlists `getProgramAccounts`, turning a 134-byte anonymous request into 4.9 MB of upstream work

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S8-C3
- **Evidence:** `frontend/src/app/api/rpc/[layer]/route.ts:66-80`, `frontend/src/app/api/rpc/[layer]/route.ts:99-115`, `frontend/src/app/api/rpc/[layer]/route.ts:132-149`

**What is wrong.** The route's own comment states the invariant: "This proxy is
unauthenticated and forwards to an upstream that carries a private API key, so it is a
free relay onto the deployer's paid RPC quota unless it is bounded", and names
`getProgramAccounts` against the 612 KB orderbook program as "exactly how this project
burned its quota before" (`frontend/src/app/api/rpc/[layer]/route.ts:66-70`). It then
allowlists that method anyway (`:80`), bounded only by a 100 KB **request** body cap
(`:71`) and a 20-call **batch** cap (`:107`). Both caps measure the request; neither
measures the upstream work the request causes. K6 records these two caps as the existing
mitigation — this finding is the residual: the audit shows the mitigation does not hold,
because the quantity it bounds is not the quantity that was exhausted.

**Proof.** Measured directly against the two upstreams the proxy forwards to
(`:24-27`), read-only, 2026-08-21. Re-runnable as
`docs/audit/audit-e2e/repro/s8/rpc-relay-amplification.sh`:

```
$ bash docs/audit/audit-e2e/repro/s8/rpc-relay-amplification.sh
one allowlisted getProgramAccounts, measured at the upstream:
base   request=134 B  response=30739 B  amplification=229x  per-capped-request(x20)=0.6 MB
er     request=134 B  response=4956842 B  amplification=36991x  per-capped-request(x20)=94.5 MB

the 612 KB OrderBook (83zMFL6cHjgXkQ7KRNcgtHaZ1fhyNgxhM8aMpPpEnMqe) is
delegated, so it is returned by the ER scan, not the base-layer scan.
```

The batch cap permits 20 such calls in one request, all of which pass `methodsAllowed`
(`:108-114`) because it checks only the `method` string. A 2.7 KB request — well inside
the 100 KB cap — therefore costs the upstream ~94.5 MB. There is no rate limiter, no
authentication, and no per-IP accounting anywhere in the file; `POST` (`:117-149`) goes
straight from the two caps to `forward()`, which additionally retries up to 3 times
(`:33`), tripling the cost of any request the upstream drops.

**Blast radius.** Any anonymous internet client. The upstream is the deployer's keyed
base RPC and the MagicBlock ER. Exhausting that quota is precisely the K1 chain — public
devnet RPC quota exhausted → keepers crash-loop → pm2 gives up at `max_restarts: 50` —
so this route hands an outside party a remote trigger for the same 17-day outage. The
keepers, the browser, and the settlement pipeline all share that quota. On mainnet the
same route would be a paid-egress bill an attacker writes.

**Suggested remediation.** Move `getProgramAccounts` behind either a durable rate limit
keyed on a trustworthy client identity or a small server-side endpoint that performs the
one memcmp scan `use-positions.ts` actually needs and returns only the matching
`Position` accounts; keep the generic method off the public allowlist. Failing that, cap
batches containing `getProgramAccounts` at 1 and require a `filters` array.

### S8-02 · Every faucet limiter is per-process memory, so nothing durable bounds minting or the operator's SOL

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S8-C1
- **Evidence:** `frontend/src/app/api/faucet/route.ts:52-63`, `frontend/src/app/api/faucet/route.ts:145-161`, `frontend/src/app/api/faucet/route.ts:178-206`

**What is wrong.** `PRODUCT.md:60` states the faucet "is rate-limited per wallet, per IP,
and globally". All three limiters are module-scope JavaScript containers — `lastDrip`
(`:53`), `dripTimes` (`:61`), `lastDripByIp` (`:62`) — whose entire lifetime is one
process. `frontend/vercel.json:2` declares the Next.js framework preset with per-function
overrides (`:6-13`), i.e. the configured deployment target is serverless: a second
concurrent invocation starts with all three containers empty, and so does every cold
start. The per-wallet limiter additionally bounds nothing on its own, which the file's
own comment concedes at `:55-59` ("the wallet is supplied by the caller, and fresh
keypairs are free"). That leaves the global hourly cap as the only real bound, and it
resets on restart. This is K3's residual gap: not that the faucet holds mint authority
(given), but that the mitigations K6 credits it with are not durable in the topology the
repo itself configures.

The cost side compounds it. A fresh pubkey has no ATA and no SOL, so **both** expensive
branches always fire for a first-time caller: `getOrCreateAssociatedTokenAccount` with
the operator as payer (`:178-183`) and the SOL top-up, whose floor check `bal <
SOL_TOPUP_FLOOR * LAMPORTS_PER_SOL` is trivially true at `bal = 0` (`:193-206`). Fresh
pubkeys are free to the caller and cost the operator real lamports.

**Proof.** `docs/audit/audit-e2e/repro/s8/faucet-bounds.mjs`; ATA rent read live from
devnet on 2026-08-21:

```
$ curl -s -X POST https://api.devnet.solana.com -H 'Content-Type: application/json' \
    -d '{"jsonrpc":"2.0","id":1,"method":"getMinimumBalanceForRentExemption","params":[165]}'
{"jsonrpc":"2.0","result":2039280,"id":1}

$ node docs/audit/audit-e2e/repro/s8/faucet-bounds.mjs
=== A2) limiter lifetime ===
  in-process: { wallets: 1, ips: 1, drips: 1 }
  after a restart / a second serverless instance: { wallets: 0, ips: 0, drips: 0 }
=== B) operator cost per first-time pubkey ===
  ATA rent (operator pays) : 0.00203928 SOL
  SOL top-up               : 0.05 SOL
  tx fees                  : 0.000015 SOL
  total per drip           : 0.052054 SOL
  at the nominal 60/hr cap : 3.123 SOL/hr and 600000 test USDC/hr
  ...per process. The cap is not durable (A2), so this is a floor, not a bound.
```

**Blast radius.** Anonymous. Two harms, both live today. (1) **Operator SOL drain** at
≥3.12 SOL/hour per process, multiplied by however many instances the host runs. Per K2
that key is simultaneously the keeper signer and the program upgrade authority, so
draining its SOL stops every keeper — the K1 failure, reachable by HTTP. (2) **Unbounded
collateral inflation**: ≥600,000 test USDC/hour minted into the live market the bots
quote in, which distorts every position and every liquidation in it. On mainnet a server
route that signs with the mint authority under a memory-resident limiter is a P0 shape;
it is P1 here only because the minted token is worthless.

**Suggested remediation.** Move all three counters to durable shared storage (the same
SQLite file the indexer already uses, or an external KV) so the cap survives restarts and
spans instances; and gate the SOL top-up behind a signature-of-ownership challenge so a
caller must prove control of the pubkey before the operator pays its rent.

### S8-03 · A non-numeric `FAUCET_MAX_PER_HOUR` silently deletes the global cap

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S8-C4
- **Evidence:** `frontend/src/app/api/faucet/route.ts:60`, `frontend/src/app/api/faucet/route.ts:71-76`

**What is wrong.** `GLOBAL_MAX_PER_HOUR = Number(process.env.FAUCET_MAX_PER_HOUR || "60")`
(`:60`) is never validated. `Number("sixty")` is `NaN`, and the cap test at `:75` is
`dripTimes.length >= GLOBAL_MAX_PER_HOUR` — every comparison against `NaN` is `false`, so
an unparseable value does not fall back to 60 and does not error: it removes the only
durable-in-principle bound the faucet has, silently. Nothing logs, nothing 500s, and the
route behaves identically to a healthy one until someone loops it. This is the same shape
as the run's calibration example: a configuration value that is silently ignored, with no
error anywhere, leaving a safety property off. It is an outlier rather than a house
style — every other faucet knob fails *closed* under the same treatment.

**Proof.** `docs/audit/audit-e2e/repro/s8/faucet-bounds.mjs`:

```
=== A) env parsing: which knobs fail open ===
  FAUCET_MAX_PER_HOUR  = "60"     -> Number() = 60     cap enforced at 1000 drips? true
  FAUCET_MAX_PER_HOUR  = "sixty"  -> Number() = NaN    cap enforced at 1000 drips? false
  FAUCET_SOL_AMOUNT    = "0.05"   -> Number() = 0.05   top-up fires? true
  FAUCET_SOL_AMOUNT    = "abc"    -> Number() = NaN    top-up fires? false
  FAUCET_SOL_FLOOR     = "0.02"   -> Number() = 0.02   0-balance wallet below floor? true
  FAUCET_SOL_FLOOR     = "abc"    -> Number() = NaN    0-balance wallet below floor? false
  only FAUCET_MAX_PER_HOUR flips a guard OFF when it is unparseable.
```

`FAUCET_USDC_AMOUNT="abc"` also fails closed, but noisily: `BigInt(Math.round(NaN * 1e6))`
(`:184`) throws `RangeError`, caught by the outer handler at `:221` and returned as a
generic 502.

**Blast radius.** One typo or one shell-quoting accident in the deployment environment
removes the faucet's global cap with no signal, converting S8-02 from "≥3.12 SOL/hour per
process" into "unbounded". Requires operator error, not attacker action, which is what
keeps it at P2.

**Suggested remediation.** Parse once with validation — `const n =
Number(process.env.FAUCET_MAX_PER_HOUR); GLOBAL_MAX_PER_HOUR = Number.isFinite(n) && n > 0
? n : 60;` — and apply the same guard to the other three `Number(process.env...)` reads at
`:36`, `:43`, and `:45`.

### S8-04 · The IP cooldown is skipped entirely for callers with no forwarding header, and the header it does read is client-settable

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S8-C4
- **Evidence:** `frontend/src/app/api/faucet/route.ts:65-69`, `frontend/src/app/api/faucet/route.ts:145-150`

**What is wrong.** `clientIp()` (`:65-69`) returns the **leftmost** entry of
`x-forwarded-for`, else `x-real-ip`, else the literal string `"unknown"`. The caller's
guard at `:147` is `if (ip !== "unknown" && now - prevIp < IP_COOLDOWN_MS)` — so a request
carrying neither header gets no IP cooldown at all, and `lastDripByIp.set("unknown", now)`
at `:160` writes a bucket that is never read. Both inputs are ordinary request headers.
The edge in front of this origin is Cloudflare (`server: cloudflare`, and the hostname
resolves to `2606:4700:...` proxy addresses), which publishes the client address in
`cf-connecting-ip` — a header it sets itself and that a client cannot forge. That header
is not read anywhere in the file.

**Proof.** Static, and complete for the owned file — `x-forwarded-for` / `x-real-ip` /
`cf-connecting-ip` appear nowhere else in the route or in the repo's frontend server code:

```
$ grep -rn "x-forwarded-for\|x-real-ip\|cf-connecting-ip" frontend/src
frontend/src/app/api/faucet/route.ts:66:  const fwd = req.headers.get("x-forwarded-for");
frontend/src/app/api/faucet/route.ts:68:  return req.headers.get("x-real-ip") || "unknown";
```

**Not settled here:** whether this specific edge *appends* to a client-supplied
`x-forwarded-for` (making `split(",")[0]` attacker-chosen) or *replaces* it. Settling it
needs one request carrying a forged `X-Forwarded-For` against a reachable origin, and the
origin returns Cloudflare 522 for the duration of this audit. The confirmed half — the
`"unknown"` bypass and the unread unspoofable header — does not depend on that answer.

**Blast radius.** A caller that reaches the origin directly (bypassing the proxy, e.g. by
its origin IP) supplies neither header, gets `"unknown"`, and faces no IP cooldown at all;
combined with fresh pubkeys per S8-02 that is an unthrottled drip loop. If the edge
appends rather than replaces, the same is true through the proxy with a one-line header.

**Suggested remediation.** Read `cf-connecting-ip` first, fall back to the **rightmost**
`x-forwarded-for` entry (the one the trusted hop appended) rather than the leftmost, and
treat an unresolvable client identity as rate-limited rather than exempt — invert `:147`
so `"unknown"` shares a single strict bucket.

### S8-05 · `/api/status` measures RPC reachability, not keeper liveness, and its one freshness field is unread and structurally null

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** S8-C7
- **Evidence:** `frontend/src/app/api/status/route.ts:1-6`, `frontend/src/app/api/status/route.ts:51-81`, `frontend/src/app/api/status/route.ts:83-94`

**What is wrong.** The route documents itself as "base/ER RPC health + settlement indexer
freshness" (`:1-6`). It measures exactly three things (`:87-91`): `getSlot` against the
base upstream, `getSlot` against the ER upstream, and `MAX(settled_at) FROM fills`. The
first two answer only "did this RPC endpoint reply" — both were true throughout the 17-day
K1 outage, because the RPCs were healthy and the *keepers* were dead. Nothing in the route
reads `market.last_mark_price`, `market.last_funding_ts`, or any process-liveness signal,
so the endpoint has no way to express the one condition it exists to surface.

The third signal is the only keeper-freshness measurement present, and it is dead three
times over. (1) `lastFillAt()` collapses "no DB", "unreadable DB", "wrong schema" and
"query threw" into the same `null` (`:66`, `:78-80`) — indistinguishable from a healthy
brand-new deployment that has simply not settled a fill yet. (2) `dbPath()` (`:51-62`)
walks up at most five directories from `process.cwd()` looking for
`keepers/data/fills.db`; on any deployment where the frontend does not share a filesystem
with the keeper — which is what `frontend/vercel.json:2-13` configures — that file cannot
exist, so the field is permanently `null`. (3) No consumer reads it: the sole caller types
the field and never renders it (routed as S8-X02).

**Proof.** The measured surface, and the absence of the DB in the audited tree:

```
$ ls keepers/data/
ls: cannot access 'keepers/data/': No such file or directory
   -> dbPath() returns null -> lastFillAt() returns null (route.ts:66)
   -> GET /api/status yields indexer:{lastFillAt:null} with base.ok / er.ok unaffected

$ grep -rn "lastFillAt" frontend/src
frontend/src/app/api/status/route.ts:6://   -> { base: { ok, slot }, er: { ok, slot }, indexer: { lastFillAt | null } }
frontend/src/app/api/status/route.ts:29:  indexer: { lastFillAt: number | null };
frontend/src/app/api/status/route.ts:64:async function lastFillAt(): Promise<number | null> {
frontend/src/app/api/status/route.ts:90:    lastFillAt(),
frontend/src/app/api/status/route.ts:92:  cached = { base, er, indexer: { lastFillAt: fillTs }, at: Date.now() };
frontend/src/components/trading/status-panel.tsx:39:  indexer: { lastFillAt: number | null };
```

The last line is the only appearance outside the route: a type declaration. There is no
render site.

**Counterweight, stated so the reviewer can weigh it.** The system is not wholly blind to
K1: `frontend/src/components/trading/status-panel.tsx:70-77` derives a "Mark freshness"
row *client-side* by comparing the on-chain mark against the live Pyth stream, and that
row does turn red under K1. The defect filed here is the server half — the endpoint that
claims to report indexer freshness reports none, and reports two green lights instead. If
the reviewer holds that the client-side row discharges the product-level obligation, P2 is
the defensible downgrade.

**Blast radius.** Anyone — operator or user — who reads `/api/status` to answer "is
Slipstream working". Through 17 days of frozen marks and zero settlements it answered with
two `ok: true` layers and a `null` that means "no data" and reads as "nothing wrong". It
is also the only machine-readable health surface in the repo, so it is what any future
uptime monitor would poll, and it would have reported green for the whole outage.

**Suggested remediation.** Add the two on-chain freshness numbers the outage actually
moved — `now - market.last_funding_ts` and the age of `market.last_mark_price` against the
configured Pyth feed — to the payload, and distinguish `lastFillAt: null` (no indexer
reachable) from `lastFillAt: 0` (indexer reachable, no fills) so a caller can tell "not
measured" from "measured, and stale".

### S8-06 · `/api/pyth/history` echoes raw upstream error text to the client, the one thing `PRODUCT.md` forbids

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S8-C2
- **Evidence:** `frontend/src/app/api/pyth/history/route.ts:34-54`, `PRODUCT.md:60`

**What is wrong.** `PRODUCT.md:60` states the rule without qualification: the server "must
never echo raw RPC error text to clients — upstream URLs can carry private keys."
`frontend/src/app/api/pyth/history/route.ts:54` returns
`` errmsg: `benchmarks proxy failed: ${String(lastErr)}` `` — the raw thrown error,
interpolated into the client-visible body. It is the only one of the five routes that does
so: the faucet classifies the message and logs the detail server-side only
(`frontend/src/app/api/faucet/route.ts:221-245`), the RPC proxy does the same
(`frontend/src/app/api/rpc/[layer]/route.ts:52-63`) and says why, `/api/status` returns
`{ok:false}` with no text, and `/api/trades` logs and returns an empty list. The rule was
applied to four routes and missed on the fifth, and the upstream here is operator-supplied
via `PYTH_BENCHMARKS_UPSTREAM` (`:15-17`) exactly like the ones the rule was written for.

**Proof.** `docs/audit/audit-e2e/repro/s8/pyth-history-leak.mjs`, Node v24.10.0. The
common failure modes do **not** leak the URL — an honest negative — but the URL-parse
failure does, and that is the shape a keyed upstream with a stray character produces:

```
$ node docs/audit/audit-e2e/repro/s8/pyth-history-leak.mjs
A1 String(err)            : TypeError: fetch failed
A1 leaks 'SECRET123'?     : false
A2 client-visible body    : {"s":"error","errmsg":"benchmarks proxy failed: TypeError: fetch failed"}

$ node -e 'fetch("https://a b.example/v1?api-key=SECRET123/history").catch(e=>console.log(String(e)))'
TypeError: Failed to parse URL from https://a b.example/v1?api-key=SECRET123/history
```

So the leak is conditional on the upstream string being unparseable once concatenated at
`:30-32`, not on the network failing. A timeout yields `TimeoutError: The operation was
aborted due to timeout` — no URL. The unconditional part is the violation itself: `:54`
places `String(lastErr)` in the response body with no classification, so what reaches the
client is whatever the runtime decided to put in that message.

**Blast radius.** Any unauthenticated caller who can make the upstream fetch throw. Today
the default upstream is the public unkeyed `benchmarks.pyth.network` (`:16-17`) so nothing
secret is behind it — this is P2, a missing defence, not a live leak. Setting
`PYTH_BENCHMARKS_UPSTREAM` to a keyed endpoint, which the env var exists to allow, makes
it exploitable without any code change.

**Suggested remediation.** Replace `:54` with the pattern the other four routes already
use: `console.error("[pyth-history] upstream failed:", lastErr)` server-side, and return a
fixed `{ s: "error", errmsg: "history upstream unavailable" }` to the client.

### S8-07 · `from` and `to` are spliced unencoded and unbounded into the upstream Pyth URL while the neighbouring parameters are encoded

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S8-C5
- **Evidence:** `frontend/src/app/api/pyth/history/route.ts:19-32`

**What is wrong.** The handler reads four query parameters (`:20-24`) and validates
exactly one property of them: that `from` and `to` are non-empty strings (`:26-28`). It
then builds the upstream URL with `encodeURIComponent` on `symbol` and `resolution` and
**raw interpolation** on `from` and `to` (`:30-32`). Two consequences. (a) A caller
controls literal query-string syntax in the request the server makes on its behalf: `&`
appends parameters the route never intended to send. (b) Neither value is parsed as a
number, range-checked, or ordered, so a caller can ask the upstream for an arbitrary span
at arbitrary resolution. The asymmetry inside a single template literal is what makes this
an oversight rather than a decision.

**Proof.** `docs/audit/audit-e2e/repro/s8/pyth-history-leak.mjs`, section B, which builds
the URL with the code copied verbatim from `:30-32`:

```
B benign                   -> .../history?symbol=Crypto.SOL%2FUSD&resolution=60&from=0&to=1
B param injection via &    -> .../history?symbol=Crypto.SOL%2FUSD&resolution=60&from=0&to=1&symbol=Crypto.BTC/USD
B fragment truncation via # -> .../history?symbol=Crypto.SOL%2FUSD&resolution=60&from=0&to=1#
B huge unbounded range     -> .../history?symbol=Crypto.SOL%2FUSD&resolution=60&from=0&to=9007199254740991

B no numeric parse, no range bound, no ordering check on from/to: route.ts:23-28 only
checks both are non-empty strings.
```

Note the injected second `symbol=` sails past the `encodeURIComponent` applied to the
first one, because it rides in on `to`.

**Blast radius.** Unauthenticated. The host is fixed at `:15-17` so this is not SSRF; the
harm is that the route will emit whatever upstream query a caller composes, and will ask a
third-party API for an unbounded candle range on demand — the second free-relay handle on
this origin after S8-01, against a service the project does not own. The rendered chart
also silently becomes a different symbol's data if the upstream honours the last `symbol`.

**Suggested remediation.** Parse both as integers and reject non-finite, negative,
out-of-order, or over-span values before building the URL, then interpolate the parsed
numbers — one `Number.isSafeInteger` guard plus a max-span constant covers all four cases
above.

### S8-08 · The manifest's silent fallbacks cover six fields that `manifestError` never checks, and `manifest.ts` hardcodes the tick/lot/leverage it forbids components from hardcoding

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S8-C8
- **Evidence:** `frontend/src/lib/manifest.ts:92-104`, `frontend/src/lib/manifest.ts:141-151`, `frontend/src/lib/deploy-manifest.generated.json:14-19`

**What is wrong.** Only three fields are guarded. `resolveAddress` (`:59-85`) throws a
descriptive error for `programId`, `market`, and `orderBook`, and `manifestError`
(`:92-104`) drives the visible banner. Everything else degrades in silence:
`USDC_MINT`/`USDC_VAULT` become `null` (`:129-139`), `MARKET_INDEX` becomes `0` (`:141`),
and `TICK_SIZE`/`LOT_SIZE`/`MAX_LEVERAGE` become the literals `1_000n`, `100_000_000n`, and
`20` (`:147-149`) — directly under a comment that reads "Keep these authoritative — do NOT
hardcode tick/lot/leverage in components" (`:144-146`). The rule is stated and broken three
lines apart, in the module that is supposed to be the single source of truth.

Worse, the banner can be suppressed while the fallbacks stay active: `:96-97` returns
`null` from `manifestError` whenever the three *address* env vars are set, regardless of
`__manifestPresent__`. A deployment that points at a new program with
`NEXT_PUBLIC_PROGRAM_ID`/`_MARKET`/`_ORDER_BOOK` therefore gets the old build's
`usdcMint`, `usdcVault`, and `marketIndex`, plus default tick/lot/leverage, with no
warning anywhere.

**Proof.** The generated manifest currently carries all three market params, so the
defaults are dormant — which is exactly the mechanism that keeps this from surfacing:

The hardcoded defaults at `:147-149` happen to equal the live values today, so a stale or

### S8-09 · `/api/trades` reports "no indexer" for three different conditions, and its wallet query sorts an unbounded row set

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S8-C6
- **Evidence:** `frontend/src/app/api/trades/route.ts:50-60`, `frontend/src/app/api/trades/route.ts:68-87`

**What is wrong.** Two hygiene defects in the route's DB half; the injection question
itself is clean (see `## Cleared`). (a) `{ fills: [], indexed: false }` is returned for
"no DB file" (`:58-59`) and identically from the `catch` at `:84-87`, which covers a
corrupt file, a schema mismatch, a locked WAL, and a missing native module. A client
therefore cannot distinguish "the keeper has not started yet" from "the indexer is
broken" — and under K1, with no `keepers/data/` directory in the tree at all, the
former-looking answer is the live one. (b) The wallet query (`:72-75`) is
`WHERE maker = ? OR taker = ? ORDER BY sequence DESC LIMIT ?`. SQLite resolves the OR with
both indexes but must then materialise and sort every matching row before applying the
limit, and `keepers/src/shared/fill-db.ts:14-15` documents retention as unbounded by
default. The caller picks the wallet, so an anonymous request can name the market-maker
bot — a party to nearly every fill — and pay for a full sort of the table with `limit=1`.

**Proof.** Query plans against the schema reconstructed verbatim from
`keepers/src/shared/fill-db.ts:83-97`:

```
EXPLAIN QUERY PLAN for the /api/trades wallet query (route.ts:72-74):
   (6, 0, 0, 'MULTI-INDEX OR')
   (15, 7, 62, 'SEARCH fills USING INDEX idx_fills_maker (maker=?)')
   (28, 20, 62, 'SEARCH fills USING INDEX idx_fills_taker (taker=?)')
   (53, 0, 0, 'USE TEMP B-TREE FOR ORDER BY')      <-- sorts every matching row

EXPLAIN QUERY PLAN for the no-wallet query (route.ts:77):
   (4, 0, 216, 'SCAN fills')                        <-- reverse rowid walk, O(limit), fine
```

The no-wallet path is genuinely cheap: `sequence INTEGER PRIMARY KEY` is the rowid, so
`ORDER BY sequence DESC LIMIT n` stops after n rows. Only the wallet path sorts.

**Blast radius.** Low today — the DB does not exist in this tree, so both paths return the

unbounded per-request work on an unauthenticated route sharing a host with the keepers, and
an operator who cannot tell a broken indexer from an idle one.

**Suggested remediation.** Return a third state — `{ fills: [], indexed: false, error:
"unavailable" }` from the `catch` only — so the two conditions are distinguishable; and
replace the `OR` with a `UNION ALL` of the two index-driven halves, each with its own
`ORDER BY sequence DESC LIMIT ?`, so the sort is bounded by the limit.
