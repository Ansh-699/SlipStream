## Producer contract — S1-C5, the owner-vs-session-key boundary

Published for S2 (`S2-C10`) and S9 (`S9-C1`). This is the definition S1 owns; S2 checks
that `place_order` / `cancel_order` honour it.

**The boundary, as the program actually enforces it.**

1. `TradingCredit.session_authority` / `.session_expiry`
   (`programs/slipstream/src/state/trading_credit.rs:42-45`) are the *only* two fields
   in the whole program that name a non-owner signer. No other state type has a
   delegate, operator, or session field.
2. `authorize_session` (`programs/slipstream/src/instructions/authorize_session.rs:56-61`)
   is the **only** writer of those two fields outside `initialize_trading_credit`
   (which zeroes them, `initialize_trading_credit.rs:73-74`) and
   `delegate_trading_credit` (which sets them in the same transaction as delegation,
   `delegate_trading_credit.rs:181`). Every one of those writers requires
   `owner.is_signer()` **and** `credit.owner == *owner.key()`.
3. `TradingCredit::is_authorized_signer` (`trading_credit.rs:110-117`) is the sole
   consumer. Grep of the whole program: it is called from exactly two sites,
   `place_order.rs:151` and `cancel_order.rs:56`. **No instruction in S1's owned set
   calls it, and no instruction in S1's owned set has any code path that accepts a
   signer other than the account's recorded `owner`.**
4. Every one of the fifteen owned instructions gates on exactly one `is_signer()` check
   and, where program state carries an `owner`/`authority` field, an equality check
   against it. The table is in `## Cleared` under `S1-C1`.

**The contract S2 and S9 may rely on.**

- A session key can never move collateral: no path in `deposit_collateral`,
  `withdraw_collateral`, `fund_trading_credit`, `withdraw_trading_credit`,
  `close_trading_credit`, `close_user_account`, `propose_authority`,
  `accept_authority`, or `set_market_oracle` consults `session_authority`.
- A session key can never rotate itself: `authorize_session.rs:57` compares against
  `credit.owner`, not against `is_authorized_signer`.
- Attribution is never the signer. Nothing in the owned set writes a signer's key into
  an `owner` field; every `owner` field is written once, at init, from the account's
  PDA-deriving signer (`initialize_user.rs:61`, `initialize_position.rs:85`,
  `initialize_trading_credit.rs:70`).

**Two caveats S2/S9 must not assume away.**

- **The expiry ceiling is not enforced on-chain.** `authorize_session` accepts any
  `i64` (see `S1-07`). "Expiring" is a client-chosen property, not a program invariant.
- **The boundary is defined per `TradingCredit`, and `TradingCredit` is the delegated
  account.** Everything the ER can reach is bounded by `credit.credit`, which only
  owner-signed L1 instructions raise (see `## Cleared`, `S1-C8`). S1 confirms the
  ceiling exists; whether the ER honours it is `S2-C11`'s question, not S1's.

## Findings

### S1-01 · Legacy 56-byte TradingCredit accounts are unreachable by every instruction; funded credit and rent are permanently stranded

- **Status:** CONFIRMED
- **Severity:** P0
- **Tag:** [reachable-now]
- **Class:** S1-C7
- **Evidence:** `programs/slipstream/src/state/trading_credit.rs:51-59`, `programs/slipstream/src/instructions/close_trading_credit.rs:54`, `programs/slipstream/src/instructions/withdraw_trading_credit.rs:46`, `programs/slipstream/src/instructions/fund_trading_credit.rs:57`, `programs/slipstream/src/instructions/delegate_trading_credit.rs:118`, `programs/slipstream/src/instructions/close_trading_credit.rs:13-16`

**What is wrong.** `TradingCredit::from_account_info` and its `_mut` sibling reject any
account whose data is shorter than `TradingCredit::LEN` (96 bytes) with
`ProgramError::InvalidAccountData` (`trading_credit.rs:53-55`, `:68-70`). Every single
instruction that touches a `TradingCredit` loads it through one of those two functions —
all 18 load sites, with no exception and no shorter-layout fallback. Accounts created
under the pre-session-keys 56-byte layout are therefore refused by *every* instruction
that could drain, close, delegate, or repair them: `withdraw_trading_credit`,
`close_trading_credit`, `fund_trading_credit`, `delegate_trading_credit`,
`undelegate_trading_credit`, `authorize_session`, `place_order`, `cancel_order`. The
program has no realloc path for a `TradingCredit` (the only `resize` call anywhere is
`propose_authority.rs:92`, on `GlobalState`). The written invariant this violates is
`close_trading_credit.rs:13-16`, which states the instruction exists precisely to
"migrate a legacy (e.g. 56-byte) credit to the new layout: close the old account" — the
one case it is written for is the one case it structurally cannot serve. Nothing
surfaced it because `close_trading_credit` has **zero** test coverage (unit or
integration), and the one verification script that exercises it,
`keepers/src/verify-close.ts:56-70`, creates a *fresh* 96-byte credit first, so it can
never hit the legacy path it claims to prove.

**Proof.** Exhaustive grep of every `TradingCredit` load site — all route through the
96-byte guard:

USDC is 6-decimal, so the frozen balances are 50.00 + 50.00 + 13,163.24 + 50.00 =

**Blast radius.** Four distinct owner wallets (none of them the operator key

already-realised loss of user principal, and it recurs on *every* future change to

both layouts), credit `credit` back to the caller's `UserAccount` and then close. Longer
term, put a layout-version byte in the reserved padding at `trading_credit.rs:34` and
dispatch on it, so a future `LEN` change cannot strand accounts again.

### S1-02 · close_trading_credit destroys a non-zero credit balance, and its own comment claims a recovery path that no code provides

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S1-C7
- **Evidence:** `programs/slipstream/src/instructions/close_trading_credit.rs:27-30`, `programs/slipstream/src/instructions/close_trading_credit.rs:58-72`, `programs/slipstream/src/instructions/fund_trading_credit.rs:61-74`

**What is wrong.** `close_trading_credit` gates on `committed == 0` and
`active_orders == 0` (`:59-61`) but deliberately does **not** gate on `credit == 0`. Its
doc comment (`:27-30`) justifies this: *"this does NOT validate against `credit > 0`
because the credit balance … is independently recoverable via the UserAccount
accounting."* That statement is false. `fund_trading_credit` performs a one-way move —
`user.free_collateral -= amount` and `credit.credit += amount` (`fund_trading_credit.rs:68-74`)
— and the **only** instruction that reverses it is `withdraw_trading_credit`, which reads
the balance out of the credit account itself. Zeroing that account (`:64-67`) destroys
the sole record of the claim while the matching USDC stays in the vault. No path
restores `free_collateral` from a closed credit.

**Proof.** Exhaustive grep of every writer of `free_collateral` in the program — none of
them is a "recover a closed credit" path:

```
$ grep -rn "free_collateral" programs/slipstream/src/ | grep -v '//'
initialize_user.rs:62            = 0                      (creation)
deposit_collateral.rs:84-85      += transferred amount
withdraw_collateral.rs:146-147   -= withdrawn amount
fund_trading_credit.rs:68        -= amount                (the debit in question)
withdraw_trading_credit.rs:61-62 += amount   <- reads credit.credit; needs a LIVE credit account
claim_funding.rs:90-101, close_position.rs:228, liquidate_position.rs:223,
settle_trades.rs:175/195/299/307/452, settle_from_log.rs:197/217   (settlement/funding only)
close_user_account.rs:76         != 0 guard (read only)
```

`close_trading_credit` appears nowhere in that list, and no instruction takes both a
closed-credit witness and a `UserAccount`. Against the live deployment there is one
96-byte credit that satisfies every gate this instruction checks and would be silently
emptied by it:

```
MODERN credit Bkcwr5R4jT2ovN7SyGzFnPQo2bTj7MLR3Ji7x9FsyUiY
  owner=B8QxhmyEdTvXFfmuBTcgBFRMkvb56Y3LioWSz9jyDzYU mkt=0
  credit=500000000 (500.00 USDC)  committed=0  active_orders=0
  -> close_trading_credit gates: program-owned OK, committed==0 OK, active_orders==0 OK
```

**Blast radius.** Anyone holding a funded, idle credit who calls `0x1C` loses that
balance permanently; the USDC stays in the market vault as an unclaimable surplus. Rated
P2 rather than P1 because no third party can trigger it and the only shipped UI caller
gates on `state.legacyCredit` (`frontend/src/hooks/use-session.ts:121-123`), so today it
is only reachable through the SDK (`client/src/instructions.ts:609`) or a hand-built
transaction. The gap is a missing guard whose absence is justified by a false claim, not
a live exploit.

**Suggested remediation.** Either add `if credit.credit != 0 { return Err(CreditStillActive) }`
next to the existing idle gates at `close_trading_credit.rs:59`, or take the
`UserAccount` as a fourth account and fold the remaining balance back into
`free_collateral` before zeroing. Delete the recoverability claim at `:27-30` either way.

### S1-03 · deposit_collateral and withdraw_collateral read a Market without pinning its canonical PDA, contradicting the invariant asserted in place_order

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S1-C4
- **Evidence:** `programs/slipstream/src/instructions/withdraw_collateral.rs:51-59`, `programs/slipstream/src/instructions/deposit_collateral.rs:65-73`, `programs/slipstream/src/instructions/place_order.rs:104-120`, `programs/slipstream/src/instructions/withdraw_trading_credit.rs:38-49`, `programs/slipstream/src/instructions/authorize_session.rs:48-57`

**What is wrong.** `place_order.rs:104-108` records the invariant explicitly: *"Every
other instruction that reads a Market pins it; this one didn't"* — followed by the fix,
a `find_program_address(&[SEED_MARKET, market_index])` equality check. The claim is
false. `deposit_collateral` and `withdraw_collateral` both check only
`market_acc.owner() == program_id` plus the `DISC_MARKET` byte and then read
`market.quote_vault` out of it (`withdraw_collateral.rs:51-58`,
`deposit_collateral.rs:65-72`); neither derives `SEED_MARKET`. `withdraw_collateral` is
the *only* instruction in the program that moves tokens out of the vault, and the
account it trusts to name the source vault is the unpinned one. Separately, five owned
instructions mutate a `UserAccount` or `TradingCredit` without ever deriving its PDA,
relying entirely on the recorded `owner` field:
`fund_trading_credit.rs:49-60`, `withdraw_trading_credit.rs:38-49`,
`authorize_session.rs:48-57`, `close_trading_credit.rs:50-57`,
`close_user_account.rs:60-75`.

**Proof.** Mechanical check of which `Market` readers derive `SEED_MARKET`:

```

    echo "$(basename $f)  SEED_MARKET=$(grep -c SEED_MARKET $f)"; done
# (13 output lines, reflowed into two columns and annotated)
initialize_market.rs   SEED_MARKET=3      claim_funding.rs      SEED_MARKET=2
set_market_oracle.rs   SEED_MARKET=2      close_position.rs     SEED_MARKET=2
settle_trades.rs       SEED_MARKET=2      liquidate_position.rs SEED_MARKET=2
place_order.rs         SEED_MARKET=2      settle_from_log.rs    SEED_MARKET=2

withdraw_collateral.rs SEED_MARKET=0   <- NOT pinned (owned, this finding)
```

Why it is P2 and not P0 today: a forged `Market` is not constructible. `initialize_market`
is the sole creator, is `GlobalState.authority`-gated (`initialize_market.rs:42-65`) and
pins the market PDA (`:96-102`), so the set of `DISC_MARKET` accounts equals the set of
canonical market PDAs. The live deployment has exactly one:

```
GlobalState hyPv4sWbkHPyrVa5zFHkiuqBLCmZdAiZeupieXrEEcL  market_count=1  paused=0
getProgramAccounts dataSize=2064 disc=2 -> 1 account (ECUp8pXz…, market_index=0)
```

The bound is therefore "there is currently only one market," which is exactly the
environment change the P2 bar names.

**Blast radius.** With a second market live, a user could withdraw against market *B*'s
`quote_vault` using `free_collateral` they deposited into market *A*'s vault — the
`UserAccount.free_collateral` pot is global (`user_account.rs:14`) while `quote_vault`
is per-market (`market.rs` `quote_vault`), and nothing in `withdraw_collateral` ties the
market they pass to the market they deposited through. Vault segregation between markets
is not enforced anywhere. The `UserAccount`/`TradingCredit` half is defence-in-depth only:
those `owner` fields are written once from a PDA-deriving signer, so substitution buys an
attacker nothing today.

**Suggested remediation.** Add the same three lines `place_order.rs:114-120` already has
to `deposit_collateral` and `withdraw_collateral`. If cross-market vault segregation is
intended, `withdraw_collateral` additionally needs per-market collateral accounting, not
just a PDA pin — that is a design decision, not a patch. Correct or delete the false
claim at `place_order.rs:107`.

### S1-04 · The global pause is a one-way switch with no clearing instruction, and mod.rs documents a coverage map the program does not have

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S1-C10
- **Evidence:** `programs/slipstream/src/instructions/mod.rs:169-176`, `programs/slipstream/src/instructions/mod.rs:103-166`, `programs/slipstream/src/instructions/initialize_global.rs:71`, `programs/slipstream/src/state/global_state.rs:12`, `programs/slipstream/src/instructions/withdraw_collateral.rs:77-80`

**What is wrong.** Two defects in one mechanism.
*(a) No unpause.* `GlobalState.paused` (`global_state.rs:12`) has exactly two writers in
the entire program: `initialize_global.rs:71` sets it to `0` at creation, and
`emergency_undelegate.rs:141` sets it to `1`. The dispatcher at `mod.rs:103-166` lists
all 41 instructions; none of them clears the flag. Once armed, the protocol is halted
permanently with no on-chain remedy short of a program upgrade. Because
`settle_trades.rs:81` and `settle_from_log.rs:60` are both gated on the flag, a pause
also freezes settlement, so `UserAccount.pending_fills` can never drain — and
`withdraw_collateral.rs:78-80` refuses any withdrawal while `pending_fills > 0`. A pause
therefore does not merely stop trading; it makes every user's collateral unwithdrawable
for as long as it lasts, which is forever.
*(b) The documented coverage map is wrong.* `mod.rs:169-170` states *"Non-trivial
trading instructions (place/cancel/settle/liquidate/funding) call this before mutating
state."* Three of the five named categories do not.

**Proof.** Exhaustive grep of call sites and of every write to `paused`:


Live devnet confirms the flag is currently clear, so nothing is halted today:

```
  dataLen=104 disc=1 market_count=1 paused=0 authority=A5sV4PkkVM4gm3rejACvKFgxEMmj8ouGsffSKT5qYVc8
```

**Blast radius.** P2 rather than P1 because the single writer of `paused = 1` is itself
currently unreachable — `emergency_undelegate.rs:25-36` documents that its magic-program
CPI and its `GlobalState` write require mutually exclusive layers, so the instruction
cannot complete on either. That is a documented limitation and is not re-reported here;
what is *not* documented is that if it ever were fixed as written, the first successful
call would strand every user's collateral permanently. The coverage-map half is a
correctness gap in a safety control's own documentation: an operator reading
`mod.rs:169-170` would believe a pause stops liquidations and funding accrual, and it
does not.

**Suggested remediation.** Add an authority-gated `set_pause(bool)` instruction to the
dispatcher and have `emergency_undelegate` use it, so pause is reversible before it is
ever reachable. Then either extend `ensure_not_globally_paused` to the instructions the
comment names, or rewrite the comment at `mod.rs:169-170` to state the real, deliberate
map (deposits and new orders pause; exits, cancels, liquidations and settlement do not).

### S1-05 · initialize_market records quote_vault with no validation, and Market.quote_mint is written all-zero and never read

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S1-C12
- **Evidence:** `programs/slipstream/src/instructions/initialize_market.rs:167-170`, `programs/slipstream/src/instructions/deposit_collateral.rs:59-73`, `programs/slipstream/src/instructions/withdraw_collateral.rs:127-143`, `programs/slipstream/src/state/market.rs:1-30`

**What is wrong.** `initialize_market` copies `*quote_vault_acc.key()` into
`market.quote_vault` (`:170`) after performing **no** checks on that account at all: not
