## Findings

### S9-01 · The withdraw idle-gate blocks the only instruction that can clear the state it blocks on

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S9-C7` — Withdrawal precondition gating
- **Evidence:** `frontend/src/hooks/use-session.ts:786-791`, `frontend/src/hooks/use-session.ts:802`, `programs/slipstream/src/instructions/undelegate_trading_credit.rs:40-48`, `programs/slipstream/src/instructions/undelegate_trading_credit.rs:97`, `tests/unit/src/test_trading_credit.rs:94-96`, `PRODUCT.md:58`

**What is wrong.** `PRODUCT.md:58` requires withdrawal to be gated on an idle account
"with a clear instruction rather than silently failing." `withdraw()` implements that
gate at `use-session.ts:786` by reading `TradingCredit.activeOrders` / `.committed`
and returning early. But the program's own documentation says those two fields go
**stale** exactly when a maker's resting order is filled by someone else's taker: the
maker's credit is not a tx account on that fill, so nothing decrements it
(`trading_credit.rs:20-26`). `undelegate_trading_credit.rs:40-48` states outright that
its `reconcile_credit` call exists so that the stale copy does not "show a stale
nonzero committed/active_orders forever — permanently failing
`withdraw_trading_credit`'s `is_idle()` gate." The client gate sits **16 lines above**
the `createUndelegateTradingCreditInstruction` call (`use-session.ts:802`) and returns
before reaching it, so the user can never run the reconcile that would clear the gate.
The message compounds it: it names only `activeOrders`, so the `committed > 0,
activeOrders == 0` leg — the leg `PRODUCT.md:58` names explicitly as "no committed
margin" — renders as *"Cancel your 0 open orders before withdrawing."*

**Proof.** `docs/audit/audit-e2e/repro/s9/withdraw-gate.mjs` — mechanical assertions
over the frozen tree plus the rendered message text:

```

  error message                 : line 788

  -> gate precedes undelegate by 16 lines and returns early: CONFIRMED

  authors' own rationale        :
    40: /// After this instruction, the TradingCredit is owned by the program again and the
    41: /// user can `withdraw_trading_credit`. `committed`/`active_orders` are reconciled
    42: /// against the (also ER-delegated) order book before the commit below: a maker
    43: /// whose resting order was filled by someone else never gets an ER-side
    44: /// reconcile of their own (that only happens as a side effect of the OWNER's
    45: /// own place_order/cancel_order calls), so without this the committed L1 copy
    46: /// could show a stale nonzero committed/active_orders forever — permanently
    47: /// failing withdraw_trading_credit's `is_idle()` gate for an order that has
    48: /// nothing left reserved.

so the Open Orders panel shows nothing to cancel while the gate demands a cancel.

The stale state is not hypothetical: `tests/unit/src/test_trading_credit.rs:87-105`
constructs it (`committed = 500` and `active_orders = 1` with **zero active slots for
that owner**) precisely to test that `reconcile_credit` repairs it.

**Blast radius.** Any user who rests a limit order that another account fills. Their
entire `TradingCredit` balance becomes unreachable through the UI: Withdraw refuses,
and the Open Orders panel — which reads `book.orderSlots`, not the credit
(`use-open-orders.ts:68`) — shows nothing to cancel, so the instruction the error gives
cannot be followed. There is an undocumented escape (placing any new order runs
`reconcile_credit` at `place_order.rs:198`), but nothing in the UI says so. On mainnet
this is a user's real margin stranded behind a client-side check; on devnet it is the
same path with worthless tokens. Nothing surfaced it because the devnet book has not
matched a fill since the keepers died (K1/K4), so no maker has been filled in 16 days.

**Suggested remediation.** Move the idle check to *after* the undelegate leg (or drop
it and let `withdraw_trading_credit`'s on-chain `is_idle()` be the gate), since
undelegating is what reconciles. If a pre-check is kept, gate it on the owner's active
slot count read from the order book rather than the credit's stale counter, and give
`committed > 0 && activeOrders == 0` its own message.

### S9-02 · The order-book hooks silently fall back to an L1 copy that is documented as never committed, and label it "live"

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S9-C5` — Async correctness
- **Evidence:** `frontend/src/hooks/use-orderbook.ts:84-87`, `frontend/src/hooks/use-orderbook.ts:115`, `frontend/src/hooks/use-orderbook.ts:31-36`, `frontend/src/hooks/use-open-orders.ts:56-59`, `frontend/src/hooks/use-er-position.ts:176-179`, `docs/03-ephemeral-rollups-and-delegation.md:172`

**What is wrong.** All three book-reading hooks try the ER and fall back to the base
layer when the ER read throws. `docs/03-ephemeral-rollups-and-delegation.md:172` states
the 612 KB OrderBook is "delegated once forever — never committed, never undelegated",
so the L1 copy is frozen at its state at delegation time and can never advance. It
still carries a valid discriminator, so `decodeOrderBook` accepts it and
`use-orderbook.ts:115` sets `status: "live"` with `updatedAt: Date.now()`. That directly
contradicts the hook's own docstring at `use-orderbook.ts:31-36`, which says rendering
an ambiguous book state as one thing "is a lie" and is why the status enum exists at
all — the enum has a `"stale"` value but it is only reachable from the `catch`
(`:118-126`), never from the fallback. `use-open-orders.ts:56-59` has no status field
whatsoever: the fallback returns whichever orders were resting at delegation time and
omits the user's real ER orders, indistinguishable from "you have none".
`use-er-position.ts:176-179` replays a fill ring that stopped at sequence 10.

**Proof.** Live read of both layers, `docs/audit/audit-e2e/repro/s9/er-vs-l1-book.sh`
(read-only RPC, no signer):

```
$ bash docs/audit/audit-e2e/repro/s9/er-vs-l1-book.sh
OrderBook 83zMFL6cHjgXkQ7KRNcgtHaZ1fhyNgxhM8aMpPpEnMqe — header read at 2026-08-21T19:24:43Z
L1: owner=DELeGGvXpWV2fqJUhqcF5ZSYMS4JTLjteaAMARRSaeSh
    disc=5 activeOrderCount=11 bidLevelCount=3 askLevelCount=3 fillEventCount=9 nextOrderId=26 nextFillSequence=10
ER: owner=7qujfsb4ZPbQHYVZdqiXq1r8tVAMyyukX94obPqXbVwz
    disc=5 activeOrderCount=12 bidLevelCount=6 askLevelCount=6 fillEventCount=4096 nextOrderId=765434 nextFillSequence=44190
```

The L1 copy the fallback reaches is **44,180 fill sequences and 765,408 order ids
behind** the ER copy, and it decodes cleanly (`disc=5`), so nothing in the hook can tell
the two apart. Address from `frontend/src/lib/deploy-manifest.generated.json`; header
layout from `frontend/src/lib/slipstream/accounts.ts:374-398`.

**Blast radius.** Every viewer of `/trade` during any ER or `/api/rpc/er` proxy
failure — the same same-origin proxy path implicated in K1's quota exhaustion. They see
a depth ladder, a trade tape, an open-orders list and a pending position that are all
presented as current and are in fact a snapshot from delegation. A trader who acts on
that ladder prices against a book that has moved 44k fills. `PRODUCT.md` Principle 1
("every claim on screen traces to something a reader can check") makes this a
correctness defect, not a display one, and the mislabelling is what makes it worse than
showing nothing.

**Suggested remediation.** Do not fall back for the order book: it is the one account
whose base-layer copy is known to be meaningless. Either drop the base-layer branch in
all three hooks and return `status: "unavailable"`, or keep it and mark the result
`"stale"` with the header's `nextFillSequence` as the staleness evidence. Give
`useOpenOrders` the same status enum the other two have.

### S9-03 · The terminal issues 9.33 unbounded, undeduplicated RPC round trips per second per tab, with no backoff on failure

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S9-C5` — Async correctness
- **Evidence:** `frontend/src/hooks/use-session.ts:402-406`, `frontend/src/hooks/use-session.ts:325-335`, `frontend/src/hooks/use-session.ts:361-371`, `frontend/src/hooks/use-market.ts:87-91`, `frontend/src/hooks/use-orderbook.ts:129-133`, `frontend/src/hooks/use-er-position.ts:207-211`, `frontend/src/hooks/use-positions.ts:119-123`, `frontend/src/hooks/use-triggers.ts:51-55`

**What is wrong.** Every polled hook is `setInterval(fetch, N)` with a bare `catch {}`
and nothing else: no in-flight guard, no `AbortController`, no backoff, no shared
instance. Three consequences compound. (1) **Duplication** — hooks are called
per-component, so one render mounts 4 `useMarket`, 3 `useSession`, 3 `useOrderBook` and
4 `useLivePrice` WebSockets, each with its own timer over the same account. (2)
**Redundancy within a tick** — `useSession.refresh` reads the *same* ER credit PDA twice
per tick, from two freshly constructed `Connection` objects (`:325-335` and `:361-371`).
(3) **No back-pressure** — a failing or rate-limited RPC is swallowed and the next tick
fires on the same period, so slow responses overlap and the request rate rises exactly
when the endpoint is least able to serve it. The spec's own `S9-C5` names "unbounded
polling that contributes to K1's quota problem"; K1's root-cause chain is public devnet
RPC quota exhaustion, and the browser reaches that same endpoint through
`/api/rpc/base`. I do **not** claim the frontend caused K1 — I have no per-client
attribution — only that its request rate is unbounded by construction and measured
below.

**Proof.** `docs/audit/audit-e2e/repro/s9/poll-budget.mjs` derives the period, the
per-tick RPC count and the mount count from source, and asserts the absence of every
back-pressure mechanism:

```

single most expensive call in the set — and `use-open-orders.ts` adds a further 1.00
req/s whenever the Orders tab is selected.

**Blast radius.** The whole deployment, and anything else sharing the endpoint. Ten
concurrent viewers is ~93 requests/second against `api.devnet.solana.com` plus 40 ER
sockets, with the rate rising rather than falling as the endpoint degrades. The keepers
share that endpoint and died of quota exhaustion. On mainnet this is a per-viewer RPC
bill that scales with tab count rather than with information, and a self-reinforcing
outage under any provider throttle.

**Suggested remediation.** Hoist each hook's state into one provider/store per account
so N components share one poller; add an in-flight guard plus exponential backoff on
error to every interval; drop the duplicated ER read in `refresh` and reuse one ER
`Connection` module-wide, as `use-wallet-compat.ts:30-32` already does for the base
layer.

### S9-04 · The session key's 64-byte secret is persisted to `localStorage` and never cleared, while the docs say it is held in memory

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** `S9-C1` — Session-key custody
- **Evidence:** `frontend/src/hooks/use-session.ts:158-173`, `frontend/src/hooks/use-session.ts:148-151`, `docs/06-session-keys.md:111`, `README.md:229`

**What is wrong.** `docs/06-session-keys.md:111` states the frontend "keeps the session
key **in memory** to auto-sign ER orders." It does not: `storeSession` writes
`Array.from(keypair.secretKey)` — the full 64-byte ed25519 secret — as a JSON array
into `window.localStorage` under `slipstream:session:<owner>:<market>`
(`use-session.ts:138-140`, `:165-172`). Nothing ever removes it. A repo-wide grep finds
no `removeItem`, no clear-on-disconnect, and no clear-on-expiry: an expired key's secret
bytes stay on disk indefinitely, and switching or disconnecting the wallet leaves the
previous owner's key in place. The written invariant that *is* upheld —
`README.md:229`, "the session key can only place and cancel orders" — holds (see
`## Cleared`, `S9-C1`), which is why this is P2 and not higher: the leak radius is order
churn inside one credit, not the vault.

**Blast radius.** Anyone with read access to the browser profile — a shared or kiosk

so that bound is being reasoned about against the wrong premise.

wallet disconnect, on owner change, and when `loadStoredSession` observes an expired
entry. Then correct `docs/06-session-keys.md:111` to whichever is chosen (routed as
`S9-X03`).

### S9-05 · The docs renderer pipes unsanitized `marked` output into `dangerouslySetInnerHTML` on the origin that holds the session secret, with no CSP

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** `S9-C2` — XSS reachability of the session key
- **Evidence:** `frontend/src/lib/docs.ts:97`, `frontend/src/app/docs/page.tsx:12`, `frontend/src/app/docs/[slug]/page.tsx:24`, `frontend/src/hooks/use-session.ts:169`, `frontend/next.config.ts:3-5`

**What is wrong.** `getDoc` renders markdown with `marked.parse` and returns the raw
string (`docs.ts:97`); both doc routes inject it with `dangerouslySetInnerHTML`
(`docs/page.tsx:12`, `docs/[slug]/page.tsx:24`). `marked` v14 does not sanitize — the
`sanitize` option was removed in v5 and the project ships no sanitizer, so raw HTML in a
source markdown file reaches the DOM verbatim. That is defensible on its own because
the input is build-time repo content copied by `frontend/scripts/copy-docs.mjs`, not
user input. What makes it a finding is the *composition*: this renderer shares an origin
with a plaintext ed25519 secret in `localStorage` (`use-session.ts:169`), and there is no
Content-Security-Policy anywhere in the deployment to contain a script if one ever does
execute. The answer to `S9-C2`'s question — "if a script runs on the origin, does it get
the key?" — is unambiguously yes, with no second line of defence.

**Proof.**

```
$ grep -rniE "dompurify|sanitize|Content-Security-Policy" frontend/src frontend/next.config.ts frontend/vercel.json frontend/package.json; echo "exit=$?"
exit=1

$ grep -rn "dangerouslySetInnerHTML" frontend/src
frontend/src/app/layout.tsx:60:          dangerouslySetInnerHTML={{

```

Zero matches for any sanitizer or any CSP declaration across the frontend source, the
Next config, the Vercel config and the manifest. `frontend/next.config.ts:3-5` is an
empty config object with no `headers()`. The mermaid runner is the one place that is
already hardened — `mermaid-runner.tsx:39` sets `securityLevel: "strict"` and
`docs.ts:89-92` hand-escapes `&`, `<`, `>` before building the `<pre class="mermaid">`
block — which is why this finding is about the markdown path only.

**Blast radius.** P2 today because no attacker-controlled input reaches `marked`: the
only sources are the ten files under `frontend/src/content/docs/`, and `slugToFile`
matches the request slug against `readdirSync` basenames rather than joining it into a
path (`docs.ts:51-58`), so there is no traversal. It becomes P1 the moment any
user-supplied or externally-fetched markdown is rendered through the same helper, or if
a third-party script on the page is compromised — the spec's own `S9-C2` text calls a
stored session key plus a docs-renderer XSS "a P1 chain even on devnet."

**Suggested remediation.** Sanitize `getDoc`'s output (DOMPurify or `marked`'s
`walkTokens` with an allowlist) so the pipeline is safe by construction rather than by
provenance, and add a Content-Security-Policy via `next.config.ts`'s `headers()` — a
`script-src` without `unsafe-inline` would also need `layout.tsx:60`'s inline theme
script nonced. The CSP half is routed to S10 as `S9-X01`.

### S9-06 · `getSessionKeypair`'s contract claims an on-chain authority check it does not perform

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** `S9-C1` — Session-key custody
- **Evidence:** `frontend/src/hooks/use-session.ts:230-243`, `frontend/src/hooks/use-session.ts:375-378`, `frontend/src/components/trading/order-form.tsx:153-155`

**What is wrong.** The docstring at `use-session.ts:231-235` states the function returns
the keypair "IFF it is still valid: it exists, has not expired locally, **and matches

### S9-07 · `waitForUndelegation` charges RPC failures against its retry budget and reports them as the rollup withholding funds

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** `S9-C6` — Undelegation polling
- **Evidence:** `frontend/src/hooks/use-session.ts:184-200`, `frontend/src/hooks/use-session.ts:815-821`, `PRODUCT.md:43`

**What is wrong.** `PRODUCT.md:43` requires the UI to poll for the asynchronous
ownership flip rather than assume it, and `waitForUndelegation` does exactly that —
30 attempts, 2 s apart, checking `info.owner == PROGRAM_ID` on the base layer. The gap
is in how it fails. Its `catch` at `:194-196` swallows every RPC error and lets the loop
continue, so a transient outage consumes tries from the same 30-attempt budget as a slow
rollup. Thirty consecutive RPC failures therefore exhaust the budget in ~60 s and the
caller reports *"The rollup hasn't handed your funds back yet"* (`:817-819`) — blaming
MagicBlock for what was a devnet RPC problem. Under K1's exact live condition
(quota-exhausted public devnet RPC) that is the misattribution the user will actually
see. The function also cannot distinguish "still settling" from K5's permanent
half-delegated deadlock; both produce the same "give it a moment and press Withdraw
again", which is advice that can never succeed in the K5 case.

**Proof.**

```
$ sed -n '190,199p' frontend/src/hooks/use-session.ts
  for (let i = 0; i < tries; i++) {
    try {
      const info = await conn.getAccountInfo(creditPda, "confirmed");
      if (info && info.owner.toBase58() === programId) return true;
    } catch {
      /* transient RPC error — keep polling */
    }
    await new Promise((r) => setTimeout(r, 2_000));
  }
  return false;
```

The `catch` records nothing; `i` advances identically for a successful "not yet" and for
a thrown request. `waitForUndelegation` returns a bare `boolean`
(`use-session.ts:187-188`), so the caller has no channel to distinguish the two even if
it wanted to.

**Blast radius.** A user mid-withdrawal during any RPC blip is told the rollup is
holding their funds. Funds are not at risk — the undelegate has already been scheduled
on-chain and a later retry succeeds — but the message points the user (and any support
process) at the wrong system, and in the K5 deadlock it advises an action that can never
work. P3 rather than P1 because the withdrawal path itself still completes on retry.

**Suggested remediation.** Count consecutive RPC errors separately from "not flipped
yet", and return a discriminated result (`"flipped" | "timeout" | "rpc-unavailable"`) so
`withdraw()` can say which happened. Cap total wall-clock time instead of attempt count,
and after a timeout report the credit's current L1 owner so a K5 deadlock is
distinguishable from a slow flip.

### S9-08 · `humanizeError`'s `/0x1/` pattern matches every Slipstream program error, so any of them is reported as a USDC balance shortfall

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** `S9-C4` — Transaction construction and signing UX
- **Evidence:** `frontend/src/hooks/use-session.ts:87-89`, `programs/slipstream/src/error.rs:5`, `frontend/src/hooks/use-session.ts:76-97`

**What is wrong.** `humanizeError` classifies a failure by regex over the error message
plus the transaction logs. The third rule, `if (/0x1|insufficient/i.test(hay) &&
/transfer/i.test(hay))`, returns *"USDC transfer failed — your balance is lower than the
deposit amount."* `SlipstreamError` starts at `0x100` (`error.rs:5`) and has 56 sequential
variants, so every custom error the program can return renders as `0x100`…`0x137` — all
of which contain the substring `0x1`. Every transaction that `use-session.ts` builds for
`initialize` or `withdraw` includes an SPL token transfer, so `Instruction: Transfer`
is always in the logs and the second conjunct is always true. The result: **every**
program-level rejection on the money path is reported to the user as a balance
shortfall.

**Proof.**

```
$ V=$(awk '/^pub enum SlipstreamError/{f=1;next} /^}/{f=0} f' programs/slipstream/src/error.rs | grep -cE '^\s+[A-Z][A-Za-z0-9]*\s*(=|,)'); echo "variants: $V"
variants: 56
$ python3 -c "print('first = 0x%X, last = 0x%X' % (0x100, 0x100+56-1)); print('all render with the prefix 0x1:', all(('0x%x'%c).startswith('0x1') for c in range(0x100,0x100+56)))"

$ node -e '...replay of the use-session.ts:87 predicate against real error strings...'

CreditStillActive          custom program error: 0x129  -> humanizeError says: "USDC transfer failed - your balance is lower than the deposit amount."

```

(The two earlier rules at `:81` and `:84` intercept genuine lamport/ATA problems first,
so the rule only ever fires on cases it then misdescribes.)

**Blast radius.** Every user who hits any program rejection during deposit, funding or
withdrawal. Most damaging in combination with `S9-01`: a `CreditStillActive` on withdraw
tells the user their USDC balance is too low, steering them away from the actual stale
`committed` condition. No funds move incorrectly; the harm is that the UI's only
diagnostic actively misdirects. P3 rather than P1 because no on-chain state or displayed
figure is wrong, only the explanation.

**Suggested remediation.** Anchor the pattern to a whole error code
(`/custom program error: (0x[0-9a-f]+)/`) and map the captured code through the
`SlipstreamError` enum, falling through to the raw message for anything unmapped;
reserve the balance-shortfall wording for the SPL token error `0x1` alone.

- **Class:** `S13-C1`
