### S11-01 · No test in the runnable suite ever issues the same instruction twice, so exactly-once settlement is asserted nowhere

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S11-C3
- **Evidence:** `tests/unit/src/test_settle_trades_regressions.rs:148-236`, `tests/unit/src/test_mirror_fills_regressions.rs:137-183`, `tests/unit/src/test_record_pending_fill_regressions.rs:93-134`, `programs/slipstream/src/instructions/mod.rs:84-88`

**What is wrong.** The written invariant is the spec's own statement of S4's interface —
"exactly-once settlement: every fill lands on L1 once, in order, with the same numbers it
had in the ER" (`docs/spec/audit-e2e.md:668-669`). A double-settle or replay defect is by
construction only observable across **two** submissions of the same instruction against
the state the first one left. Across all 98 tests in `tests/unit/src/` there are 40
`process_instruction` calls; exactly two tests submit more than one instruction, and both
of those submit two *different* discriminators (`0x26` then `0x27`,
`tests/unit/src/test_authority_rotation.rs:51`, `:83`). No test anywhere submits the same
discriminator twice. The three settlement instructions are each driven exactly once and
then the harness is discarded, so `last_mirrored_sequence`, the FillLog `head`/`count`
cursor and `UserAccount.pending_fills` are never observed across a second call.

**Proof.**

```
$ python3 docs/audit/audit-e2e/repro/s11/replay_probe.py
  tests/unit/src/test_authority_rotation.rs::test_propose_then_accept_rotates_authority calls=2 discs=['26', '27']
  tests/unit/src/test_authority_rotation.rs::test_accept_authority_rejects_wrong_signer calls=2 discs=['26', '27']

#[test] fns                              : 98
total process_instruction calls          : 40
tests issuing MORE THAN ONE instruction  : 2
tests issuing the SAME instruction twice : 0
```

**Blast radius.** Everyone who trades. This is the single blind spot that let the whole
S4 cluster ship green: `S4-01` (P0, a fill settled zero times,
`docs/audit/audit-e2e/s4.md:65`), `S4-04` (P0, `pending_fills` has no reset path and is
already blocking 438,643 USDC on devnet, `docs/audit/audit-e2e/s4.md:251`), `S4-07` (P1,
one commit settled repeatedly inside a single call, `docs/audit/audit-e2e/s4.md:441`) and
`S4-02` (P1, a rotated epoch re-mirrors already-settled fills,
`docs/audit/audit-e2e/s4.md:143`) are all defects a second submission would have surfaced
and a first submission cannot. On mainnet each is a direct credit of value that was never
debited, or a permanent freeze of collateral.

**Suggested remediation.** Add one Mollusk test per settlement stage that calls
`process_instruction`, feeds `res.resulting_accounts` straight back in as the account set,
calls it again with the identical instruction, and asserts the second call is either
rejected or a no-op — for `record_pending_fill` (0x14), `mirror_fills` (0x1F),
`settle_trades` (0x04) and `settle_from_log` (0x21).

### S11-02 · Twenty-four of the forty instructions are never executed by any test, including the credit money path and `settle_from_log`

- **Class:** S11-C1

**What is wrong.** `PRODUCT.md:82` offers "123 passing Rust tests (25 unit + 98 Mollusk)
as the regression baseline". Sixteen of the forty declared instruction discriminators are
ever driven through the compiled program; the other twenty-four have no in-SVM coverage
at all. `tests/unit/src/lib.rs:5` and `tests/unit/src/test_instructions_simple.rs:2` both
say the missing coverage lives in `tests/integration/` — a suite CI never runs (spec K8,
`docs/spec/audit-e2e.md:401-403`), so the pointer resolves to nothing. Per the class rule in
`docs/spec/audit-e2e.md:1230-1234` this is filed at P2 rather than P3 because three of the

`docs/audit/audit-e2e/s1.md:1`) through `initialize_trading_credit` (0x0D). `S3-05`

**Suggested remediation.** Add one Mollusk test per uncovered value-moving instruction,
starting with the three withdraw/settle-path rows (0x13, 0x1C, 0x21), then 0x0E and 0x07.
Where the harness cannot reach the success path (see S11-04), a negative test that reaches
the last check before the CPI is still worth more than nothing, and the file should say so
in a comment the way `tests/unit/src/test_withdraw_collateral_regressions.rs:59` already
does.

### S11-03 · The ER trust boundary — the product's central claim — is asserted by no test on either layer

- **Status:** CONFIRMED
- **Severity:** P2
- **Class:** S11-C8
- **Evidence:** `tests/unit/src/lib.rs:1-6`, `tests/unit/src/test_instructions_simple.rs:19-20`, `tests/unit/src/test_order_book.rs:272`, `tests/unit/src/test_global_pause.rs:6`

**What is wrong.** `PRODUCT.md:38` sells the system on "a misbehaving ER can at worst
scramble order ordering or misuse an already-capped credit allowance. It can never reach
the vault or an undelegated balance." `S5-C1` establishes that the property holds because
exactly three `Assign`-to-delegation-program sites exist and each is PDA-pinned
(`docs/audit/audit-e2e/s5.md:30-52`). Nothing in `tests/unit/src/` executes any of the
nine delegation-lifecycle instructions, and the delegation program id appears in the test
crate zero times — the only mentions of delegation anywhere in the suite are two constant
equality assertions (`tests/unit/src/test_instructions_simple.rs:19-20`) and two prose
comments (`tests/unit/src/test_order_book.rs:272`, `tests/unit/src/test_global_pause.rs:6`).
Separately, the pinning that makes the claim true is spread over **thirteen** hardcoded
32-byte literals in eight instruction files — `DELEGATION_PROGRAM_ID` three times,
`MAGIC_PROGRAM_ID` and `MAGIC_CONTEXT_ID` five times each. They all agree today. No test
asserts that they agree, so a one-byte edit to any single copy would repoint one
delegation or commit CPI at a decoy program with a green suite.

**Proof.**

**Blast radius.** Everyone. This is the property the whole architecture is justified by,
and it is the one property with no automated evidence at all — S5 had to establish it by
grep during this audit rather than by pointing at a test. On mainnet, a regression that
widened the delegation inventory to `Position`, `UserAccount` or `Market` would reach
production with a fully green CI, and so would a mistyped decoy program id in any one of
the thirteen copies.

**Suggested remediation.** Two cheap tests, both pure-Rust and neither needing an ER:
(1) a test that asserts the three `DELEGATION_PROGRAM_ID` copies and the five
`MAGIC_PROGRAM_ID` / `MAGIC_CONTEXT_ID` copies are byte-equal to a single canonical
constant — this requires making them `pub(crate)` in one module; (2) a Mollusk test per
delegate instruction that passes a *wrong* delegation-program account and asserts
rejection, which needs no CPI to succeed because the pin check runs first
(`programs/slipstream/src/instructions/delegate_orderbook.rs:112`).

### S11-04 · The harness ceiling is real and written down nowhere: Mollusk here loads no token program and no delegation program, so no successful vault transfer is executable by any test

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S11-C7
- **Evidence:** `tests/unit/src/test_close_position.rs:21-27`, `tests/unit/src/test_withdraw_collateral_regressions.rs:59`, `tests/unit/src/test_withdraw_collateral_regressions.rs:153-253`, `tests/unit/src/lib.rs:1-6`

**What is wrong.** Every Mollusk file builds its harness with the same six-line helper —
`Mollusk::new(program_id, "slipstream")` and nothing else
(`tests/unit/src/test_close_position.rs:21-27` and fifteen siblings). `mollusk-svm` 0.12's
default builtin set is exactly the System program plus the v2 and v3 BPF loaders; SPL
Token, the MagicBlock delegation program and the magic program are absent, and the test
crate never calls `add_program` and never enables the `all-builtins` feature. **This
bounds what the entire suite can ever prove**, and no file in the repo states the bound.
Concretely, Mollusk as configured here structurally cannot cover:

| Threat class it cannot reach | Why |
|---|---|
| `S1-C6` vault accounting, success side | `withdraw_collateral` ends in an SPL Token `Transfer` CPI (`programs/slipstream/src/instructions/withdraw_collateral.rs:137-143`) to a program that is not loaded. All three tests are therefore revert-path-only, and the file says so at `tests/unit/src/test_withdraw_collateral_regressions.rs:59`. No test has ever moved a token. |
| `S5-C1`, `S5-C9`, `S5-C10` delegation lifecycle | every delegate/undelegate/commit ends in a CPI to `DELeGGvXpWV2fqJUhqcF5ZSYMS4JTLjteaAMARRSaeSh` or the magic program. Neither is loaded. |
| `S2-C11` ER execution under a hostile sequencer | Mollusk is one in-process SVM with one L1 clock. It cannot model an ER-controlled `Clock`, so `S2-03` (session-key expiry decided by the sequencer's clock) has no reachable test. |
| `S4-C8` trust in ER-authored data | there is no ER, so "the ER wrote these bytes" and "L1 wrote these bytes" are indistinguishable in the harness. A test can hand-craft hostile bytes, but nothing forces the distinction. |
| `S4-C1` exactly-once across a commit boundary | a commit is a CPI to an unloaded program; the ER→L1 hand-off cannot be executed at all, only simulated by hand-writing the post-state. |

What Mollusk *does* cover honestly, and covers well: single-instruction account
validation, discriminator and owner checks, PDA pinning, and every branch of the value
math that terminates before a CPI. That is the correct reading of the "123 passing tests"
figure and it is a narrower claim than the figure implies.

**Proof.**

```

$ grep -n "mollusk-svm" tests/unit/Cargo.toml

    #[cfg(feature = "all-builtins")] ...            <- not enabled by tests/unit/Cargo.toml:12
```

Three tests over the one instruction that removes money from the vault; all three are
rejections; the token program they pass is `Pubkey::new_unique()` with
`Account::default()`, annotated "unused before every revert path tested here".

**Blast radius.** Reviewers, and anyone sizing the project's assurance from the test
count. The unwritten invariant here — nothing in the repo states what the suite structurally
cannot cover — is itself the P3 defect under `docs/spec/audit-e2e.md:195-197`. It cost this
audit real time to establish, and a reader without a Solana background would take "123

**Suggested remediation.** Add `mollusk-svm-programs-token` and load the SPL Token program
in the harness helper so the `deposit_collateral` / `withdraw_collateral` success paths
become testable; then put the residual ceiling (no ER, no delegation program, no
sequencer-controlled clock) in a header comment at `tests/unit/src/lib.rs:1-6`, where the
current comment points at the unrun integration suite instead.

### S11-06 · Batched P3 — the one integration test that runs offline is gated nowhere, one suite asserts nothing, and the suite's cross-package import is undeclared

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S11-C5
- **Evidence:** `tests/integration/manifest_wellformedness.test.ts:30-31`, `tests/integration/option_b_flow.test.ts:250-257`, `tests/integration/crank_twap_harness.ts:41`, `.github/workflows/ci.yml:71-73`

**What is wrong.** Three separate gaps, all in the state of the unrun suite, batched per
`docs/spec/audit-e2e.md:35`.

1. **The one offline suite is not a gate.** Six of the seven `.test.ts` files need a live
   devnet, an ER, or the operator keypair. `manifest_wellformedness.test.ts` needs none —
   its own header says "Run (fully offline, no SOL required)" at
   `tests/integration/manifest_wellformedness.test.ts:30-31` — and it validates the real
   emitted `deploy.json` in about two seconds. It appears in no CI job
   (`.github/workflows/ci.yml:71-73` is the last test step and it is Rust) and it is not in
   the suite's own aggregate script (`tests/integration/package.json:12`). The one piece of
   the suite that could be evidence is the one piece nothing runs.
2. **`option_b_flow.test.ts` verifies nothing.** It is named `.test.ts` and sends the
   entire Option-B flow, but contains no assertion and no check helper of any kind: it
   fails only if a transaction throws (`tests/integration/option_b_flow.test.ts:250-257`).
   It is also the only suite file with no `package.json` script. By contrast
   `full_flow.test.ts` and `er_orderbook.test.ts` both use a counted `check()` helper and
   exit non-zero — so the suite has the right pattern available and this file skips it.
3. **An undeclared cross-package dependency.** `tests/integration/option_b_flow.test.ts:59`
   and `tests/integration/crank_twap_harness.ts:41` import from `../../client/src`, whose
   own dependencies are not in `tests/integration/package.json`. Following the suite's
   README literally therefore leaves it un-type-checkable. `.github/workflows/ci.yml:111-118`
   shows the project already knows this shape of problem and solves it for `keepers/` with
   a second `npm ci`; the integration suite has no equivalent because it has no CI job.

**Proof.** The suite *does* still compile against the current SDK once `client/`'s
dependencies are present — that half is clean:

**Suggested remediation.** Add `npx tsx manifest_wellformedness.test.ts` to the CI
frontend or rust job (it needs only Node and the repo), add it to
`tests/integration/package.json:12`'s `test:all`, add a `check()` helper and exit code to

### S11-08 · Every Mollusk file mutates the process environment from inside parallel test threads

- **Status:** CONFIRMED
- **Severity:** P3
- **Class:** S11-C6
- **Evidence:** `tests/unit/src/test_close_position.rs:21-27`, `tests/unit/src/test_security_regressions.rs:23-29`, `tests/unit/src/test_place_order_regressions.rs:17`, `tests/unit/src/test_settle_trades_regressions.rs:25`

**What is wrong.** Sixteen files define the same harness helper, and each one calls
`std::env::set_var("SBF_OUT_DIR", …)` on every invocation
(`tests/unit/src/test_close_position.rs:22`). The helper is called from inside each
`#[test]` function, and the Rust test harness runs tests on a thread pool by default —
there is no `.cargo/config.toml` and no `--test-threads` setting anywhere in the repo, and
the interleaved program logs in a normal run confirm concurrent execution. `set_var`
writes the process environment while other threads may be reading it; the C `setenv`
underneath is not thread-safe against concurrent `getenv`, which is why Rust made
`std::env::set_var` `unsafe` in edition 2024. The crate is on edition 2021
(`tests/unit/Cargo.toml`), so it compiles today. All sixteen copies write the *same* value,
which is why it has never misbehaved — the race is benign in outcome but not in mechanism,
and it will refuse to compile on an edition bump.

**Proof.**

```
$ grep -rn "set_var" tests/unit/src/*.rs | wc -l
16
$ ls .cargo/config.toml tests/unit/.cargo/config.toml 2>&1
ls: cannot access '.cargo/config.toml': No such file or directory
ls: cannot access 'tests/unit/.cargo/config.toml': No such file or directory
                        # no --test-threads override anywhere: the harness is parallel
$ cargo test --workspace 2>&1 | sed -n '/invoke \[1\]/,+3p' | head -4
Program 11172Xj9y... invoke [1]          <- two programs from two different tests
Program 1117ntbFo... invoke [1]             interleaved inside one harness run
Program 11172Xj9y... consumed 149 of 1400000 compute units
Program 1117ntbFo... consumed 237 of 1400000 compute units
```

**Blast radius.** CI reliability only; no on-chain consequence. The realistic failure is a
future contributor pointing one file's helper at a different `SBF_OUT_DIR` (a second
program, a fixtures directory) and getting a non-deterministic pass/fail depending on
thread interleaving — the hardest class of test failure to diagnose. The certain
consequence is that a move to edition 2024 breaks all sixteen files at once.

**Suggested remediation.** Set `SBF_OUT_DIR` once, outside the test threads — a
`tests/unit/build.rs` emitting `cargo::rustc-env=SBF_OUT_DIR=…`, or a `[env]` block in a
`.cargo/config.toml`, or `Mollusk::new_with_elf` reading the `.so` path directly — and
delete all sixteen `set_var` calls.
