### S13-01 · The order ticket's leverage slider and "Margin at risk" describe a position `place_order` will not open

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S13-C1` — Data honesty, per-number source table
- **Evidence:** `frontend/src/components/trading/order-form.tsx:35-41`, `frontend/src/components/trading/order-form.tsx:94-102`, `frontend/src/components/trading/order-form.tsx:106`, `frontend/src/components/trading/order-form.tsx:376-388`, `frontend/src/components/trading/order-form.tsx:431-434`, `programs/slipstream/src/instructions/place_order.rs:169-171`, `programs/slipstream/src/math/fixed_point.rs:64-69`, `programs/slipstream/src/instructions/liquidate_position.rs:131-134`

**What is wrong.** The ticket has a 1×–20× leverage slider (`order-form.tsx:376-388`) and
a summary row labelled **"Margin at risk"** whose value is `actualNotional / leverage`
(`order-form.tsx:101`, rendered at `:433`). The leverage the trader picks is never
transmitted: `createPlaceOrderInstruction` is given side, type, price, size, expiry and
slippage only (`order-form.tsx:157-170`), and the program computes the margin it will
actually reserve as `notional / market.max_leverage` — always 20 —
(`place_order.rs:169-171` calling `fixed_point.rs:64-69`). The same component already
knows this: its own `requiredMarginAtoms` helper divides by `MAX_LEVERAGE`
(`order-form.tsx:37-41`) and is used for the submit-time credit check at `:142`. So the
component computes two different "margin" numbers and shows the wrong one. The comment
at `order-form.tsx:35-36` claims the displayed math mirrors "the (now FIXED) on-chain
math"; it does not. The consequence is not cosmetic: because the reserved margin is
always `notional/20`, maintenance margin is always `notional/40`
(`liquidate_position.rs:134`), so **every position liquidates on a 2.50% adverse move
regardless of the leverage the trader selected**.

**Proof.** `docs/audit/audit-e2e/repro/s13/live-render.mjs`, at the live oracle price:

```
=== order-form.tsx: 'Margin at risk' vs place_order.rs:171 ===
  lev  1x  size 1.1 SOL  notional $100.15  | shown "Margin at risk" $100.15  | program reserves $5.01  | liquidates on a 2.50% adverse move
  lev  2x  size 2.2 SOL  notional $200.30  | shown "Margin at risk" $100.15  | program reserves $10.01  | liquidates on a 2.50% adverse move
  lev  5x  size 5.5 SOL  notional $500.75  | shown "Margin at risk" $100.15  | program reserves $25.04  | liquidates on a 2.50% adverse move
  lev 10x  size 11.0 SOL  notional $1001.50  | shown "Margin at risk" $100.15  | program reserves $50.07  | liquidates on a 2.50% adverse move
  lev 20x  size 22.0 SOL  notional $2002.99  | shown "Margin at risk" $100.15  | program reserves $100.15  | liquidates on a 2.50% adverse move
```

The instruction carries no leverage field — `grep -n 'leverage' frontend/src/lib/slipstream/instructions.ts`
returns nothing, and the builder's parameter object at `order-form.tsx:159-167` has six
keys, none of them leverage.

**Why nothing surfaced it.** The displayed number is always **≥** the reserved number for
any `leverage ≤ MAX_LEVERAGE`, so the client-side blocker at `order-form.tsx:106` and
`:244-245` is strictly more conservative than the chain. Orders that pass the UI always
pass the program. Nothing errors, nothing reverts, and the two numbers are never printed
side by side.

**Blast radius.** Every trader who moves the slider below 20×. A trader who selects "1×"
and reads "Margin at risk $100.00" believes they hold an unleveraged position with a ~50%
buffer; the chain holds a 20× position with $5.01 of collateral that liquidates 2.5% away.
On mainnet this is the difference between a position surviving a normal session and being
liquidated in the first hour. The overstatement of margin also means the trader's real
free collateral is 20× what the ticket implies, so they can silently open far more risk
than the panel says they can afford.

**Suggested remediation.** Render "Margin at risk" from `requiredMarginAtoms(sizeVal, priceVal)`
— the number the component already computes for the submit check — and label the slider
"Position size multiplier", or remove it and size directly, until the program accepts a
per-order leverage. Add a line stating the liquidation distance the reserved margin
actually buys.

### S13-02 · Positions are priced off the frozen mark, so the terminal shows a green health score on a position `liquidate_position` computes as liquidatable

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S13-C1` — Data honesty, per-number source table
- **Evidence:** `frontend/src/components/trading/dashboard.tsx:28`, `frontend/src/components/trading/dashboard.tsx:50`, `frontend/src/components/trading/positions-table.tsx:283`, `frontend/src/components/trading/positions-table.tsx:355`, `frontend/src/components/trading/positions-table.tsx:358-365`, `frontend/src/components/trading/positions-table.tsx:520-540`, `frontend/src/components/trading/market-bar.tsx:53-55`, `programs/slipstream/src/instructions/liquidate_position.rs:91-101`, `programs/slipstream/src/instructions/liquidate_position.rs:131-157`, `PRODUCT.md:16`

**What is wrong.** `dashboard.tsx:28` reads `market.lastMarkPrice` — the K1-frozen value —
and hands it to `ActivityDrawer` (`:50`), which hands it to `PositionsTable`. Every
per-position figure is then derived from it: the column literally headed **"Mark"**
(`positions-table.tsx:283`, `:355`), the liquidation price and health factor
(`:358-365` → `liqAndHealth` at `:520-540`), and the uPnL that `use-positions.ts` computed
from the same argument. None of them carries the staleness treatment the market bar
applies to the identical value 400 px above: `market-bar.tsx:53-55` states the invariant
outright — *"if the keepers stop, mark freezes while the market does not, and showing the
frozen number as 'the price' would be a lie"* — and acts on it at `:101-104` and `:117-124`.
The positions table inherits none of that. Worse, the on-chain liquidation engine does
**not** use `last_mark_price` at all: `liquidate_position.rs:91-101` reads the live
dual-oracle price and recomputes notional, maintenance margin and uPnL against it
(`:131-156`). So the two sides disagree by construction, not just by staleness.
`PRODUCT.md:16` makes "every claim on screen traces to something a reader can check" the
binding principle; a health score that the liquidator will contradict fails it.

**Proof.** `docs/audit/audit-e2e/repro/s13/live-render.mjs`, live devnet at
2026-08-21T19:36Z — `last_mark_price` $74.114 (last written 2026-08-05), configured Pyth
feed $91.05, 73 s fresh:

```
=== UI health vs liquidate_position.rs, at the live prices above ===
  SHORT 1 SOL @ entry $74.114 (the terminal's own "Mark")
    UI    -> health 2.00 GREEN, liq $75.97, uPnL +$0.00
    chain -> health 0.00 *** LIQUIDATABLE (HEALTH_FACTOR_LIQUIDATION_THRESHOLD = 1.0) ***, uPnL -$16.93
  LONG 1 SOL @ entry $74.114 (the terminal's own "Mark")
    UI    -> health 2.00 GREEN, liq $72.26, uPnL +$0.00
    chain -> health 9.07 safe, uPnL +$16.93
```

The short's liquidation price as the UI renders it ($75.97) was crossed sixteen days ago;
the UI cannot show that because its own "Mark" column reads $74.11. The same run shows the
market bar doing the right thing with the same input (`headline "91.05"`, `Mark stat
"74.114"`, label `"Mark (stale)"`), which is what makes this a seam defect rather than a
missing feature.

**Why nothing surfaced it.** The decision to distrust the frozen mark was taken inside
`market-bar.tsx` and never expressed as a value the rest of the terminal could consume.
`dashboard.tsx:28` passes the raw `bigint` down with no freshness flag, and
`liqAndHealth` has no parameter that could carry one. A second contributor: `liqAndHealth`
deliberately discards the position's real collateral (`positions-table.tsx:505-511`,
`_collateral` unused at `:525`), so the health score is a pure function of entry price and
a constant — at `mark == entry` it returns exactly 2.00 for every position that has ever
existed, which reads as a plausible number and never as a bug.

**Blast radius.** Every trader holding a position while the crank is stopped — the live
condition since 2026-08-05. A short reads GREEN / health 2.00 and is liquidatable now; a
long reads its uPnL $16.93 too low and would close a winning position at a loss. On
mainnet the short case is the expensive one: the screen actively tells the user they have
a 2× buffer at the moment a liquidator can take their collateral, and the trader has no
on-screen reason to add margin.

**Suggested remediation.** Give `useMarket` a `markFresh` boolean once S6-01 lands the
`Market._padding1` stamp in the decoder, pass it through `dashboard.tsx:28`, and have
`positions-table.tsx` render "—" plus the market bar's stale banner for Mark / Liq. /
Health / uPnL when it is false. Separately, feed `liqAndHealth` the position's real
`collateral` and the live oracle price so the displayed health matches
`compute_health_factor`.

### S13-03 · The book panel renders a sixteen-day-old ladder as live, with a bold "mid" 18.6% away from the oracle

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S13-C2` — Stale and error states
- **Evidence:** `frontend/src/components/trading/order-book-display.tsx:37`, `frontend/src/components/trading/order-book-display.tsx:96-113`, `frontend/src/components/trading/order-book-display.tsx:126-134`, `frontend/src/components/trading/order-book-display.tsx:187-199`, `frontend/src/lib/slipstream/accounts.ts:416-430`, `PRODUCT.md:16`

**What is wrong.** The panel has exactly three states beyond "has rows":
`loading`, `unavailable`, and `empty` (`order-book-display.tsx:96-113`). There is no state
for *"the book decoded, it has depth, and the depth is ancient"* — which is the live
condition (K4). A non-empty stale ladder renders byte-identically to a live one: the mid
is the largest, boldest number in the column (`:126-134`), and the buy/sell pressure bar
below it (`:187-199`) presents sixteen-day-old resting depth as current market balance.
The panel is careful elsewhere — `:184-187` explains why the pressure bar is hidden when
the book is empty, "rendering a half-and-half bar next to 'No resting orders' would invent
a split that does not exist" — so the invariant is understood in this file; it simply is
not applied to stale depth.

**Proof.** `docs/audit/audit-e2e/repro/s13/live-render.mjs`, reading the ER book the
terminal actually renders:

```
=== ER order book, what order-book-display.tsx renders ===
  activeOrderCount 12  bidLevels 6  askLevels 6
  order-book-display.tsx:128  "mid" = 74.154   spread 0.208
  oracle now $91.045 -> the rendered mid is 18.6% away
  the empty-state branch (:100-104) only knows loading / unavailable / empty;
  a 16-day-old ladder renders identically to a live one.
  active slots 12; slots carrying a non-zero expiry_ts: 0
  -> OrderSlot has no creation timestamp (accounts.ts:416-430), so age cannot be
     derived from the book; a mid-vs-oracle check is the only available signal.
```

**Why nothing surfaced it.** `OrderSlot` stores `expiry_ts` but no creation timestamp
(`accounts.ts:416-430`), and all twelve resting orders were placed with `expiryTs: 0n`
(the value `order-form.tsx:165` always sends), so the book carries no age data at all.
The panel therefore has nothing to key a staleness state off *from the book itself* —
the signal has to come from outside, and no one wired it.

**Blast radius.** Anyone reading the terminal for a price. A trader who prices a limit
order off the displayed mid of 74.154 posts an order 18.6% through the real market: a bid
there never fills, an ask there is instantly picked off by the first live counterparty.
On mainnet the ask case is a direct, silent transfer of ~18% of notional to whoever is
watching.

**Suggested remediation.** Reuse the comparison the market bar already computes
(`market-bar.tsx:59-63`): when `|mid − oracle| / oracle` exceeds the same
`MARK_DIVERGENCE_WARN` threshold, tone the mid down, label it "stale book", and hide the
pressure bar exactly as the empty case already does.

### S13-04 · "Close" on a pending ER position builds its crossing price from the frozen mark, so closing a short cannot fill

- **Status:** CONFIRMED
- **Severity:** P1
- **Tag:** [reachable-now]
- **Class:** `S13-C2` — Stale and error states
- **Evidence:** `frontend/src/components/trading/positions-table.tsx:51-54`, `frontend/src/components/trading/positions-table.tsx:80-84`, `frontend/src/components/trading/positions-table.tsx:118-120`, `frontend/src/components/trading/positions-table.tsx:308-317`, `frontend/src/components/trading/order-form.tsx:58-68`

**What is wrong.** `handleFlatten` is documented at `positions-table.tsx:51-54` as *"the
way to close a position that hasn't settled to an L1 Position yet"* — for a pending ER
position it is the only way. It builds a marketable IOC limit as `mark * 0.95` (long) or
`mark * 1.05` (short) at `:82-83`, where `mark` is the same frozen `last_mark_price`. A ±5%
band around a value that is 18.6% below the market does not reach the market on the buy
side. The button at `:308-317` reports nothing about this; the failure surfaces only as
whatever the RPC says, printed raw at `:118-120` — this component has no equivalent of
`order-form.tsx:58-68`'s `decodeProgramError`, so the user does not even get the program's
error name.

**Proof.** `docs/audit/audit-e2e/repro/s13/live-render.mjs`:

```
=== positions-table.tsx:83 flatten cross price, built off the frozen mark ===
  closing a LONG  -> IOC ASK limit $70.408  (best bid is near $91.05) -> fills
  closing a SHORT -> IOC BID limit $77.820  (best ask is near $91.05) -> DOES NOT CROSS, silently no-fills
```

An IOC that crosses nothing is cancelled by the matching engine, so the transaction
confirms, `refresh()` runs at `:117`, and the row comes back unchanged with no error text.

**Why nothing surfaced it.** The 5% band is generous relative to any *live* mark, so the
code is correct whenever the crank is running — which it was for the entire period the
component was written and tested. It fails only in the regime K1 created, and it fails on
one side only, which is exactly the shape that survives manual testing.

**Blast radius.** Any trader holding an unsettled short while the crank is stopped — a
population the stalled settlement keeper makes larger, not smaller. They press Close,
watch it appear to succeed, and remain exposed. On mainnet that is an unbounded loss on a
position the user believes they exited.

**Suggested remediation.** Build the crossing price from the live oracle
(`useLivePrice().live.price`) with the frozen mark only as a last resort, refuse to submit
when the two disagree by more than the market bar's threshold, and route the catch at
`:118-120` through `decodeProgramError` so a rejection names the program error.

**Proof.** The two feeds are distinct accounts and both were read live:


(`docs/audit/audit-e2e/s9.md:9`) independently records the same row: *"Display only — no

**Blast radius.** No wrong number today: the two feeds track the same asset and agreed to

- **Status:** CONFIRMED

- **Class:** `S13-C2` — Stale and error states
